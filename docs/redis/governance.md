# Redis 使用规范与平台化治理

> [!ABSTRACT] 核心要点
> - 多团队共用 Redis，最常见的事故来源是**使用方式**而不是 Redis 本身：**无 TTL、大 key、危险命令、`KEYS`、连接泄漏、超时重试风暴、缓存与数据库不一致、把 Redis 当可靠存储**。治理的目标是**把最佳实践固化到 SDK、平台和流程里**，而不是靠文档提醒。
> - **规范分四层**：**用法边界（该不该用 Redis、存什么）→ 数据设计（key/value/过期/结构）→ 客户端使用（连接池、超时、重试、序列化、降级）→ 运维流程（申请、变更、监控、成本）**。
> - **客户端配置是高危区**：**超时、连接池、重试、集群拓扑刷新、序列化**配错会在 Redis 抖动时放大成全站故障；要提供**经过压测的默认配置模板**与**统一封装**。
> - **实例分级与隔离**：核心交易、普通缓存、大数据/离线、测试环境分开；重要业务**独占实例/集群**，防止邻居噪声。**缓存与存储两类用途分开**（淘汰策略与持久化需求不同）。
> - **平台化能力**：自助申请与审批、容量与成本看板、Key 画像与大 key/热 key 巡检、慢日志与命令审计、变更与扩缩容流程、ACL 与账号管理、一键切换与演练。
> - 度量治理效果：**因 Redis 引起的故障数、大 key/无 TTL 占比、命中率、使用率、申请到交付时长、成本**。

## 用不用 Redis：边界

| 场景 | 结论 | 说明 |
| --- | --- | --- |
| **热点读缓存（可回源重建）** | ✅ 最典型 | 配 TTL、回源保护，见 [缓存设计与一致性](#/redis/cache) |
| **计数、排行榜、限流、去重、会话** | ✅ | 数据结构契合；注意持久化与丢失的业务容忍度，见 [高频场景实战](#/redis/practice) |
| **分布式锁（效率型）** | ⚠️ 可用 | 安全型强一致场景用协调服务 + fencing，见 [分布式锁](#/redis/lock) |
| **消息队列** | ⚠️ 轻量/临时 | Stream 可用，但可靠性、堆积与回溯不如专业 MQ，见 [消息队列核心问题](#/mw/mq) |
| **主存储/唯一数据源（订单、资金）** | ❌ 不建议 | 持久化与一致性弱于数据库，主从异步丢写；如必须，评估 AOF/多副本/同步复制并保留对账 |
| **大对象/文件** | ❌ | 用对象存储，Redis 只存引用 |
| **全文检索/复杂查询** | ❌ | 用 ES/数据库 |
| **海量冷数据** | ❌ | 内存成本高，冷热分层 |

原则：**Redis 里的数据应当“丢了可恢复、慢了可降级”**。无法接受丢失的数据，必须有权威的持久化来源与对账机制。

## 数据设计规范

### key 规范

| 规范 | 说明 |
| --- | --- |
| **命名** | `<业务域>:<模块>:<对象>:<标识>`（如 `trade:order:detail:{orderId}`）；小写与冒号分隔；前缀稳定，便于按前缀统计与治理；**含版本时放在前缀**（`v2`）便于迁移 |
| **长度** | 适度精简（不要过长），但不要缩到不可读；海量小 key 时可制定缩写字典，见 [内存优化与容量治理](#/redis/memory) |
| **环境隔离** | 用独立实例/库/ACL 区分环境，不依赖 key 前缀混用 |
| **禁用不确定内容** | 不放空格、换行、随机无限基数（如把完整 URL 作 key 且无 TTL） |
| **集群 hash tag** | 仅在确需多 key 原子操作时使用，粒度细到业务实体，避免倾斜，见 [Redis Cluster 生产运维](#/redis/cluster-ops) |
| **登记制** | 新增 key 前缀登记：用途、负责人、预估数量与大小、TTL、是否允许淘汰、读写 QPS |

### value 规范

- **大小**：String value 控制在 **10KB 以内**（超过要评审），避免大 key，见 [大 key 与热 key 治理](#/redis/bigkey)；
- **集合规模**：Hash/List/Set/ZSet 元素数有**上限**（如 5000，可按业务调整）并在写入时裁剪；
- **序列化**：统一使用**可演进的格式**（JSON 加版本字段，或 Protobuf/Avro）；**禁止 Java 原生序列化**（体积大、版本脆弱、反序列化漏洞）；
- **版本兼容**：新旧代码并存期间，缓存结构要**向前向后兼容**，或 key 前缀带版本避免互读；
- **敏感数据**：不存明文敏感信息（密码、证件号）；必要时加密/脱敏，见 [加密与密钥管理](#/security/crypto)；
- **空值与否定缓存**：对“不存在”缓存短 TTL 的空标记，防穿透。

### 过期规范

| 规范 | 说明 |
| --- | --- |
| **缓存类必须设置 TTL** | 无 TTL 的 key 会无限累积；平台扫描并告警 |
| **TTL 随机抖动** | 在基准 TTL 上加随机偏移（如 ±10%），避免同时过期 |
| **TTL 与业务一致性窗口匹配** | 缓存与数据库的最终一致窗口由 TTL 兜底，见 [缓存设计与一致性](#/redis/cache) |
| **会话/令牌类** | 按业务过期，续期策略明确 |
| **存储类（不能过期）** | 单独实例、明确容量与归档，不与缓存混用 |

### 命令规范

| 类别 | 规范 |
| --- | --- |
| **禁止** | `KEYS`、`FLUSHALL/FLUSHDB`（业务账号）、`DEBUG`、`CONFIG`（业务账号）、`MONITOR`（生产长期）、`SAVE`（同步） |
| **限制/审查** | `HGETALL`、`SMEMBERS`、`LRANGE 0 -1`、`ZRANGE` 全量、`SORT`、`SUNION/SINTER` 大集合、`DEL` 大 key |
| **推荐** | `SCAN/HSCAN/SSCAN/ZSCAN` 分页遍历；`UNLINK` 删除；`MGET/Pipeline` 批量；Lua 脚本保持短小（毫秒级）；`SET key value EX ttl NX` 一条命令设置带过期的锁/幂等标记 |
| **事务/脚本** | 集群下多 key 要同槽；Lua 里不要长循环与阻塞；脚本版本管理 |
| **Pipeline** | 批量大小适中（几百到几千条），过大占内存与阻塞，见 [线程模型与高性能原理](#/redis/overview) |
| **阻塞命令** | `BLPOP` 等用专用连接，设置超时 |

## 客户端使用规范（Java）

### 客户端选型

| 客户端 | 特点 | 适用 |
| --- | --- | --- |
| **Lettuce** | 基于 Netty，**线程安全的单连接多路复用**，支持响应式、集群、哨兵，Spring Data Redis 默认 | 大多数场景首选 |
| **Jedis** | 同步阻塞，**连接非线程安全，需连接池**，API 直观 | 简单场景、老项目 |
| **Redisson** | 在 Redis 之上提供分布式对象与同步器（锁、信号量、限流器、延迟队列等） | 需要丰富分布式原语时；注意引入的是**抽象层与特定数据结构**，见 [分布式锁](#/redis/lock) |
| **Spring Data Redis** | 统一抽象（`RedisTemplate`），可切换底层客户端 | 与 Spring 生态集成 |

```java
// Lettuce 集群客户端的关键配置示意（具体 API 以所用版本为准）
ClusterTopologyRefreshOptions refresh = ClusterTopologyRefreshOptions.builder()
        .enablePeriodicRefresh(Duration.ofSeconds(30))        // 周期刷新拓扑
        .enableAllAdaptiveRefreshTriggers()                   // MOVED/ASK/连接断开等事件触发刷新
        .adaptiveRefreshTriggersTimeout(Duration.ofSeconds(10))
        .build();

ClusterClientOptions options = ClusterClientOptions.builder()
        .topologyRefreshOptions(refresh)
        .maxRedirects(3)                                       // 限制重定向次数
        .validateClusterNodeMembership(true)
        .socketOptions(SocketOptions.builder().connectTimeout(Duration.ofMillis(500)).keepAlive(true).build())
        .timeoutOptions(TimeoutOptions.enabled(Duration.ofMillis(150)))   // 命令超时
        .disconnectedBehavior(ClientOptions.DisconnectedBehavior.REJECT_COMMANDS) // 断连时快速失败，而不是无限排队
        .build();
```

要点：

- **`disconnectedBehavior`/请求队列**：Lettuce 默认在断连时会把命令排队，队列大会占内存并拖长故障恢复；生产要限制队列大小或选择快速拒绝；
- **Lettuce 单连接多路复用 vs 连接池**：普通命令单连接足够；**事务、阻塞命令、大量并发 Pipeline** 才需要池化；
- **Jedis 池大小**：`maxTotal` 与应用并发匹配，`maxWait` 设短并有降级，**用完必须归还**（try-with-resources）；
- **拓扑刷新**：周期 + 事件触发都要开，避免扩缩容/故障转移后路由失效，见 [主从、哨兵与 Cluster](#/redis/cluster) 的客户端拓扑刷新；
- **超时对齐**：Redis 调用超时应小于上游接口的超时预算，见 [OpenFeign 深入](#/spring/cloud-feign) 的预算递减；
- **缓存访问封装**：统一的缓存组件封装“查缓存→未命中回源→回填→防穿透/击穿/雪崩”，业务只写回源逻辑，避免每个团队重复造轮子。

### 统一封装（SDK）应包含

| 能力 | 说明 |
| --- | --- |
| **key 构造器** | 强制使用登记的前缀与版本，禁止手拼字符串 |
| **TTL 强制** | 缓存写入必须传 TTL（自动加抖动） |
| **大小检查** | 写入前检查 value 大小与集合规模，超限拒绝/告警 |
| **命令白名单/拦截** | 禁止危险命令，对全量读操作要求分页 |
| **序列化** | 统一格式与版本 |
| **回源保护** | 互斥/逻辑过期、空值缓存、回源限流 |
| **降级与熔断** | Redis 故障时的策略可配置 |
| **指标与日志** | 按前缀统计命中率、耗时、错误、大小；慢调用日志 |
| **热点识别** | 本地计数 Top-K，上报热 key，可选自动本地缓存 |
| **多级缓存** | 本地缓存 + Redis，失效广播 |

## 实例分级、隔离与容量管理

| 维度 | 做法 |
| --- | --- |
| **用途分离** | **缓存集群**（可淘汰、可不持久化或仅副本持久化）与**存储集群**（`noeviction`、AOF/多副本、严格容量管理）分开 |
| **业务等级** | P0 核心交易独占实例/集群，P1/P2 共享但配额隔离，离线/大数据类单独集群，避免邻居噪声 |
| **规格标准化** | 提供标准规格（如 8G/16G/32G，主从/集群），避免随意定制，便于运维与采购；单分片内存上限受 fork 与恢复时间约束，见 [Redis Cluster 生产运维](#/redis/cluster-ops) |
| **容量申请** | 提供**数据量、key 数、QPS、峰值、读写比、value 大小、TTL、是否持久化、可用性要求**；平台据此评估规格与是否适合 Redis |
| **配额与限流** | 实例级 `maxmemory`、连接数；代理/平台层的命令限流与大小限制 |
| **多租户** | 同一集群的多个业务用 ACL 隔离 key 前缀与命令；监控按前缀拆分 |
| **环境** | 开发/测试/预发/生产独立，测试环境规格缩小；禁止测试连生产 |
| **生命周期** | 实例有负责人、到期复核；闲置实例回收 |

## 变更与发布管理

| 变更类型 | 要求 |
| --- | --- |
| **扩缩容/迁移** | 变更单审批；预发演练；低峰窗口；回退方案；见 [Redis Cluster 生产运维](#/redis/cluster-ops) |
| **参数变更**（maxmemory、淘汰策略、持久化） | 灰度（先副本/小实例）；记录；注意动态与持久配置的一致（`CONFIG REWRITE`） |
| **版本升级** | 兼容性评估；滚动升级；备份；回退，见 [Redis Cluster 生产运维](#/redis/cluster-ops) |
| **ACL/账号变更** | 审批；最小权限；与应用发布协同；密钥轮换留过渡期 |
| **业务缓存结构变更**（序列化格式、key 结构） | **向前向后兼容**；双写/新旧 key 共存；灰度；旧 key 用 `UNLINK` 分批清理，见 [配置管理与全链路灰度](#/spring/cloud-config-gray) 的数据兼容思路 |
| **大促/活动** | 提前评估容量、预热、压测、限流降级预案；冻结非必要变更 |
| **危险操作**（清空、批量删除、重置） | 双人复核、审批、备份、限速执行、审计 |

## 监控、告警与 SLO

| 层 | 指标 | 说明 |
| --- | --- | --- |
| **实例/集群** | 可用性、内存使用率、CPU、网络、连接数、命中率、慢日志数、failover 次数、复制延迟、fork 耗时、碎片率 | 见 [Redis Cluster 生产运维](#/redis/cluster-ops)、[故障排查与安全加固](#/redis/troubleshooting) |
| **业务前缀** | 每个前缀的 key 数、内存、QPS、命中率、无 TTL 占比、最大 key | Key 画像，驱动整改与成本 |
| **客户端** | 命令耗时分位、错误率、超时、池等待、重定向次数 | 由 SDK 统一上报 |
| **治理指标** | 大 key 数、无 TTL key 占比、危险命令调用次数、容量使用率分布、变更失败数 | 衡量治理成效 |

**SLO 示例**：可用性（如 99.95%）、命令 P99 延迟（如 < 5ms，不含客户端网络）、故障切换时间（如 < 30 秒）、数据丢失窗口（缓存无承诺/存储明确）。**告警分级并路由到业务负责人**，附 Runbook 链接；告警基于症状（延迟、错误、命中率下降）和容量水位。

## 平台化能力

| 能力 | 价值 |
| --- | --- |
| **自助申请与审批** | 标准化规格、容量评审、自动开通、ACL 账号、接入文档 |
| **服务目录与负责人** | 每个实例/前缀的归属、联系人、等级、用途 |
| **Key 画像与巡检** | 定期扫描副本/RDB，输出大 key、无 TTL、热点、编码、内存占比报告并自动提单，见 [大 key 与热 key 治理](#/redis/bigkey) |
| **慢日志与命令审计** | 集中收集，按应用/命令聚合，发现危险调用与回归 |
| **代理层（可选）** | 统一接入、连接收敛、命令限制、限流、热 key/大 key 统计、读写分离与拆分；代价是多一跳与新的单点，需高可用 |
| **运维自动化** | 扩缩容、故障转移、版本升级、备份恢复的自动化流程与审批 |
| **成本看板** | 按业务统计内存与 QPS，成本分摊，容量预测 |
| **演练与混沌** | 定期演练主从切换、网络故障、实例不可用，验证应用降级，见 [稳定性工程：混沌实验与容灾演练](#/design/eng-chaos) |
| **文档与培训** | 最佳实践、反模式案例、值班手册 |

**自建还是托管**：云托管 Redis 能免去大部分运维（备份、HA、监控），但仍需要上述**使用规范与治理**；自建则要具备运维能力与平台投入。代理层与托管服务的取舍取决于规模、成本与团队能力。

## 落地顺序

1. **止血（1~2 周）**：禁用/限制危险命令（ACL）；缓存类无 TTL 的 key 扫描整改；`KEYS` 清零；大 key Top 清单与负责人；慢日志、连接数、内存水位告警；
2. **规范（1~2 月）**：key/value/TTL/命令规范文档；统一 SDK（超时、连接池、重试、序列化、TTL 强制、大小检查、降级）；客户端配置模板；
3. **平台（2~3 月）**：自助申请与容量评审、Key 画像与巡检、命令审计、成本看板；
4. **隔离与容灾（持续）**：缓存/存储分离、业务分级、核心业务独占；故障演练；
5. **持续运营**：定期整改闭环、事故复盘沉淀规范、季度容量与成本评审，见 [事故复盘与改进](#/design/eng-postmortem)。

## 常见反模式

| 反模式 | 后果 | 改进 |
| --- | --- | --- |
| 缓存无 TTL、无上限 | 内存无限增长、OOM | TTL 强制 + 集合上限 + 巡检 |
| 全公司共用一个大实例 | 邻居噪声，一个业务拖垮所有人 | 分级隔离、配额 |
| 用 Redis 当主存储且无对账 | 丢数据无人察觉 | 权威存储 + 对账，或明确存储集群的可靠性方案 |
| `KEYS *`、`HGETALL` 大集合 | 阻塞、切换 | 禁用/分页/拆分 |
| 客户端超时过长、无限重试 | 故障放大成雪崩 | 超时预算、有限重试、退避、熔断 |
| 连接泄漏/每次新建连接 | 连接耗尽、TIME_WAIT 堆积 | 连接池/复用、泄漏检测 |
| 缓存失效后全部打到数据库 | 数据库被击穿 | 互斥/逻辑过期/限流/降级 |
| Java 原生序列化缓存对象 | 体积大、升级反序列化失败 | 统一 JSON/Protobuf + 版本 |
| 多团队随意改 Redis 配置 | 不可控、不可追溯 | 变更审批与配置即代码 |
| 无人负责的 key 前缀/实例 | 僵尸数据、成本浪费 | 登记制 + 负责人 + 到期复核 |
| 只看实例平均指标 | 掩盖倾斜与热点 | 分片/前缀/key 维度监控 |

## 治理检查清单

- [ ] 是否有明确的“能存什么/不能存什么”的用法边界文档？
- [ ] key 前缀是否登记并有负责人，缓存类 key 是否强制 TTL（带抖动）？
- [ ] 是否有统一 SDK（超时、连接池、重试、序列化、大小检查、降级、指标）并推广使用？
- [ ] 危险命令是否通过 ACL 限制，业务账号是否最小权限且独立？
- [ ] 缓存与存储是否分集群，核心业务是否隔离，容量申请是否评审？
- [ ] 是否有 Key 画像、大 key/无 TTL/热 key 的定期巡检与整改闭环？
- [ ] 变更是否有审批、灰度、回滚与审计，大促是否有预案？
- [ ] 监控是否覆盖实例、前缀、客户端三层，告警是否路由到负责人并有 Runbook？
- [ ] 是否演练过 Redis 故障时应用的降级、熔断与回源保护？

## 面试追问

> [!QUESTION] 公司里多个团队共用 Redis，你会怎么治理？
> 先止血：用 ACL 限制危险命令、扫描并整改无 TTL 和大 key、告警慢日志与内存水位。再规范：key 前缀登记与负责人、命名与 TTL 抖动、value 与集合上限、命令规范，并提供统一 SDK 固化超时、连接池、重试、序列化、大小检查与降级。再平台化：容量申请评审、Key 画像巡检、命令审计、成本看板，以及缓存与存储分集群、核心业务隔离，变更走审批灰度回滚。

> [!QUESTION] Redis 客户端有哪些关键配置？配错会怎样？
> 连接与命令超时要分别设置，连接池大小与等待超时要匹配并发，重试次数有限并带退避且写操作要幂等，集群要开启拓扑自动刷新并限制重定向，序列化统一，并配熔断降级和指标。配错会在 Redis 抖动时放大：无限重试和过长超时拖垮线程池与连接池，拓扑不刷新在扩缩容或切换后大量 MOVED，断连时命令无限排队占内存。

> [!QUESTION] 为什么说不要把 Redis 当唯一数据源？
> Redis 主从是异步复制，故障切换可能丢最近的写，持久化也有窗口；内存容量与成本高，缺乏复杂查询和强事务。应让数据库等权威存储作为事实来源，Redis 作可重建的缓存或加速层，如果必须存关键数据，要评估多副本与持久化配置并保留对账。

> [!QUESTION] 缓存集群和存储集群为什么要分开？
> 缓存可被淘汰、数据可回源重建，通常用 allkeys-lru/lfu 且持久化要求低；存储类数据不可丢，需要 noeviction、持久化与严格容量管理。混在一起会让淘汰策略和容量管理冲突，缓存的大量写入还会挤占存储数据的内存。

> [!QUESTION] 客户端统一封装应该包含什么？
> 强制 key 前缀与版本、TTL 必填并加抖动、写入前检查 value 与集合大小、命令拦截、统一序列化、回源保护（互斥、空值缓存、限流）、降级与熔断、命中率耗时错误指标和慢调用日志、热点识别与本地缓存。把最佳实践固化在代码里比写文档更有效。

> [!QUESTION] 怎么衡量 Redis 治理的效果？
> 看因 Redis 引起的故障数、大 key 与无 TTL key 的占比、命中率与内存使用率分布、危险命令调用次数、变更失败数、申请到交付的时长以及成本；同时有 SLO，如可用性、P99 延迟、故障切换时间，并推动整改闭环。
