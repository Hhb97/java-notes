# 稳定性工程：故障演练与混沌实验

> [!ABSTRACT] 核心要点
> - 稳定性不是“不出故障”，而是**故障发生时影响小、发现快、恢复快**。工程上分四层：**预防（设计与变更管控）→ 发现（监控告警）→ 止血（降级/限流/回滚/切换）→ 恢复与复盘**。
> - **混沌工程 = 在受控条件下主动注入故障，验证系统在真实故障下的行为符合“稳态假设”**。原则：**定义稳态 → 提出假设 → 控制爆炸半径 → 渐进注入 → 观察并回收 → 修复缺陷**。**没有验证过的预案等于没有预案**。
> - 超过一半的故障源自**变更**与**依赖**：所以稳定性设计的重点是**超时/重试预算、隔离（舱壁）、熔断降级、过载保护（限流/卸载）、灰度发布与快速回滚**，而不是堆更多机器。
> - 演练分层推进：**桌面推演 → 预发环境注入 → 生产小流量注入 → 全量演练（GameDay）**；每一层都有**止损条件和回滚手段**。
> - 稳定性要**制度化**：故障预案库、降级开关清单、定期演练、事故复盘闭环（见 [事故响应与复盘](#/design/eng-postmortem)）、稳定性指标（可用性、MTTD/MTTR、变更失败率）。

> [!NOTE] 关联
> 限流/熔断/降级机制见 [限流、熔断与降级](#/distributed/governance)，发布与回滚见 [发布策略](#/infra/release)，压测见 [压测与容量规划](#/design/eng-loadtest)，可观测见 [指标监控](#/infra/obs-metrics)、[链路追踪与 SLO](#/infra/obs-trace)。

## 二、高可用设计原则（演练要验证的东西）

| 原则 | 做法 | 演练时验证什么 |
| --- | --- | --- |
| **消除单点** | 多实例、多副本、多可用区；主从自动切换；注册中心/配置中心/网关/DNS 都不是单点 | 杀掉某个节点/某个可用区，业务是否无感 |
| **超时必设，分层递减** | 每次远程调用有连接/读超时，**上游超时 > 下游超时之和**；超时后释放资源 | 下游变慢时上游线程是否被拖死 |
| **重试要克制** | 仅幂等操作；指数退避 + 抖动；**重试预算**（如额外请求 ≤ 10%）；每层重试会**乘法放大**（3 层各重试 3 次 = 27 倍） | 下游故障时是否出现重试风暴 |
| **隔离（舱壁）** | 线程池/连接池/信号量隔离不同依赖和业务；独立集群；故障域隔离 | 一个依赖慢是否影响其他接口 |
| **熔断** | 失败率/慢调用超阈值打开熔断，半开探测恢复 | 熔断是否按预期触发与恢复 |
| **降级** | 非核心功能可关闭/返回兜底（缓存、默认值、静态页）；**事先定义降级清单与开关** | 开关是否生效、核心链路容量是否提升 |
| **限流与过载保护** | 入口限流、按优先级卸载（Load Shedding）、排队有界；保护自己也保护下游 | 超过容量是否优雅拒绝而非雪崩 |
| **幂等与最终一致** | 任何重试/补偿路径都可重入（见 [事件驱动架构](#/design/event-driven)） | 故障恢复后数据是否正确 |
| **灰度与回滚** | 小流量先行、指标自动判定、秒级回滚（见 [发布策略](#/infra/release)） | 回滚是否真能执行、需要多久 |
| **数据安全** | 备份与恢复演练、多副本、防误删（延迟删除/回收站） | 能否在目标时间内恢复到目标时间点（RPO/RTO） |
| **可观测** | 能一眼看出故障范围与原因（指标/链路/日志联动） | 注入故障后告警是否按时触发、是否能定位 |

**重试放大示例**：A→B→C→D 每层最多重试 3 次，D 故障时 D 实际收到最多 `3×3×3 = 27` 倍请求，正好在它最脆弱时压垮它（**重试风暴**）。对策：**只在最靠近用户的一层重试**，其他层 fail fast；或使用重试预算与熔断。

## 三、混沌工程

### 1. 原则（来自 Netflix 的 Principles of Chaos Engineering）

1. **围绕“稳态”建立假设**：稳态用**可测量的业务/系统指标**定义（下单成功率 ≥ 99.9%、P99 < 300ms），不是“机器没报警”；
2. **模拟真实世界事件**：实例宕机、网络延迟/丢包、磁盘满、依赖超时、DNS 故障、时钟漂移、证书过期、突发流量；
3. **在生产环境运行**（成熟后）：只有生产才有真实的流量、数据与依赖；起步先在预发；
4. **自动化持续运行**：把实验做成可重复的流水线，而不是一次性活动；
5. **最小化爆炸半径**：从小范围、小比例开始，有**中止条件（Abort Condition）**与一键回滚。

### 3. 常见故障注入清单

| 类别 | 注入项 | 验证点 |

| **实例/节点** | 杀进程、Kill Pod、节点宕机、重启 | 自愈、负载均衡剔除、无状态/有状态服务恢复、优雅停机 |

| **依赖** | 下游慢/超时/返回错误/限流、数据库主从切换/只读、Redis 宕机/慢、MQ 不可用/积压、第三方失败 | 舱壁、熔断、降级兜底、缓存击穿保护、数据一致性、补偿 |
| **数据** | 数据库慢 SQL、连接耗尽、锁等待、复制延迟、缓存全失效（雪崩） | 连接池保护、读写分离回退、限流 |
| **时间/配置** | 时钟漂移/跳变、配置中心不可用、错误配置下发、证书过期 | 本地缓存配置、证书自动续期告警、时钟同步 |
| **流量** | 突发流量、热点 Key、慢请求大对象、重试风暴 | 限流、过载保护、扩容速度 |
| **应用内** | 方法延迟/异常注入、返回错误码、线程阻塞、GC 压力 | 超时与容错代码路径 |
| **可用区/机房** | 整个可用区断网/下线 | 多可用区冗余容量、流量切换、数据同步与脑裂 |
| **平台/控制面** | K8s 控制面不可用、镜像仓库不可用、CI 故障 | 已运行实例是否不受影响、紧急发布路径 |

## 四、从桌面推演到 GameDay

### 1. 演练阶梯

| 阶段 | 环境 | 内容 | 目的 |
| --- | --- | --- | --- |
| **桌面推演（Tabletop）** | 会议室 | 抛出故障场景，团队口头走一遍预案、沟通、决策 | 发现流程与职责缺口，成本最低 |
| **预发/测试环境注入** | 与生产同构的预发 | 自动化注入基础故障，验证降级、告警、自愈 | 暴露技术缺陷 |
| **生产小流量/单实例注入** | 生产 | 低峰期、小爆炸半径、有中止条件 | 验证真实环境 |
| **GameDay（红蓝对抗）** | 生产或准生产 | 蓝队（运维/开发）不知道具体故障，红队（演练组织者）注入；考验发现、定位、止血与沟通 | 综合演练：监控、预案、协作、工具 |
| **常态化自动演练** | 生产 | 每周/每次发布后自动运行一批已验证的实验 | 防止稳定性退化 |
| **容灾/多活切换演练** | 生产 | 整个机房/可用区切走流量、数据库主备切换、恢复演练 | 验证 RTO/RPO 与切换手册 |

### 2. GameDay 组织要点

- **目标明确**：验证哪些预案/能力，提前定义成功标准；
- **角色**：演练总指挥、故障注入手（红队）、观察员/记录员、应急响应团队（蓝队）、业务代表（评估影响）；
- **通知与审批**：告知客服、运营、相关业务方；避开大促/发布窗口；
- **安全措施**：中止条件、一键回滚、专人盯监控与用户反馈指标；
- **记录**：时间线（注入时间、发现时间、止血时间、恢复时间）→ 计算 **MTTD、MTTR**；
- **复盘**：发现了什么缺陷、预案哪里不顺、监控哪里不灵，形成改进项并跟踪闭环。

## 五、预案与开关管理

### 1. 预案（Runbook）的要求

- **场景化**：按故障现象组织（“下单成功率下降”“数据库主库故障”“Redis 不可用”），而不是按系统；
- **可执行**：每一步是**具体命令/按钮/链接**，有判断条件与预期结果，新手也能照做；
- **包含**：触发条件、影响评估、止血步骤（降级/限流/切流/回滚）、验证方法、回退方法、升级路径与联系人；
- **定期演练 + 版本化**：预案与系统一起演进，失效预案要标记并更新；
- **自动化**：高频预案固化成脚本/平台一键操作（切流、扩容、开关）。

### 2. 降级与开关

| 项 | 做法 |
| --- | --- |
| **降级清单** | 事先梳理：哪些功能是核心、哪些可降级、降级后的体验与影响、开关位置、谁有权限 |
| **分级降级** | 一级（关闭推荐、评论等非核心）→ 二级（简化页面、关闭实时统计）→ 三级（只保留下单支付主链路） |
| **开关管理** | 配置中心/特性开关平台集中管理；有审计、权限、灰度；**开关默认值安全**；**定期演练开关是否真的生效**（见 [发布策略：特性开关](#/infra/release)） |
| **限流预设** | 为核心接口预设限流阈值与分级策略（见 [限流算法](#/cs/algo-engineering)），故障时可快速收紧 |
| **多活/切流** | 多机房/多可用区流量调度（DNS/GSLB/网关），**演练切流**，验证数据同步与会话 |

## 六、数据层面的稳定性

| 风险 | 对策与演练 |
| --- | --- |
| **数据库主库故障** | 自动故障转移（Orchestrator/MHA/Patroni/云），演练切换时间与应用重连；防脑裂 |
| **误删/误改** | 备份 + PITR、延迟从库、回收站/软删除；**定期做恢复演练并计时（验证 RTO/RPO）** |
| **缓存雪崩/击穿** | 过期随机、互斥/单飞、多级缓存、预热；注入“缓存全失效”验证数据库是否扛得住 |
| **消息积压** | 消费者扩容、降级非关键消费、死信与重放；注入“消费者停止 N 分钟”验证恢复速度 |
| **一致性** | 故障恢复后对账与补偿（见 [订单支付案例：对账](#/design/case-payment)） |

## 七、稳定性度量

| 指标 | 含义 |
| --- | --- |
| **可用性 / SLO 达成率** | 按错误预算管理（见 [SLO 与燃烧率](#/infra/obs-trace)） |
| **MTTD / MTTA / MTTR** | 发现 / 响应 / 恢复时间；演练与复盘的核心 KPI |
| **变更失败率、回滚率** | 发布质量（DORA 指标，见 [CI/CD](#/infra/cicd)） |
| **故障数与等级分布** | 各级故障的数量与趋势、重复故障比例（同类故障复发说明改进未落地） |
| **预案覆盖与演练覆盖** | 核心场景有预案的比例、过去 N 个月演练过的比例 |
| **改进项关闭率** | 复盘 Action Item 的按期完成率 |

## 八、常见反模式

| 反模式 | 问题 / 对策 |
| --- | --- |
| **只有预案文档，从未演练** | 预案过期或不可执行；定期演练并更新 |
| **演练只在预发，生产从不验证** | 预发缺少真实流量与依赖；逐步在生产小范围验证 |
| **无中止条件的“莽撞”注入** | 演练变事故；先定义稳态、爆炸半径、中止与回滚 |
| **只注入“实例宕机”这种简单故障** | 真实故障多是“变慢”“部分失败”“半死不活”；注入延迟、丢包、慢依赖更有价值 |
| **到处重试** | 重试风暴；重试预算、只在边缘层重试、熔断 |
| **没有超时或超时配置不一致** | 线程/连接被拖死；超时分层递减 |
| **降级开关从不演练** | 关键时刻失效；定期演练、监控开关状态 |
| **依赖“人肉救火”** | 沉淀预案、自动化、权限与流程；复盘改进 |
| **只关注基础设施指标** | 机器正常但业务已坏；以业务/SLO 指标为稳态 |
| **演练发现的问题没人改** | 改进项有负责人、期限、复测 |
| **把稳定性当成运维的事** | 开发在设计与编码阶段承担：超时、幂等、降级、可观测 |

## 面试追问

> [!QUESTION] 什么是混沌工程？一次实验怎么设计？
> 在受控条件下主动注入故障，验证系统在真实故障下仍满足稳态假设。先用业务指标定义稳态并提出假设，设计故障类型、范围、持续时间、中止条件和回滚手段，从小爆炸半径渐进注入并全程观测，触发中止条件立即停止，事后分析假设是否成立，修复缺陷并沉淀为自动化实验。

> [!QUESTION] 如何设计一个对下游依赖故障有韧性的服务？
> 每次远程调用设置分层递减的超时，用线程池或信号量做舱壁隔离，失败率或慢调用超阈值时熔断并半开探测，重试只针对幂等操作并带退避、抖动和重试预算，避免多层重试放大；准备降级兜底和限流保护，核心链路与非核心依赖隔离，再用故障注入验证这些配置真的生效。

> [!QUESTION] 重试为什么可能导致故障扩大？怎么避免？
> 多层调用每层都重试会乘法放大，如三层各重试三次下游收到二十七倍请求，在下游最脆弱时压垮它形成重试风暴。应只在最靠近用户的一层重试，其他层快速失败，设置重试预算与指数退避加抖动，配合熔断和限流，并保证被重试的操作幂等。

> [!QUESTION] GameDay 怎么组织？
> 明确演练目标和成功标准，设置总指挥、故障注入手、观察记录员、应急响应团队和业务代表，提前通知相关方并避开大促，定义中止条件和一键回滚；记录注入、发现、止血、恢复的时间线以计算 MTTD 和 MTTR，演练后复盘预案、监控和协作的缺口并形成可跟踪的改进项。

> [!QUESTION] 稳定性体系包括哪些方面？
> 预防包括冗余架构、容量、变更灰度与回滚、依赖隔离；发现包括监控告警和 SLO；止血包括限流、熔断、降级、切流和回滚预案；恢复与学习包括数据修复、无责复盘和改进闭环，并用混沌演练和压测持续验证，以 MTTD、MTTR、变更失败率等指标度量。

> [!QUESTION] 降级预案怎么做才有效？
> 事先梳理核心与非核心功能，定义分级降级清单、对应开关、影响与权限；开关集中管理并有审计，默认值安全；预案按故障现象组织，每一步可执行；定期演练验证开关真的生效、降级后核心链路容量确实提升，并随系统演进更新。
