# 高可用架构设计：可用性计算、故障域与容灾

> [!ABSTRACT] 核心要点
> - **高可用不是“用了集群”，而是“**在预期的故障下依然满足可用性目标**”**。先把目标量化（**SLO：几个 9**），再用**可用性计算**倒推架构：**串联依赖会相乘降低可用性，并联冗余才提高可用性**。一个有 10 个 99.9% 依赖的请求，理论可用性只有约 99.0%。
> - **故障域（Failure Domain）** 是设计的核心单位：进程、机器、机架、可用区、地域、供应商、变更批次、**配置/数据/代码本身**。冗余要**跨故障域**才有意义（同一机架的 3 个副本抵不过一次机架断电）；同时要通过**隔离**把故障的**爆炸半径**限制在最小范围。
> - **无状态服务**靠多实例 + 负载均衡 + 健康检查 + 快速剔除；**有状态服务**（数据库、缓存、消息队列）靠**复制 + 自动故障转移 + 数据不丢策略**，难度高一个量级，见 [复制与一致性](#/distributed/replication)。
> - **多数线上事故来自“变更”**（发布、配置、数据库变更、依赖升级），其次才是硬件故障。所以高可用的另一半是**变更管理：灰度、自动回滚、变更窗口、可观测**，见 [发布策略](#/infra/release)。
> - **容灾**用 **RTO（恢复时间目标）与 RPO（数据丢失目标）** 分级：同城双活/异地冷备/异地多活成本与能力不同；**没有演练过的容灾等于没有容灾**。
> - 体系化的**降级与限流**：核心链路保护、非核心可舍弃、依赖有超时与熔断、过载时快速拒绝而不是崩溃，见 [限流、熔断与降级](#/distributed/governance)、[故障模型、故障检测与脑裂](#/distributed/fault)。

## 可用性：度量与计算

### 几个 9 意味着什么

| 可用性 | 年停机时间 | 月停机时间 | 备注 |
| --- | --- | --- | --- |
| 99% | 约 3.65 天 | 约 7.3 小时 | 一般内部系统 |
| 99.9% | 约 8.76 小时 | 约 43.8 分钟 | 多数业务系统的常见目标 |
| 99.95% | 约 4.38 小时 | 约 21.9 分钟 | |
| 99.99% | 约 52.6 分钟 | 约 4.38 分钟 | 核心交易系统；**人工介入基本来不及，必须自动化恢复** |
| 99.999% | 约 5.26 分钟 | 约 26 秒 | 极高成本，通常只对局部关键组件追求 |

> [!NOTE] 可用性定义要精确
> 先定义“**什么算不可用**”：全站不可访问？核心接口错误率 > 1%？P99 延迟 > 阈值？**以用户可感知的成功率与延迟定义（基于请求/时间窗口）**，而不是以“进程是否存活”。不同定义下的 99.9% 差别很大。

计算示例：核心下单链路依赖网关、订单服务、库存服务、数据库、缓存、消息队列共 6 个组件，各为 99.9% 时，串联可用性 ≈ 0.999⁶ ≈ **99.4%**（每月约 4.3 小时不可用）。要提升到 99.99% 必须：**减少链路上的硬依赖**（缓存/消息/非关键服务改为可降级）、**对每个硬依赖做跨故障域冗余并实现可靠自动切换**。

### SLI、SLO、SLA 与错误预算

| 概念 | 含义 | 例子 |
| --- | --- | --- |
| **SLI**（指标） | 衡量服务质量的**可量化指标** | 成功请求占比、P99 延迟、数据新鲜度 |
| **SLO**（目标） | 对 SLI 的**内部目标** | “30 天窗口内下单接口成功率 ≥ 99.95%” |
| **SLA**（协议） | 对客户的**承诺与赔偿条款**（通常比 SLO 宽松） | 低于 99.9% 赔付 |
| **错误预算** | `1 − SLO` 允许的失败量（如 99.95% → 每 30 天约 21.6 分钟） | **预算内可以发布新功能与冒险；预算耗尽则冻结变更、优先稳定性** |

用法：把可用性目标变成**工程决策机制**——预算消耗过快时放慢发布节奏、优先修复可靠性问题；用**多窗口燃烧速率告警**（短窗口发现快速恶化，长窗口发现缓慢侵蚀）而不是“CPU 高了就告警”，见 [指标监控](#/infra/obs-metrics)。

## 故障域与冗余

### 故障域层级

| 层级 | 典型故障 | 冗余手段 |
| --- | --- | --- |
| **进程/实例** | 崩溃、OOM、死锁 | 多实例、自动重启、健康检查摘除 |
| **机器/虚拟机** | 硬件、宿主机故障 | 实例分散到不同机器（反亲和） |
| **机架/电源/交换机** | 机架断电、交换机故障 | 跨机架（机架感知放置） |
| **可用区（AZ）** | 机房级故障、网络隔离 | 跨可用区部署（同城多活/双活） |
| **地域（Region）** | 城市级灾难、骨干网故障 | 异地容灾/多活，见 [异地多活与单元化架构](#/design/arch-multi-active) |
| **云厂商/平台** | 控制面故障、厂商事故 | 多云（成本极高，通常只对关键业务） |
| **依赖/第三方** | 支付渠道、短信、地图不可用 | 多供应商路由、降级 |
| **变更批次** | 一次发布影响全量 | 灰度、分批、自动回滚 |
| **数据/配置** | 脏数据、错误配置全局生效 | 配置灰度与校验、数据备份与校验 |
| **代码/版本** | 同一个 bug 在所有副本 | 灰度发布、特性开关、版本多样性（极端） |

### 冗余设计原则

1. **跨故障域**：副本、实例按反亲和策略分布在不同机架/可用区；
2. **N+1 / N+2 容量冗余**：假设一个故障域整体失效，**剩余容量仍能承载峰值**（如 3 个可用区各按 50% 水位运行，丢一个后剩余 2 个运行在 75%）；
3. **冗余要“热”**：备用资源要持续承载流量或定期演练切换（**冷备在真正故障时往往起不来**）；
4. **避免共享隐式依赖**：不同冗余副本是否共享同一个配置中心、同一个注册中心、同一个 DNS、同一个证书、同一个运维账号？共享依赖本身成为单点；
5. **自动化切换**：靠人工判断与操作的恢复时间以分钟/小时计，达不到 99.99%；
6. **优雅降级优先于完全冗余**：有时“降级运行”比“双倍成本冗余”更划算；
7. **限制爆炸半径**：单元化、分片、多租户隔离，使一次故障只影响一部分用户，见 [故障模型、故障检测与脑裂](#/distributed/fault)。

### 无状态服务

- **多实例 + 负载均衡 + 健康检查**；实例**不保存本地会话/状态**（会话外置 Redis/令牌）；
- **优雅上下线**：摘流、等待在途、再停，见 [微服务可观测](#/spring/cloud-observability)；
- **弹性伸缩**：基于负载/队列长度自动扩缩，**预留缓冲**（扩容需要时间，冷启动与预热）；
- **依赖保护**：超时、熔断、舱壁，见 [熔断限流实战](#/spring/cloud-resilience)。

### 有状态服务

| 组件 | 高可用要点 |
| --- | --- |
| **数据库** | 主从复制 + 自动故障转移（注意数据丢失窗口与脑裂防护）；半同步/多数派同步保证不丢；备份 + PITR 恢复；容量与连接池保护；见 [复制与一致性](#/distributed/replication) |
| **缓存** | 主从 + 哨兵/Cluster；**缓存宕机不应拖垮数据库**（回源限流、降级、熔断）；见 [Redis Cluster 生产运维](#/redis/cluster-ops) |
| **消息队列** | 多副本跨 AZ、同步刷盘与 ISR 配置、生产端本地兜底；见 [Kafka 副本与可靠性](#/mw/kafka-reliability) |
| **注册/配置中心** | 多节点跨 AZ；客户端本地缓存兜底；**不能因控制面故障而影响数据面**，见 [Nacos 与服务注册发现、配置中心](#/mw/registry) |
| **协调服务** | 奇数节点跨 AZ，见 [分布式协调](#/mw/coordination) |
| **搜索** | 副本与跨 AZ、快照备份；非主存储，可重建 |

## 容灾：RTO、RPO 与等级

| 概念 | 含义 |
| --- | --- |
| **RTO（Recovery Time Objective）** | 故障后**多久恢复服务**（允许的最长停机时间） |
| **RPO（Recovery Point Objective）** | 故障后**允许丢失多少数据**（以时间衡量：最近 N 秒的数据） |

| 容灾等级 | 做法 | RTO | RPO | 成本 |
| --- | --- | --- | --- | --- |
| **备份恢复** | 定期备份到异地，故障时重建 | 小时~天 | 小时~天（备份间隔） | 最低 |
| **冷备/温备** | 异地有基础设施，数据定期/准实时同步，故障时启动切换 | 小时 | 分钟~小时 | 低~中 |
| **热备（主备）** | 异地备集群持续同步数据，故障时切流量 | 分钟 | 秒~分钟（异步复制） | 中 |
| **同城双活** | 同城多个可用区同时对外服务，数据同步复制 | 秒~分钟（自动） | 接近 0（同步） | 较高 |
| **异地多活** | 多个地域同时承载流量，单元化 + 数据同步 | 秒级（流量切换） | 取决于同步策略，业务设计容忍 | 最高、复杂度最高，见 [异地多活与单元化架构](#/design/arch-multi-active) |

选择依据：**业务价值与停机损失**（每小时损失多少）、合规要求、可接受成本。**不要为所有系统追求最高等级**，按业务分级（核心交易 vs 内部工具）。

容灾要点：

- **数据**：备份必须**可恢复**（定期恢复演练）、**异地**、**加密与不可篡改**（防勒索）；异步复制要明确 RPO；
- **流量切换**：DNS/全局负载均衡/网关路由；DNS TTL 影响切换速度；
- **依赖整体迁移**：不仅应用与数据库，还有配置、证书、密钥、第三方白名单、监控；
- **回切（Failback）**：恢复后如何把流量和数据切回，常被忽略；
- **演练**：至少每年一次真实切换演练，记录实际 RTO/RPO，发现文档与现实的差距，见 [稳定性工程：混沌实验与容灾演练](#/design/eng-chaos)。

## 降级、限流与过载保护体系

| 层次 | 手段 |
| --- | --- |
| **入口** | 限流（总量/用户/接口）、**优先级与准入**（保核心用户/接口）、排队与拒绝、验证码/风控挡机器流量 |
| **服务内** | 线程池/连接池隔离、超时、熔断、**舱壁**、有界队列、快速失败 |
| **依赖** | 非核心依赖降级（推荐、评论、积分关闭）、缓存兜底、静态页/CDN 兜底、默认值 |
| **数据层** | 读写分离、热点保护、慢查询熔断、连接池上限、**数据库自保护（限流/SQL 黑名单）** |
| **开关** | 降级开关、功能开关（配置中心动态下发，演练过）、大促前预置“预案开关” |
| **优先级** | 事先定义**核心链路（下单/支付）与非核心**，过载时先牺牲谁；形成**降级预案手册**与自动化触发条件 |

关键：降级与限流**必须预先设计、预先演练**，故障发生时才想“要不要降级”为时已晚；开关要能**秒级生效且有审计**。

## 容量与弹性

- **容量冗余**：按峰值 + 故障域丢失 + 增长预留（如 N+1，水位不超过 60%~70%）；
- **压测与容量模型**：用压测确定单实例/单分片拐点，建立容量公式，见 [压测与容量规划](#/design/eng-loadtest)；
- **弹性**：自动扩缩需要考虑**扩容生效时间**（启动、预热、注册、依赖连接建立），突发流量用**限流 + 预留缓冲**顶住，不要指望扩容瞬间生效；
- **容量也是可用性**：没有容量，冗余就是摆设（一个 AZ 故障后，另两个 AZ 过载一起崩溃）；
- **依赖容量联动**：上游扩容会把压力传导到下游（数据库、缓存），要整体评估；
- **预热与冷启动**：缓存预热、连接池预热、JIT 预热，避免扩容后的“冷实例”拖慢整体。

## 可观测与应急

- **监控体系**：黄金信号（延迟、流量、错误、饱和度）+ SLO 燃烧速率告警 + 依赖健康 + 业务指标；
- **告警质量**：分级、路由到负责人、附 Runbook 与仪表盘；减少噪声，避免告警疲劳；
- **应急响应**：故障分级（SEV1~4）、值班与升级机制、指挥官角色、**先止血后定位**（回滚、切流量、降级、扩容）、沟通模板；
- **复盘**：无责复盘，找系统性原因与改进项并跟踪闭环，见 [事故响应与复盘](#/design/eng-postmortem)；
- **预案与演练**：常见故障（数据库主库故障、缓存雪崩、机房断网、依赖不可用、大流量冲击）都有预案并演练。

## 可用性评审清单

| 维度 | 检查项 |
| --- | --- |
| **目标** | 是否有量化的 SLO 与定义？是否有错误预算与燃烧速率告警？ |
| **单点** | 是否存在单点（单实例、单可用区、单个共享依赖、单个配置/证书/账号）？ |
| **故障域** | 冗余是否跨机架/可用区？共享依赖是否也有冗余？ |
| **依赖** | 硬依赖数量？非核心依赖是否可降级？超时/熔断/舱壁是否配置并验证？ |
| **状态** | 有状态组件是否有自动故障转移、fencing、备份与恢复演练？数据丢失窗口（RPO）是否明确？ |
| **容量** | 一个故障域丢失后剩余容量是否足够？是否压测验证？有无自动伸缩与限流兜底？ |
| **变更** | 是否灰度、自动回滚、变更窗口？配置/数据库变更是否兼容可回滚？ |
| **降级** | 降级预案、开关是否存在并演练？核心链路是否明确？ |
| **观测** | 能否在 5 分钟内发现、15 分钟内定位？告警是否有 Runbook？ |
| **容灾** | RTO/RPO 是否明确并演练过？回切方案是否有？ |
| **安全与外部依赖** | 证书/密钥过期监控、第三方依赖的多供应商/降级？ |

## 常见架构缺陷

| 缺陷 | 后果 | 改进 |
| --- | --- | --- |
| **“集群”但全部在同一机架/可用区** | 一次故障全灭 | 跨故障域分布，反亲和 |
| **N 个副本但容量只够 N** | 丢一个就过载级联 | N+1 容量，水位上限 |
| **主从切换从没演练** | 真故障时切不了/数据丢 | 定期演练，自动化 |
| **缓存挂了数据库被打穿** | 雪崩 | 回源限流、降级、熔断、多级缓存 |
| **同步调用链过长、硬依赖多** | 可用性乘积低 | 缩短链路、异步化、降级非核心依赖 |
| **没有超时/无限重试** | 重试风暴、线程耗尽 | 超时预算、退避、熔断 |
| **健康检查只看进程存活** | 灰色故障发现不了 | 业务级探针、调用方观测 |
| **配置/证书单点、过期无监控** | 一个过期全站挂 | 过期监控与自动续期，配置灰度 |
| **备份从未恢复过** | 需要时发现不可用 | 恢复演练与校验 |
| **一次变更全量发布** | 爆炸半径 100% | 灰度、分批、自动回滚 |
| **注册/配置中心故障导致业务不可用** | 控制面拖垮数据面 | 客户端缓存、本地快照、降级 |
| **只有 SLA 没有 SLO 与错误预算** | 稳定性与发布速度无法权衡 | 引入 SLO 与错误预算机制 |

## 面试追问

> [!QUESTION] 如何计算系统的可用性？怎么提高？
> 串联依赖的可用性是各部分的乘积，依赖越多越低，例如六个 99.9% 的组件串联约 99.4%；并联冗余的不可用概率相乘，两个 99.9% 副本并联约 99.9999%。提高办法是减少硬依赖并把非核心依赖做成可降级，对关键组件做跨故障域冗余并保证自动可靠切换，同时留足容量并控制变更风险。

> [!QUESTION] SLO、SLA 和错误预算是什么？怎么使用？
> SLI 是可量化指标，SLO 是内部目标如 30 天成功率 99.95%，SLA 是对客户的承诺与赔偿，通常比 SLO 宽松。错误预算是 1 减 SLO 允许的失败量，预算内可以发布冒险，预算耗尽就冻结变更优先稳定性，并用多窗口燃烧速率告警。

> [!QUESTION] 为什么说冗余不等于高可用？
> 副本若在同一机架或同一可用区、共享同一配置中心或同一版本 bug，会一起失败，并联公式不成立；故障切换本身可能失败或耗时；容量不足时一个副本故障会让剩余副本过载级联；冷备往往到真正故障时起不来。所以要跨故障域、保证 N+1 容量、自动切换并定期演练。

> [!QUESTION] RTO 和 RPO 是什么？怎么选容灾方案？
> RTO 是故障后允许的最长恢复时间，RPO 是允许丢失的数据量，以时间衡量。备份恢复成本最低但 RTO、RPO 以小时到天计，热备分钟级，同城双活秒到分钟且数据近零丢失，异地多活最复杂最贵。按业务停机损失与合规要求分级选择，并定期做真实切换演练验证。

> [!QUESTION] 为什么说变更是最大的可用性风险？怎么控制？
> 多数重大故障由发布、配置、数据库变更、依赖升级引起。控制办法是变更评审与风险分级、预发验证、灰度分批发布并按版本对比指标、异常自动回滚、变更窗口与冻结、配置和数据库变更保持兼容可回滚，并把变更事件与告警联动用于归因。

> [!QUESTION] 缓存集群挂了怎么保证系统不被拖垮？
> 缓存故障时请求会涌向数据库，要有回源限流与熔断，对热点用互斥或逻辑过期合并回源，降级返回缓存兜底或默认值、关闭非核心功能，多级缓存和本地缓存兜底，数据库有连接池与限流保护，并预先演练缓存不可用的预案。
