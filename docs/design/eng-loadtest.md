# 压测与容量规划

> [!ABSTRACT] 核心要点
> - **压测的目的不是“跑出一个 QPS 数字”**，而是回答三个问题：**系统能承载多少（容量）**、**在什么地方先垮（瓶颈）**、**超载时怎么表现（降级是否有效）**。没有明确问题的压测只会产出无用数字。
> - **容量 = 压测得出的“单位资源可承载量” × 资源规模 ÷ 安全水位**：用**可接受延迟（SLO）下的最大吞吐**而不是“CPU 打满”当容量；生产水位通常控制在 **50%~70%**，并预留 **N+1/N+2 冗余**与**峰值系数**。
> - **Little 定律** `并发数 L = 吞吐 λ × 平均延迟 W` 是估算线程池、连接池、并发度的基础；**通用扩展性定律（USL）**解释了为什么**加机器不一定线性提升**（争用 + 一致性开销）。
> - **测量陷阱比工具更重要**：**协调遗漏（Coordinated Omission）**、压测机自身成为瓶颈、数据被缓存或数据量不真实、思考时间缺失、连接复用与生产不一致、只看平均值——都会让结论失真。
> - **全链路压测**在生产环境用**流量染色 + 影子库/影子表**做真实容量验证，是大促保障的核心手段，但要严格做**数据隔离与熔断开关**。
> - 容量规划是**持续闭环**：业务预测 → 压测/建模 → 扩容 → 监控 → 复盘，而不是上线前做一次。

## 一、先把问题问清楚

| 要回答的问题 | 对应的压测 |
| --- | --- |
| **单实例/单接口的性能基线是多少？** | **基准测试（Baseline）**：小并发、稳定环境，记录 P50/P99 与资源消耗，作为后续对比的参照 |
| **目标峰值（如 2 万 QPS）能不能扛住？** | **负载测试（Load）**：按预期负载持续运行，验证指标满足 SLO |
| **极限在哪里？先垮的是什么？** | **压力测试（Stress）**：逐步加压直到拐点/崩溃，找到瓶颈与失效方式 |
| **长时间运行会不会泄漏/退化？** | **稳定性/浸泡测试（Soak）**：中等负载连续跑数小时~数天，观察内存、连接、句柄、GC、磁盘 |
| **突发流量（秒杀、热点）能否承受？** | **尖峰测试（Spike）**：短时间内流量剧增后回落，验证弹性与恢复 |
| **改动（新版本、参数、硬件）是否引起性能回退？** | **回归性能测试**：固定场景，在 CI/发布前对比基线 |
| **故障时能否保持可用？** | 与 [故障演练](#/design/eng-chaos) 结合，在压力下注入故障 |

压测前先写清：**目标场景（接口组合与比例）、目标指标（吞吐、P99、错误率）、通过标准、环境与数据**。

## 二、理论工具：Little 定律与扩展性

### 1. Little 定律

**`L = λ × W`**：系统中的平均并发数 = 到达率（吞吐）× 平均停留时间（延迟）。

| 应用 | 例子 |
| --- | --- |
| **估算并发/线程数** | 目标 2000 QPS，平均耗时 100ms → 并发 = 2000 × 0.1 = **200**；线程池至少 200 个并发处理能力（IO 型），或 Tomcat 最大线程 ≥ 峰值并发 × 安全系数 |
| **估算连接池大小** | 服务 1000 QPS，访问数据库平均 5ms → 数据库并发 = 1000 × 0.005 = **5**；连接池 10~20 足够，**盲目调大反而拖垮数据库**（见 [线程池调优](#/java/concurrency/pool)） |
| **延迟变高时并发会堆积** | 延迟翻倍则同吞吐下所需并发翻倍，线程池/连接池很快被占满——这是**雪崩的放大器**（见 [限流、熔断与降级](#/distributed/governance)） |
| **队列长度** | 排队中的请求数 = 吞吐 × 排队时间；队列无限长 = 延迟无限长 |

### 3. 通用扩展性定律（USL）

加机器后吞吐并不线性增长：

- **争用（Contention，σ）**：共享资源串行化（锁、单点、数据库行、热点 Key），对应 **Amdahl 定律**——串行部分决定上限；
- **一致性开销（Coherency，κ）**：节点间需要协调、同步（缓存一致、分布式锁、跨分片事务），开销随节点数**二次**增长，甚至**越加越慢**；
- **意义**：发现“加到某个规模后吞吐不升反降”，先找**争用与协调点**（热点 Key、数据库单点、全局锁、同步调用链），而不是继续加机器；扩展要靠**去状态、分片、异步、减少跨节点协调**。

## 三、压测方法与工具

### 1. 工具选择

| 工具 | 特点 | 适合 |
| --- | --- | --- |
| **JMeter** | 图形化/脚本，协议多，生态广；JVM 进程较重，高并发需分布式压测机 | 通用 HTTP/JDBC/MQ 压测、团队入门 |
| **wrk / wrk2 / hey / ab** | 极轻量命令行；**wrk2 修正了协调遗漏**，可固定速率压测 | 单接口快速基准、高吞吐 |
| **k6** | JS 脚本、代码化、CI 友好、指标输出清晰 | 现代 API 压测、持续性能回归 |
| **Gatling** | Scala/Java DSL，高效（异步），报告好 | 复杂场景、Java 团队 |
| **Locust** | Python 脚本，分布式简单 | 复杂用户行为模拟 |
| **ghz** | gRPC 压测 | gRPC 服务 |
| 自研/公司平台、云厂商 PTS | 流量录制回放、全链路、分布式压测机 | 大规模/全链路压测 |

### 2. 负载模型：开环 vs 闭环

| | **闭环（Closed）**：固定并发用户数，一个请求完成后再发下一个 | **开环（Open）**：按固定到达率发请求，不等响应 |
| --- | --- | --- |
| 行为 | 系统变慢 → 压测机发得也慢（**被动降速，掩盖问题**） | 系统变慢 → 请求继续按速率到达，**堆积、暴露排队与过载** |
| 真实性 | 像有限用户的内部系统 | **更贴近互联网流量**（用户不会因为你慢就少来） |
| 工具 | JMeter 线程组（默认）、ab | **wrk2、k6 的 constant-arrival-rate**、Gatling 的 `constantUsersPerSec` |

**结论**：评估容量与过载行为，优先用**开环（固定到达率）**压测。

### 3. 场景设计

- **按真实流量构成**：接口比例（搜索 70%、详情 20%、下单 5% …）、读写比、热点分布（Zipf：少数商品占大部分请求），而不是只压一个接口；
- **数据**：参数化大量不同的用户/商品，**避免所有请求命中同一个缓存 key**；数据量与分布要接近生产（索引大小、表行数影响查询计划）；
- **思考时间**：真实用户请求间有间隔，模拟用户行为的场景要加；
- **连接行为**：长连接/连接池与生产一致；是否启用 TLS、HTTP/2、Keep-Alive；
- **预热**：JIT、连接池、缓存要预热，**测量窗口取稳定期**，丢弃启动阶段；
- **逐步加压（Ramp-up）**：阶梯式（如每 3 分钟提升 20% 流量），每个阶梯观察稳态，找到拐点；
- **持续时间**：每个阶梯足够长（至少几分钟）以暴露 GC、连接池、队列堆积。

### 4. 示例

```bash
# wrk2：固定速率 5000 req/s，持续 5 分钟，64 连接，16 线程，输出延迟分布（已修正协调遗漏）
wrk2 -t16 -c64 -d300s -R5000 --latency -s post_order.lua https://staging.example.com/api/orders

# k6：开环（constant-arrival-rate）+ 阶梯
cat > load.js <<'EOF'
import http from 'k6/http'; import { check } from 'k6';
export const options = {
  scenarios: { ramp: { executor: 'ramping-arrival-rate', startRate: 500, timeUnit: '1s', preAllocatedVUs: 500, maxVUs: 5000,
    stages: [ { target: 2000, duration: '3m' }, { target: 4000, duration: '3m' }, { target: 6000, duration: '3m' } ] } },
  thresholds: { http_req_failed: ['rate<0.01'], http_req_duration: ['p(99)<300'] },     // 不满足阈值则判失败（可接入 CI）
};
export default function () { const r = http.get('https://staging.example.com/api/products/' + (__ITER % 100000)); check(r, { 'status 200': (x) => x.status === 200 }); }
EOF
k6 run load.js
```

## 四、测量陷阱（决定结论是否可信）

| 陷阱 | 说明 | 对策 |
| --- | --- | --- |
| **协调遗漏（Coordinated Omission）** | 压测工具在响应慢时**停止发送后续请求**，只统计“实际发出”的请求，**低估长尾延迟**（本应在慢的那段时间发出的请求没被计入） | 开环工具（wrk2/k6 arrival-rate）；或记录**预期发送时间**校正（HdrHistogram 的纠正功能） |
| **压测机成为瓶颈** | 压测机 CPU/网卡/端口/文件描述符打满，测到的是压测机极限 | 监控压测机资源；分布式压测；调大 `ulimit -n`、临时端口范围（见 [TCP 深入：调优](#/cs/net-tcp)） |
| **只看平均值** | 平均延迟掩盖长尾 | 看 **P50/P90/P99/P99.9** 与延迟分布直方图 |
| **缓存与数据不真实** | 所有请求命中缓存 → 虚高；数据量小 → 查询计划与线上不同 | 参数化+热点分布；数据量级对齐；分别测“缓存命中/未命中/击穿” |
| **环境差异** | 压测环境硬件、配置、依赖（Mock 下游）与生产不同 | 容量结论按比例折算要谨慎；关键结论在**生产同构环境或生产**验证；Mock 下游要带上真实延迟分布 |
| **下游被 Mock 掉** | 忽略了下游的限流与延迟，结论偏乐观 | 联调下游或模拟其延迟与限流 |
| **预热不足/测量窗口选错** | JIT/缓存冷启动拖低成绩，或只测了尖峰一小段 | 预热 + 稳态窗口 + 足够时长 |
| **压测影响线上** | 在共享环境/生产压测把别人拖垮 | 隔离环境或影子流量；限速、熔断、通知相关方 |
| **一次测量当结论** | 偶然波动 | 重复多次，记录方差；固定变量，每次只改一个因素 |
| **单位混淆** | QPS（请求）与 TPS（事务）、并发用户与并发连接混用 | 定义清楚指标含义 |

## 五、瓶颈定位

### 1. 方法：USE + 自上而下

压测中同时观测**四层**，按**饱和度**找最先撞墙的资源（USE：利用率 Utilization、饱和度 Saturation、错误 Errors，见 [指标监控](#/infra/obs-metrics)）：

| 层 | 看什么 | 常见瓶颈 |
| --- | --- | --- |
| **压测机/网络** | 压测机 CPU、带宽、连接数、丢包重传 | 压测机本身、带宽、LB 连接上限 |
| **应用层** | QPS、P99、错误率、线程池活跃/队列、连接池等待、GC 停顿、锁竞争 | 线程池/连接池耗尽、同步锁、GC、慢序列化、日志同步写 |
| **中间件/存储** | DB 连接/慢 SQL/锁等待/IOPS，Redis 延迟与带宽，MQ 积压/磁盘，ES 慢查询 | 数据库热点行/索引缺失、Redis 大 Key/单线程饱和、磁盘 IO |
| **基础设施** | CPU（含 `sys`/`steal`/throttling）、内存/swap、磁盘 await、网络、容器限流 | 容器 CPU 限流（见 [进程与调度](#/cs/os-process)）、内存换页 |

### 2. 定位流程

1. 找到拐点：吞吐不再增长、P99 突增的那个阶梯；
2. 看**哪个资源首先饱和**（CPU 100%？连接池 `pending` > 0？磁盘队列长？某分片热点？）；
3. 用**火焰图/Profile**（async-profiler、Arthas）看应用 CPU 去哪了；看**线程栈**（`jstack`）确认是在等锁/等 IO/等下游；
4. 用**链路追踪**找慢 span（见 [链路追踪](#/infra/obs-trace)）；
5. 修复瓶颈 → **重新压测** → 找下一个瓶颈（**瓶颈会转移**），直到达到目标或成本不划算。

### 3. 常见瓶颈与对策

| 现象 | 常见原因 | 对策 |
| --- | --- | --- |
| CPU 高 | 序列化/反射、日志、正则、加解密、GC | Profile；缓存；异步日志；对象池/减少分配；GC 调优 |
| CPU 低但延迟高 | 等锁/等 IO/等下游/线程池满/连接池满 | 线程栈分析；调连接池与超时；异步化；下游扩容或限流 |
| 吞吐在某值不再上升且各资源不满 | 单点串行（热点 Key/行锁/全局锁/单线程） | 分片、拆 Key、读写分离、去锁（见 USL） |
| P99 周期性毛刺 | GC 停顿、定时任务、容器 CPU 限流、日志刷盘、连接重建 | GC 日志；错开任务；调 limit；批量异步 |
| 压测后期变慢 | 内存泄漏、连接泄漏、日志/磁盘撑满、缓存淘汰 | 浸泡测试；堆 dump；监控句柄/磁盘 |
| 数据库首先垮 | 慢 SQL、缺索引、连接数、热点行、主从延迟 | 优化 SQL/索引、缓存、分库分表、读写分离（见 [SQL 调优](#/mysql/optimize)） |

### 2. 关键参数

| 参数 | 说明 |
| --- | --- |
| **峰值系数** | 峰值/平均流量比：日常 2~3 倍，大促/秒杀数倍到数十倍；从历史监控取峰值而不是平均 |
| **增长预期** | 业务增长（半年/一年）+ 活动预估；留出买量/扩容的提前期（云上弹性可缩短，物理机需提前数周） |
| **安全水位** | 生产常控制在 50%~70%：留给突发、发布（滚动更新少一批实例）、故障转移、GC 与不可预见波动 |
| **冗余** | N+1（挂一台不影响）、可用区冗余、机房容灾（可能要 2 倍）；成本与可用性的权衡 |
| **依赖容量** | **木桶原理**：整体容量取决于最小的那块——数据库连接/IOPS、Redis 单分片、MQ 分区数、下游的限流；上游扩容必须同步确认下游 |
| **线性度折损** | 实例增加后吞吐不是严格线性（USL），按压测的多节点数据校正，不要简单外推 |

### 3. 资源之外的容量

- **存储容量**：数据增长曲线（日增量 × 保留期 × 副本 × 索引放大）、磁盘水位告警（70%/85%）；归档与分级存储；
- **连接/句柄容量**：数据库最大连接数、Redis 连接、Nginx/网关连接、文件描述符；
- **带宽与跨可用区流量**：高流量服务的带宽与专线；
- **配额与限流**：云厂商 API/资源配额、第三方接口调用额度；
- **人力/成本容量**：扩容预算与审批周期。

## 七、全链路压测

**问题**：单系统压测无法覆盖真实的多系统耦合（共享数据库、缓存、MQ、网关、第三方），大促前需要在**生产环境**用真实规模验证整条链路。

### 1. 核心要素

| 要素 | 做法 |
| --- | --- |
| **流量染色（标记压测流量）** | 压测请求携带标记（Header/Baggage，如 `x-stress-test: true`），通过链路上下文**全链路透传**（HTTP/RPC/MQ），见 [链路追踪：上下文传播](#/infra/obs-trace) |
| **数据隔离（影子库/影子表）** | 压测流量识别后，**写入路由到影子库/影子表**（或影子 Key 前缀、影子 Topic），**不污染真实数据**；读取按需访问真实只读数据（用户、商品）或影子副本 |
| **中间件改造** | 数据源路由（ShardingSphere 影子库）、Redis Key 前缀、MQ 影子 Topic/打标、ES 影子索引；统一用中间件/Agent 层面实现，业务无感 |
| **外部依赖** | 第三方（支付、短信）使用**Mock/挡板**（返回模拟结果并带上真实延迟分布），避免真实扣款与发送 |
| **压测数据** | 用生产数据脱敏/合成：真实分布的用户、商品、订单；账号/卡等要预置 |
| **安全保护** | **一键熔断压测流量**；设置**压测流量占比上限**；监控线上真实用户的指标，**一旦影响立即停止**；在低峰期、有人值守 |
| **报告与复盘** | 各层瓶颈、扩容建议、降级验证结果，落成改进项 |

### 2. 风险与代价

- 数据污染、影响真实用户、统计报表被压测数据干扰（需要在统计口径中排除压测流量）；
- 改造和维护成本高（要求全链路组件支持染色透传）；
- 小团队可先做**预发/独立压测环境 + 核心链路单独压测 + 流量回放**（录制线上流量脱敏后回放，GoReplay 等），再逐步演进。

## 八、与降级、限流联动

压测**必须覆盖过载行为**：

- 超过容量后系统是**优雅拒绝**（限流返回 429/排队）还是**雪崩**（延迟暴涨、线程耗尽、级联）？
- 验证**限流阈值**是否合理：阈值应设在**拐点之前**，并用压测校准（见 [工程中的算法：限流](#/cs/algo-engineering)）；
- 验证**降级开关**：关闭非核心功能后，核心链路容量提升多少；
- 验证**熔断/超时/重试**配置：下游变慢时上游是否被拖死；
- 验证**扩容速度**：HPA/弹性伸缩从触发到生效的时间是否赶得上流量增速（冷启动、镜像拉取、预热）。

## 九、容量规划的持续闭环

1. **建立容量基线**：每个核心服务记录“单机容量、瓶颈资源、水位”，随版本变化更新；
2. **业务预测**：与产品/运营对齐活动与增长；大促前 4~8 周启动；
3. **压测验证**：核心链路阶梯压测、尖峰压测、故障下压测；
4. **扩容与优化**：按结论扩容、优化瓶颈、调整限流降级阈值；
5. **监控与告警**：容量水位（CPU/连接池/磁盘/队列）、预测趋势告警（见 [指标监控：predict_linear](#/infra/obs-metrics)）；
6. **大促保障**：预案、值班、实时看板、降级演练（见 [稳定性工程](#/design/eng-chaos)）；
7. **复盘**：预测 vs 实际、哪些环节超预期、成本是否合理，更新模型；
8. **成本优化**：错峰、弹性伸缩、Spot 实例、资源回收；容量不是越大越好。

## 十、压测报告应包含

| 项 | 内容 |
| --- | --- |
| 目标与范围 | 场景、接口比例、目标指标 |
| 环境与版本 | 硬件、配置、被测版本、依赖状态、数据规模 |
| 方法 | 工具、负载模型（开/闭环）、阶梯、时长、预热 |
| 结果 | 吞吐-延迟曲线、拐点、各阶梯的 P50/P99/错误率、资源利用率 |
| 瓶颈分析 | 先饱和的资源、证据（Profile/线程栈/链路） |
| 容量结论 | 单机容量、集群容量估算、水位建议 |
| 风险与建议 | 优化项、扩容建议、限流阈值、遗留问题 |
| 可复现性 | 脚本、数据、命令放进仓库，CI 可回归 |

## 十一、常见坑

| 坑 | 对策 |
| --- | --- |
| 以“CPU 打满时的 QPS”当容量 | 以满足 SLO 的最大吞吐为容量，并留水位 |
| 闭环压测掩盖慢请求 | 用开环（固定到达率）+ 修正协调遗漏的工具 |
| 压测机先垮 | 监控压测机；分布式；调系统参数 |
| 数据太少全命中缓存 | 参数化、热点分布、数据量对齐 |
| 连接池盲目调大 | 用 Little 定律估算；看下游承受力 |
| 只压单接口，忽略混合场景与依赖 | 按真实流量模型；覆盖依赖 |
| 压测完不优化、不复测 | 修复后重新压测，闭环 |
| 容量规划只算应用，忽略数据库/缓存/下游 | 木桶原理，依赖同步评估 |
| 大促前一次性压测，之后无人维护 | 持续基线与回归；性能纳入 CI |
| 全链路压测污染数据 | 染色透传 + 影子库 + 统计排除 + 熔断开关 |
| 扩容速度跟不上流量 | 预扩容、预热、弹性伸缩策略演练 |

## 面试追问

> [!QUESTION] 如何评估一个服务的容量？
> 先定义 SLO，如 P99 小于 200ms、错误率小于 1%，然后用阶梯式开环压测找到满足 SLO 的最大吞吐作为单机容量，而不是 CPU 打满；按真实流量模型和数据分布压测，观测应用、中间件、基础设施各层饱和度找瓶颈；再根据峰值预测、安全水位、冗余与依赖容量推算集群规模。

> [!QUESTION] Little 定律怎么用？线程池和连接池怎么估算？
> 并发数等于吞吐乘以平均延迟。目标 2000 QPS、平均耗时 100ms 则并发约 200，据此估算线程池；访问数据库平均 5ms、1000 QPS 则数据库并发约 5，连接池十几个就够，盲目调大只会拖垮数据库。延迟变高时同吞吐所需并发成比例增加，这是雪崩的放大器。

> [!QUESTION] 压测有哪些常见陷阱？什么是协调遗漏？
> 协调遗漏是压测工具在响应慢时停止发送后续请求，只统计实际发出的请求，从而低估长尾延迟，应使用开环固定到达率的工具或校正。其他陷阱包括压测机自身瓶颈、只看平均值、数据全命中缓存、环境和依赖与生产不一致、预热不足、结果未重复验证。

> [!QUESTION] 加机器为什么吞吐没有线性增长？
> 通用扩展性定律指出有争用和一致性两类开销：串行化的共享资源如锁、热点 Key、数据库单点限制上限，节点间协调开销随节点数增长甚至使吞吐下降。要找出争用和协调点，通过去状态、分片、异步和减少跨节点协调来扩展。

> [!QUESTION] 全链路压测怎么做到不影响线上数据？
> 给压测流量染色并全链路透传，中间件和数据源层识别后把写入路由到影子库、影子表、影子 Key 或影子 Topic，第三方依赖用挡板模拟，统计口径排除压测流量；设置流量占比上限和一键熔断，低峰期有人值守，一旦影响真实用户立即停止。

> [!QUESTION] 压测发现吞吐上不去但各项资源都不满，怎么办？
> 说明存在串行化争用点，如热点 Key、数据库行锁、全局锁、单线程组件或同步调用链。用线程栈和火焰图看线程是否在等锁或等下游，用链路追踪找慢 span，再通过分片、拆热点 Key、读写分离、去锁或异步化消除，然后重新压测找下一个瓶颈。
