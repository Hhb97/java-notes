# 技术方案与 ADR 写作

> [!ABSTRACT] 核心要点
> - **好的技术方案文档的价值是“让别人（和未来的你）能评审、能执行、能理解为什么这么做”**，不是展示技术细节的堆砌。结构上最重要的三块：**问题与目标（含非目标）**、**方案对比与取舍**、**风险与落地/回滚计划**。
> - **先写问题，再写方案**。“为什么要做”“做到什么程度算成功”“明确不做什么”，比“用了什么技术”更能避免方向性错误；没有量化目标的方案无法验收。
> - **至少给出 2 个备选方案并说明为何不选**：只有一个方案的文档是“通知”，不是“设计”。**取舍要显式**：成本、复杂度、风险、可逆性、对团队的影响。
> - **ADR（Architecture Decision Record）**用一页纸记录**一个重要决策及其背景和后果**，存放在代码仓库里，**随代码演进**；它回答“当时为什么这么选”——这是新人和未来维护者最缺的信息。
> - **评审是为了暴露风险，不是为了通过**：把方案提前发给评审人，会上聚焦关键分歧；评审意见要记录并闭环。
> - **可逆的决策快速做，不可逆的决策慢慢做**：对**单向门（难回头）**的决策（数据模型、对外接口、云厂商锁定）多投入论证，对**双向门**的决策先做再迭代。

## 一、什么时候需要写方案

| 情形 | 是否写 | 形式 |
| --- | --- | --- |
| 小改动（单模块、可轻松回滚、影响面小） | 不需要正式文档 | PR 描述 + 代码评审 |
| **新系统/新模块、跨团队/跨服务变更** | 需要 | 完整技术方案（本文模板） |
| **引入新技术/中间件、更换存储/消息队列** | 需要 | 方案 + **ADR**（记录选型决策） |
| **对外接口/数据模型/核心流程变更**（难回头） | 需要，且评审 | 方案 + 兼容与迁移计划 |
| **性能/稳定性重大治理** | 需要 | 方案 + 压测与验证计划 |
| **事故后的架构改进** | 需要 | 方案，关联复盘 Action Item（见 [事故响应与复盘](#/design/eng-postmortem)） |

经验：**“如果做错了代价很大，或别人需要配合，或将来有人要问为什么”——就写**。

### 2. 各章节写作要点

| 章节 | 要写什么 | 常见问题 |
| --- | --- | --- |
| **背景与问题** | 现状、**痛点（附数据）**、不解决的后果、谁受影响、已有尝试 | 直接跳到方案；痛点只有形容词没有数字 |
| **目标** | **可量化**：P99 < 100ms、迁移 0 停机、成本下降 30%、支持 5 万 QPS；验收标准 | 目标模糊（“更高性能”“更稳定”） |
| **非目标** | **明确不做**：本期不支持多租户、不改动老接口；防止范围蔓延 | 缺失 → 评审时无限扩范围 |
| **方案概览** | 一张总体架构图 + 一段话讲清核心思路；术语表 | 只有文字没有图；术语不统一 |
| **备选方案对比** | 每个备选：思路、优缺点、成本、风险、**为何不选**；用**决策矩阵**（见下） | 只给一个方案，或“稻草人”式备选 |
| **详细设计** | 模块职责与交互、**数据模型**（表/索引/生命周期）、**接口契约**（含错误码、幂等、版本）、**核心流程时序图**、**状态机**、**并发与一致性**（锁、事务、幂等、重试）、异常处理 | 只描述“正常路径”；缺少失败路径与边界 |
| **非功能设计** | **容量估算**（见 [压测与容量规划](#/design/eng-loadtest)）、性能预算、可用性与降级、安全与权限（见 [认证授权](#/security/auth)）、可观测（指标/日志/链路/告警，见 [指标监控](#/infra/obs-metrics)）、成本 | 全部“后续优化” |
| **风险与缓解** | 技术/人员/依赖/时间风险；每项有**概率、影响、对策、触发信号** | 写成“无明显风险” |
| **实施计划** | 阶段与里程碑、每阶段交付物与验收、负责人、依赖与关键路径、人力估算（给区间而非单点） | 只有一个“上线日期” |
| **发布/迁移/回滚** | 灰度策略、**兼容性**（接口/数据/缓存）、**数据迁移**（双写、校验、回退）、回滚触发条件与步骤（见 [发布策略](#/infra/release)） | 没有回滚方案；迁移“一把梭” |
| **测试与验证** | 单测/集成/契约测试、压测目标、故障注入（见 [稳定性工程](#/design/eng-chaos)）、验收清单 | 上线前才想测试 |
| **待决问题** | 当前还不确定的点、需要谁拍板 | 隐藏不确定性 |

### 3. 写作原则

1. **读者导向**：先想“谁会读、读完要做什么决定”；开头放**摘要（TL;DR）**：问题—方案—关键取舍—需要的决策；
2. **用图和表**：架构图、时序图、状态图、对比表、数据模型图，比大段文字清晰（本笔记里的 SVG 图解风格可参照）；
3. **数字说话**：容量、延迟、成本都给数量级与推导过程，**明确标注“假设”**；
4. **显式写出取舍和假设**：“我们假设写入 QPS 不超过 1 万，如果超过则……”；
5. **写失败路径**：超时、重试、幂等、数据不一致怎么处理，比“正常流程”更能体现设计质量；
6. **控制范围**：能分期就分期，**第一期要有可交付的最小价值**；
7. **版本与状态**：文档头部写明作者、评审人、状态（草稿/评审中/已批准/已实施/废弃）、日期；变更记录；
8. **保持更新**：实施中与方案偏离时更新文档，或补 ADR 记录变更原因。

## 三、取舍分析：怎么做出有说服力的选择

### 1. 方案对比的维度

| 维度 | 说明 |
| --- | --- |
| **满足需求的程度** | 功能、性能、可用性、一致性、扩展性对目标的覆盖 |
| **复杂度与可维护性** | 代码量、概念数量、运维组件、排障难度、学习曲线 |
| **成本** | 开发人天、基础设施成本、许可费用、长期运维成本 |
| **风险** | 技术成熟度、团队经验、社区与供应商风险、迁移风险 |
| **上线与回滚** | 能否灰度、能否回滚、对线上的影响 |
| **可演进性与锁定** | 未来需求变化的适应、被厂商/技术锁定的程度 |
| **对团队/组织的影响** | 技能、协作、依赖其他团队的程度 |

### 2. 加权决策矩阵（示例：选择消息队列）

| 维度（权重） | 方案 A：Kafka | 方案 B：RocketMQ | 方案 C：云托管 MQ |
| --- | --- | --- | --- |
| 吞吐与扩展（25%） | 5 | 4 | 4 |
| 事务消息/顺序消息/延迟消息（25%） | 3 | 5 | 4 |
| 团队熟悉度（20%） | 4 | 3 | 4 |
| 运维成本（20%） | 2 | 3 | 5 |
| 成本（10%） | 4 | 4 | 3 |
| **加权得分** | **3.60** | **3.85** | **4.10** |

注意：**矩阵不是为了“算出答案”，而是让分歧显式化**。权重本身就是争论点——如果结论反直觉，要检查权重与评分是否合理；矩阵只是辅助，**最终仍需对关键风险做判断和验证（PoC/压测）**。

### 3. 思考框架

- **可逆性（单向门 / 双向门）**：能轻松回头的决策（内部库选型、实现细节）快速决定；难回头的（数据模型、对外 API、核心中间件、云厂商）需要更严谨；
- **YAGNI 与“最后责任时刻”**：不为想象中的未来需求过度设计；**把决策推迟到不得不决定的时刻**，除非推迟的代价很高；
- **“无聊技术”优先**：选择团队熟悉、成熟稳定的技术，**把“创新额度”花在真正带来业务差异的地方**；
- **第一性原理 + 数据**：从需求和约束出发，用 PoC/压测验证关键假设（性能、兼容性、运维复杂度），而不是靠博客与口碑；
- **看总拥有成本（TCO）**：开发 + 运维 + 排障 + 招聘培训，而不只是许可费；
- **选择“可演进”的方案**：留好扩展点与迁移路径（接口抽象、数据双写、防腐层，见 [DDD 战略设计](#/design/ddd-strategic)）；
- **识别单点与不确定性**：对最大的不确定性先做**探针/原型（Spike）**，用最小代价降低风险。

## 四、ADR：架构决策记录

### 1. 是什么、为什么

**ADR** 是对**一个**重要架构决策的**简短、不可变**的记录：背景、决策、后果。它：

- 以**文本文件**放进**代码仓库**（`docs/adr/0007-use-kafka-for-event-bus.md`），与代码一起评审和版本化；
- 回答未来最常被问的问题：“**当时为什么没选 X？**”“**这个限制是有意的吗？**”；
- 避免“考古学”：人员流动后决策原因丢失，团队重复讨论或盲目“重构”掉有意的设计；
- **不修改历史**：决策变了就**新建一条 ADR 取代（Supersede）旧的**，旧的标记为“已被取代”。

### 2. 什么决策值得写 ADR

- 影响**结构、关键质量属性（性能/可用/安全）、依赖、接口、构建/部署**的决策；
- **难以逆转**或**代价高**的选择：数据库、消息中间件、通信协议、认证方案、多租户策略、服务拆分边界；
- 违背常规/看起来“奇怪”但有理由的设计；
- 团队内**有争议**并最终收敛的决定。

不值得：命名风格、小工具库选型、可轻易替换的实现细节。

### 3. ADR 模板（Michael Nygard 风格）

```markdown
# ADR-0007: 事件总线使用 Kafka

- 状态：已接受（Accepted）  <!-- 提议 / 已接受 / 已废弃 / 已被 ADR-0015 取代 -->
- 日期：2026-10-12
- 决策者：@alice @bob（评审：@carol）
- 相关：ADR-0003（微服务拆分边界）

## 背景（Context）
订单、库存、积分等服务之间需要异步解耦，当前通过同步 RPC 造成级联超时（事故 #2026-08）。预计峰值 3 万条/秒，需要消息可重放用于数据平台消费。团队已有 Kafka 运维经验，没有 RocketMQ 经验。约束：本季度内上线，运维人力 1 人。

## 决策驱动因素（Drivers）
- 吞吐与水平扩展；消息可重放；与数据平台（Flink）集成；团队熟悉度；运维成本

## 备选方案（Options）
1. Kafka（自建）  2. RocketMQ  3. 云厂商托管消息队列

## 决策（Decision）
采用 **Kafka（自建，3 broker 起步）**，事件通过 **Outbox** 模式发布，Schema 使用 Protobuf 并强制兼容性检查。

## 后果（Consequences）
- 正面：吞吐充足；可重放；与 Flink/ClickHouse 生态集成顺畅；团队可立即上手。
- 负面：事务消息/延迟消息能力弱，延迟任务需另行实现（时间轮/调度平台）；需自建运维（监控、扩缩容、升级）；多语言客户端行为差异。
- 需要后续跟进：建立 Topic 命名与容量规范；Q4 评估迁移到托管服务的成本（重新评估触发条件：运维事故 ≥ 2 次/季度）。

## 备选方案为何不选
- RocketMQ：事务/延迟消息更强，但团队无经验，生态集成需额外工作；
- 托管 MQ：运维最省，但当前预算与合规（数据出境）不确定，且重放/保留成本较高。
```

### 4. 使用规范

| 规范 | 说明 |
| --- | --- |
| **一个 ADR 一个决策** | 短小聚焦（一页）；多个决策拆成多条 |
| **编号 + 状态** | 顺序编号；状态：提议、已接受、已废弃、已被取代；变更用新 ADR 取代旧的 |
| **写“为什么”不是“是什么”** | 重点是背景、约束、备选与取舍，而不是技术介绍 |
| **记录负面后果与重审触发条件** | 诚实写出代价，并写明“什么情况下需要重新评估” |
| **放在仓库里、走 PR 评审** | 与代码同源；`docs/adr/` 目录 + 索引（`README.md` 列表）；可用 adr-tools 等脚手架 |
| **及时写** | 决策当时写，比事后回忆准确；评审结论落到 ADR |
| **团队共识** | ADR 评审是**讨论的载体**，也是新人了解架构演进的入口 |

## 五、评审：怎么开、怎么提问

### 1. 评审流程（RFC 风格）

1. **作者**写完草稿，先找 1~2 位信任的同事**预读**；
2. 发布给评审人（提前 2~3 个工作日），明确**评审范围**与**期望的决策**（“请重点评审第 3、6 节，需要在周五前决定是否采用方案 B”）；
3. **异步评论优先**：评审人在文档里留言，作者回复；争议大的点再开**评审会**；
4. **评审会**：作者 5~10 分钟讲核心思路（不要逐字念文档），**聚焦分歧与风险**，会后记录结论与待办；
5. **决策者拍板**（技术负责人/架构组），记录**未采纳的意见及原因**；
6. **状态更新**：已批准后进入实施；重大偏离再次评审；上线后复盘“实际与设计的差异”。

### 2. 评审人提问清单

| 方向 | 问题示例 |
| --- | --- |
| **目标与范围** | 这个问题真的需要解决吗？成功的标准是什么？有没有更简单的方式达到 80% 的价值？ |
| **方案取舍** | 为什么不选 X？假设有哪些？若假设不成立会怎样？ |
| **数据与一致性** | 数据模型能支持未来 N 种查询吗？并发写冲突、重复请求、部分失败怎么处理？（见 [事件驱动：幂等与 Saga](#/design/event-driven)） |
| **性能与容量** | 容量估算依据？热点在哪里？降级与限流策略？ |
| **可用性与故障** | 任一组件故障会怎样？依赖故障的降级？单点在哪？ |
| **兼容与迁移** | 新旧版本并存期间的兼容？数据迁移如何校验与回退？（见 [发布策略](#/infra/release)） |
| **安全与合规** | 权限、数据保护、审计、隐私（见 [Web 安全](#/security/web)） |
| **可观测与运维** | 上线后怎么知道它正常？告警是什么？怎么排障？谁来值班？ |
| **成本与人力** | 开发与运维成本？有没有现成方案可复用？ |
| **可逆性** | 如果错了，回头的成本多大？ |

### 3. 作为作者：如何被“挑战”得更有收益

- 把评审当作**免费的风险排查**，不是对个人的评判；
- 对批评回应**事实与数据**，不辩解；承认不知道的点，承诺验证；
- 区分**必须解决（blocker）**、**建议（suggestion）**、**疑问（question）**；
- 记录**被否决的方案与原因**（也是 ADR 素材）。

## 六、示例骨架：一份“为订单服务引入缓存”的方案

> [!NOTE] 说明
> 示例为**虚构**，用于展示结构与取舍写法。

**摘要（TL;DR）**：订单详情接口 P99 480ms、数据库读占用 70% CPU。建议引入 **Cache Aside + 本地缓存二级** 把 P99 降到 < 80ms，数据库读降 85%。需决策：是否接受**秒级最终一致**。

**背景与问题**：近三个月订单详情 QPS 增长 3 倍；慢查询占比上升；大促预估再 ×5，数据库无法扩展到该规模（单库单表 9 亿行）。

**目标**：详情接口 P99 < 80ms @ 2 万 QPS；数据库读 QPS 下降 ≥ 80%；缓存与库不一致时间 < 3 秒（P99）；上线零停机。**非目标**：不改订单写入路径；不做分库分表（另行立项）。

**方案对比**：
- **A. Redis 缓存（Cache Aside）**：成熟、易实施；需处理一致性与击穿；
- **B. 读写分离 + 增加从库**：改动小，但从库延迟与成本线性增长，无法 ×5；
- **C. 直接分库分表**：根本解，但周期长、风险高，本期不选。
- **结论**：选 A（+ 本地缓存热点），B 作为兜底，C 另立项。

**详细设计**（略）：缓存键与 TTL（含随机抖动）；更新策略（先写库后删缓存 + 订阅 binlog 异步补删）；击穿保护（单飞/互斥）；穿透保护（空值缓存 + 布隆）；降级（Redis 故障回源并限流）；监控指标（命中率、回源 QPS、延迟、不一致检测）。（参考 [缓存设计与一致性](#/redis/cache)）

**风险**：缓存雪崩（缓解：TTL 抖动 + 预热 + 限流）；删缓存失败导致脏数据（缓解：binlog 补偿 + TTL 兜底）；热点大 Key（缓解：拆分与本地缓存）。

**实施与回滚**：灰度 1% → 10% → 50% → 100%，开关可随时关闭回源；双读校验阶段比对缓存与库差异；回滚 = 关开关。

**验证**：压测达标（见 [压测与容量规划](#/design/eng-loadtest)）；注入 Redis 故障验证降级（见 [稳定性工程](#/design/eng-chaos)）。

## 七、常见反模式

| 反模式 | 问题 / 对策 |
| --- | --- |
| **只写方案不写问题** | 评审在“要不要做”上空转；先写背景与目标 |
| **只有一个方案** | 无法体现取舍；至少 2 个备选并说明不选理由 |
| **目标不可量化** | 无法验收；给数字与验收标准 |
| **没有非目标** | 范围无限膨胀；显式列出不做的事 |
| **只写正常路径** | 线上都是异常路径；补充失败、并发、回滚 |
| **“后续优化”掩盖关键问题** | 容量、安全、可观测不能后置 |
| **文档过长、没有摘要和图** | 没人读；TL;DR + 图表 + 控制篇幅 |
| **评审走过场/一言堂** | 风险没暴露；提前分发、异步评论、记录意见闭环 |
| **决策不留痕** | 半年后没人记得原因；ADR 入库 |
| **文档写完不更新** | 与实现脱节；偏离时更新或补 ADR |
| **技术选型靠“热门”和简历驱动** | 用需求、约束、PoC 和 TCO 决策 |
| **过度设计** | 为不确定的未来堆复杂度；YAGNI、可演进、分期 |

## 八、面试中讲一个技术方案

面试官考察的是**问题意识与取舍能力**，建议按这个顺序讲（3~5 分钟）：

1. **背景与痛点**（含数字）：为什么要做？不做会怎样？
2. **目标与约束**：量化目标、时间/人力/兼容性约束；
3. **方案与备选**：你考虑了哪几种？**为什么选这个、放弃那些**（成本、风险、团队）；
4. **关键设计与难点**：一两个最难的点怎么解决（一致性、性能、迁移），遇到的坑；
5. **风险与上线**：灰度、回滚、监控；
6. **结果与复盘**：指标改善（前后对比）、遗留问题、如果重来会怎么做。

准备好被追问：**“为什么不用 X？”“如果流量翻 10 倍呢？”“出了故障怎么办？”“怎么保证数据一致？”**——这些在你的方案文档里都应有答案（见 [面试速查](#/design/interview)、[系统设计答题框架](#/design/interview)）。

## 面试追问

> [!QUESTION] 一份好的技术方案应该包含哪些内容？
> 背景与带数据的问题、可量化的目标和明确的非目标、至少两个备选方案及取舍和结论、详细设计包括架构、数据模型、接口、核心流程和失败路径、容量与可用性等非功能设计、风险与缓解、实施计划、发布迁移与回滚、测试验证以及待决问题。开头要有摘要，多用图表，并显式写出假设。

> [!QUESTION] 什么是 ADR？为什么要写？
> ADR 是对一个重要架构决策的简短记录，包含背景、备选、决策和后果，放在代码仓库里随代码版本化。它回答未来维护者最关心的为什么当时这样选，避免决策原因随人员流动丢失和重复讨论；决策变化时新建 ADR 取代旧的，而不是修改历史。

> [!QUESTION] 如何在多个技术方案之间做取舍？
> 从需求满足度、复杂度与可维护性、成本、风险、上线与回滚能力、可演进与锁定、对团队的影响等维度对比，可用加权决策矩阵让分歧显式化，但最终要靠 PoC 或压测验证关键假设；同时区分可逆与不可逆的决策，不可逆的投入更多论证，并倾向于成熟的无聊技术、考虑总拥有成本。

> [!QUESTION] 技术评审应该怎么开？
> 作者提前分发文档并说明评审范围和需要的决策，评审人先异步留言，争议点再开会，会上聚焦分歧与风险而不是逐字念文档，会后由决策者拍板并记录未采纳意见和原因，意见区分阻塞项、建议和疑问，所有结论闭环并更新文档状态。

> [!QUESTION] 为什么方案里要写“非目标”？
> 非目标明确本期不做什么，防止评审和实施中范围无限蔓延，帮助团队聚焦、评估工作量和按期交付，也让评审者知道哪些问题不需要在此方案里解决。

> [!QUESTION] 面试时怎么讲清楚一个技术方案？
> 按背景痛点和数字、量化目标与约束、考虑过的方案及为何选择这个、关键难点与解决办法、风险与灰度回滚监控、结果前后对比与复盘的顺序讲，重点突出取舍和失败路径，并准备回答如果流量翻十倍、出故障怎么办、如何保证一致性等追问。
