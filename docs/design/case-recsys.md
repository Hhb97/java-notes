# 案例：推荐系统设计详解

> [!ABSTRACT] 核心要点
> - 推荐系统是**“在海量候选里，用有限的延迟预算，为每个用户挑出最可能满足其目标的少量内容”**。工程上是一个**漏斗**：**召回（万级）→ 粗排（千级）→ 精排（百级）→ 重排（几十条）**，每一层**候选量递减、模型复杂度递增**。
> - 三层架构：**离线（批量特征与模型训练）→ 近线（流式实时特征与增量更新）→ 在线（毫秒级服务）**。**训练与服务的特征一致性**、**数据时效性**和**线上稳定性**是工程难点。
> - **召回追求“不漏”（多路互补、快）**，**排序追求“排准”（精细、可慢）**：召回靠协同过滤、**双塔向量 + ANN**、热门/新品/关注/序列等多路；排序用点击率/转化率等多目标预估后融合。
> - **重排处理“列表整体质量”**：多样性打散、去重已读、频控、保量扶持、业务规则、公平性。
> - **冷启动与探索**：新用户靠热门与上下文、新物品靠**保量流量池 + 探索（bandit）**；没有探索系统会陷入“只推已知爆款”的马太效应。
> - **没有评估就没有推荐**：离线看 **AUC/GAUC/NDCG/召回率**，线上以 **A/B 实验**的业务指标（CTR、时长、转化、留存）为准，并设**护栏指标**（投诉、多样性、延迟）。

> [!NOTE] 说明
> 推荐是算法 + 工程的交叉领域，本文聚焦**后端工程架构**与关键算法思路（不展开模型数学）。容量数字为用于推演的**假设**。与搜索的对比见 [搜索系统案例](#/design/case-search)，Feed 流召回源见 [Feed 流案例](#/design/case-feed)，向量检索思想见 [RAG 检索优化](#/ai/rag-advanced)，模型基础见 [AI 模型与数学](#/aimodel/ml-intro)。

## 一、需求与约束

### 1. 场景与目标

| 场景 | 例 | 输入 | 目标 |
| --- | --- | --- | --- |
| **首页/信息流推荐** | 内容 App、商品瀑布流 | 用户（无 query） | 点击、时长、转化、留存 |
| **相关推荐** | 商品详情页“看了又看”、视频“相关视频” | 当前物品 + 用户 | 点击、加购 |
| **购物车/结算页推荐** | 凑单、关联商品 | 购物车内容 | 客单价、转化 |
| **Push/邮件/召回推荐** | 召回流失用户 | 用户画像 | 打开率、回流 |

**业务目标往往是多目标**（点击率、转化率、时长、互动、多样性、新品曝光、广告收入），需要权衡与融合。

### 2. 非功能与容量估算（假设）

| 维度 | 假设 |
| --- | --- |
| 规模 | 注册用户 2 亿，DAU 5000 万；物品库 5000 万（内容/商品），日新增 200 万 |
| 请求量 | 日均 10 亿次推荐请求 ≈ 1.2 万 QPS 平均，峰值 **4~5 万 QPS** |
| 延迟 | 端到端 **P99 < 150ms**（不含网络）：召回 30ms + 粗排 15ms + 精排 50ms + 重排 15ms + 其他预留 |
| 候选漏斗 | 召回 **5000~1 万** → 粗排 **1000** → 精排 **200** → 重排 **~30** → 展示 **10~20**（分页/下拉） |
| 数据 | 日志：日均数百亿条曝光/点击事件（见 [Kafka](#/mw/kafka)、[ClickHouse](#/bigdata/ck-analytics)）；用户特征存储 2 亿 × 数 KB ≈ 数百 GB；物品向量 5000 万 × 128 维 × 4B ≈ **25GB** |
| 时效 | 用户行为到特征生效：秒~分钟（近线）；模型更新：天级，部分增量小时级 |

## 三、数据与样本

### 1. 行为日志（最重要的资产）

| 日志 | 内容 | 注意 |
| --- | --- | --- |
| **曝光**（展示） | 用户、物品、位置、时间、场景、策略版本、请求 ID | **必须记录曝光**：没有曝光就无法算 CTR、也无法构造“曝光未点击”的负样本 |
| **点击/互动** | 点击、点赞、收藏、评论、分享、加购、下单、观看时长 | 带上同一个请求 ID 与曝光关联 |
| **反馈信号** | 负反馈（不感兴趣、举报、秒退）、完播率 | 比点击更接近满意度 |
| **上下文** | 设备、网络、地理、时间、入口页 | 影响偏好 |

日志入口通常是端上埋点 → 网关 → Kafka，要保证**不丢、可去重、字段规范（Schema 版本化）**（见 [事件驱动：事件设计](#/design/event-driven)）。

### 2. 样本构造

- **正样本**：点击/购买/长时间观看等（按目标定义）；**负样本**：曝光未点击（真实负）+ 随机采样（召回阶段常用“全局随机负样本 + 难负样本”）；
- **标签定义**与目标一致：CTR 用点击、CVR 用转化（**CVR 样本选择偏差**：转化只在点击后才发生，需 ESMM 等多任务方法或全空间建模）；
- **时间窗口与防穿越**：特征必须是**事件发生之前**可得的数据，**严禁使用未来信息**（特征穿越/数据泄漏会让离线指标虚高、线上失效）；训练集按时间切分（不要随机切）；
- **样本不均衡**：正样本稀少，需要负采样或加权；注意**采样后概率校准**；
- **延迟反馈**：转化可能数小时/天后才发生，近期样本标签不完整，需要延迟窗口或校正。

### 2. 关键召回方法

| 方法 | 原理 | 工程要点 |
| --- | --- | --- |
| **ItemCF（协同过滤）** | 同时被很多人喜欢的物品相似；用户历史物品 → 取相似物品聚合 | 离线用 Spark 计算物品相似度矩阵（Top-K 倒排表存 KV）；**热门物品惩罚**（IUF/相似度归一化）避免全推热门；可解释、稳定 |
| **UserCF** | 找相似用户，推荐其喜欢的 | 用户量大时计算与存储代价高，较少单独使用 |
| **双塔模型（Two-Tower）+ ANN** | 用户塔、物品塔分别输出向量，**内积/余弦表示相关度**；物品向量离线预算并建索引，在线只算用户向量再做**最近邻检索** | 物品索引用 **HNSW/IVF-PQ**（Faiss、Milvus、ES 向量）；**物品向量更新与索引重建**、增量更新；负采样质量决定效果；用户塔需低延迟推理 |
| **序列召回（Session/SASRec 等）** | 用最近行为序列预测下一个交互物品 | 实时性强；需要实时行为特征 |
| **热门/新品/运营** | 按场景维度的榜单（见 [Feed 与排行榜](#/design/case-feed)） | 兜底，保证系统在其他路失效时仍有结果 |
| **标签/内容召回** | 用户兴趣标签 → 带标签物品倒排；文本/图片 Embedding 相似 | 冷启动友好（不依赖行为数据） |
| **图召回（GNN/Item2Vec/Node2Vec）** | 在行为图上学习物品表示 | 离线训练成本较高 |

**向量检索**的工程要点与 [RAG 检索优化](#/ai/rag-advanced) 同源：HNSW 内存占用大、召回率与延迟权衡（`efSearch`）、过滤条件的处理（先过滤还是后过滤）、增量写入与重建。

## 五、排序

### 1. 粗排与精排

| | **粗排** | **精排** |
| --- | --- | --- |
| 候选量 | 数千 → 数百 | 数百 → 几十 |
| 模型 | 轻量：双塔/LR/小 DNN（可预计算物品侧） | 复杂：**DeepFM / DIN（注意力）/ 多任务（MMoE、PLE）**、序列建模、交叉特征 |
| 特征 | 少量核心特征 | 丰富：用户长短期兴趣、物品、上下文、**用户-物品交叉**、实时特征 |
| 延迟预算 | 十几毫秒 | 几十毫秒（批量推理） |
| 目标 | 过滤明显不相关，保证不漏好内容 | 精准预估，决定最终顺序 |

### 2. 多目标与融合

业务通常要同时优化多个目标（点击、点赞、评论、分享、完播、转化、负反馈）：

- **多任务学习**：共享底层表示，分别预估 `pCTR、pLike、pShare、pWatchTime、pCVR`（MMoE 等结构缓解任务冲突）；
- **融合公式**（把多个预估合成最终分数），常见形式：

```text
score = pCTR^a × (1 + b·pLike + c·pShare + d·pComment) × E[watch_time]^e × (1 − f·pNegative)
```

- 融合参数由**业务目标 + 在线 A/B + 贝叶斯/自动调参**确定，而不是拍脑袋；
- **校准**：预估概率要接近真实概率（尤其用于广告竞价/多目标乘积），训练时的负采样需要做概率校正。

### 3. 位置偏差与反馈偏差

- **位置偏差**：排在前面的更容易被点，训练数据里点击不全反映偏好——训练时加入**位置特征**（上线时置固定值）或用倾向分加权；
- **选择偏差**：只有被曝光的才有反馈（没曝光的好内容永远没数据）——需要**探索**机制（见冷启动）；
- **流行度偏差/马太效应**：热门越推越热——引入多样性与探索、对热门惩罚。

### 4. 模型推理的工程

| 方向 | 要点 |
| --- | --- |
| **推理部署** | TF Serving / TorchServe / **Triton** / ONNX Runtime；GPU 或高性能 CPU；Java 服务通过 RPC（gRPC，见 [gRPC](#/mw/grpc)）调用推理服务 |
| **批量打分** | 一次请求对几百个候选**批量推理**，利用向量化；控制 batch 与延迟 |
| **特征获取** | 用户特征一次取，物品特征 `mget` 批量取；热点特征本地缓存；避免 N+1 |
| **模型/特征版本一致** | 模型 v5 必须使用对应版本的特征处理逻辑与词表 |
| **性能优化** | 模型蒸馏/量化、精排特征裁剪、结果缓存（相同用户短时间重复请求）、异步预取 |

## 六、重排

重排关注**整个列表的质量**，而不仅是单个物品的分数：

| 手段 | 说明 |
| --- | --- |
| **多样性打散** | 避免连续出现同作者/同品类/同风格：MMR（最大边际相关）、DPP（行列式点过程）、规则打散（同类间隔 N 个） |
| **去重与已读过滤** | 已展示/已看过/已购买：用户已读集合或**布隆过滤器**（见 [工程中的算法](#/cs/algo-engineering)），并保留“重复曝光上限”（频控） |
| **业务规则** | 置顶/运营位、广告穿插、保底品类占比、合规黑名单、库存/可售性过滤（价格、库存实时校验） |
| **保量与扶持** | 新作者/新物品保证最低曝光（流量池）、冷启动探索位（见下） |
| **公平与生态** | 避免头部垄断；创作者生态与长期价值 |
| **体验约束** | 首屏质量、加载策略、分页稳定性（下拉刷新带来的重复） |

## 七、冷启动与探索

### 1. 冷启动

| 对象 | 做法 |
| --- | --- |
| **新用户** | 无行为：用**热门/编辑精选 + 上下文（地域、设备、时间、来源渠道）**；**兴趣引导**（注册时选兴趣）；快速学习：前几次点击即实时更新兴趣（近线特征）；注册信息/第三方画像（合规前提） |
| **新物品** | 无行为数据：靠**内容特征**（文本/图像 Embedding、类目、作者历史表现）做内容召回；进入**新品流量池**，给固定曝光配额，根据初期 CTR 决定是否放量（**赛马机制**） |
| **新场景/新业务** | 迁移已有数据 + 规则策略兜底，随数据积累逐步模型化 |

### 2. 探索与利用（Exploration vs Exploitation）

只利用已知偏好会陷入“信息茧房”并让新内容永无出头之日。常用方法：

- **ε-greedy**：以小概率 ε 随机推荐探索；
- **UCB / Thompson Sampling（多臂老虎机）**：对不确定性高的候选加“探索奖励”；
- **上下文 Bandit（LinUCB）**：结合用户特征；
- **工程化做法**：预留**探索位**（如每屏 1~2 个）、新品流量池、对低曝光物品加不确定性加成；
- 需要**评估长期收益**：探索短期降低点击，但提升多样性与新内容生态，需用长期指标（留存、创作者留存）衡量。

## 八、特征平台

特征是推荐效果的核心，也是工程复杂度所在。

| 类型 | 例 | 生产方式 | 存储与读取 |
| --- | --- | --- | --- |
| **静态/离线特征** | 用户画像（性别、长期兴趣）、物品类目/作者 | 离线批处理（Hive/Spark，T+1） | KV（Redis/HBase/内部 KV）按 ID 读取 |
| **统计特征** | 物品近 7 日 CTR、用户近 30 日点击品类分布 | 离线 + 近线增量 | 同上 |
| **实时特征** | 用户最近 20 次点击序列、物品最近 5 分钟曝光/点击 | **Flink 流计算**（见 [Flink](#/bigdata/flink-core)）写入在线存储 | Redis（低延迟）、带 TTL |
| **交叉特征** | 用户品类偏好 × 物品品类 | 在线计算/模型内部 | — |
| **上下文特征** | 时间、设备、网络、位置 | 请求时携带 | — |
| **Embedding 特征** | 用户/物品向量 | 模型训练产出 | 向量库/KV |

**关键问题**：

- **训练-服务一致性（Training-Serving Skew）**：线上特征的计算逻辑、取值时间点、缺失值处理必须与训练时**完全一致**。做法：**同一份特征定义（代码/DSL）同时用于离线与在线**（特征平台：Feast、自研）；线上**落盘实际使用的特征**（特征快照/日志）直接作为训练样本——“用线上真实特征训练”能彻底避免不一致；
- **时间正确性（Point-in-Time）**：训练样本里的特征要取**样本发生时刻**之前的值（时间旅行 Join），不能用最新值；
- **实时特征的延迟与丢失**：监控特征新鲜度、缺失率、分布漂移；
- **读性能**：精排一次请求要取上千个物品特征：KV 批量 `mget`、分片、本地缓存热点、特征打包（把一个物品的所有特征存成一个 value）；
- **特征治理**：特征字典、负责人、使用方、质量监控、下线机制（防止特征爆炸与僵尸特征）。

## 九、在线服务：延迟预算与降级

### 1. 延迟预算

```text
总预算 150ms（P99）
 ├─ 网关/解析/用户上下文：10ms
 ├─ 多路召回（并发，取最慢者 + 超时）：30ms
 ├─ 特征获取（粗排+精排）：20ms
 ├─ 粗排：10ms
 ├─ 精排（批量推理）：45ms
 ├─ 重排：10ms
 └─ 序列化与预留：25ms
```

- 各阶段设置**超时**（不是“等到结果为止”），超时用**降级结果**；
- **并发与批量**：多路召回并发；精排批量推理；
- **预计算与缓存**：高频用户/场景的推荐结果（Top 100）离线或近线预算并缓存（Redis），在线只做轻量重排；用户短时间内重复请求命中缓存；
- 对 P99 影响最大的往往是**慢依赖**（某一路召回、特征服务、模型推理的长尾），需要**对冲请求（Hedged Request）**、超时与熔断。

### 2. 降级策略（分层）

| 故障 | 降级 |
| --- | --- |
| 某一路召回超时/失败 | 丢弃该路，使用其他路结果 |
| 特征服务慢/不可用 | 使用缺省特征/缓存特征；跳过精排，使用粗排结果 |
| 模型推理服务故障/过载 | 回退到**上一版本模型**或**规则/统计排序**（按热度+个性化标签） |
| 向量检索服务故障 | 仅用倒排/热门召回 |
| 整个推荐链路超时 | 返回**兜底缓存**（按场景的热门/精选榜单）——保证“有内容可看” |
| 流量洪峰 | 限流、缩小候选规模、减少召回路数、关闭复杂重排（见 [稳定性工程](#/design/eng-chaos)） |

**降级要事先设计、开关化、定期演练**（见 [稳定性工程：降级演练](#/design/eng-chaos)）。

### 3. 工程细节

- **请求去重与分页**：下拉刷新要避免重复内容：服务端记录用户**已曝光集合**（Redis，短 TTL）或在重排过滤；翻页用上次游标/曝光序列，而不是简单 offset；
- **缓存一致性**：物品下架/价格库存变化要尽快从候选中剔除（召回侧过滤 + 重排前**批量校验可售性**）；
- **日志**：每次请求记录**策略版本、候选来源、各阶段分数、最终列表与位置**，用于复盘、训练样本与归因（日志量大，用 Kafka + 列存分析）；
- **灰度**：新模型/新策略通过实验平台按用户分桶放量，配合指标自动回滚（见 [发布策略](#/infra/release)）。

## 十、评估：离线、在线与实验

### 1. 离线指标

| 指标 | 用于 | 说明 |
| --- | --- | --- |
| **AUC / GAUC** | 精排（CTR 预估） | AUC 衡量整体排序能力；**GAUC（按用户分组的 AUC）**更贴近“每个用户的排序质量”，与线上相关性更高 |
| **LogLoss / 校准误差** | 概率预估质量 | 多目标融合与竞价要求概率准 |
| **Recall@K / HitRate@K** | 召回 | 真实点击物品是否在召回的前 K 个里 |
| **NDCG@K / MAP** | 排序质量 | 考虑位置折扣的相关性 |
| **覆盖率 / 多样性 / 新颖性** | 生态 | 推荐是否只集中在少数物品 |

**注意**：**离线指标提升不等于线上提升**（数据偏差、特征穿越、目标不一致）；离线指标主要用于**淘汰差方案、快速迭代**，**最终以线上 A/B 为准**。

### 2. 在线 A/B 实验

- **分流**：按用户 ID 哈希分桶（同一用户始终在同一实验组，避免体验跳变），**正交分层**（不同层的实验互不干扰：召回层、排序层、重排层、UI 层各一层）；
- **指标体系**：**核心指标**（CTR、人均时长、转化/GMV、留存）、**护栏指标**（延迟、投诉、负反馈、多样性、崩溃率）、**长期指标**（7/30 日留存、创作者留存）；
- **统计功效**：足够样本量与时长（至少覆盖一个周期，避免周内效应）；**显著性检验**、置信区间、多重比较校正；警惕**新奇效应**（新策略短期点击高后回落）；
- **干净对照**：AA 实验验证分流无偏；避免实验间干扰；记录实验 ID 用于归因；
- **快速失败**：先小流量（1%）验证无严重问题，再逐步放量。

### 3. 常见评估陷阱

| 陷阱 | 说明 |
| --- | --- |
| 特征穿越/数据泄漏 | 训练用了未来信息，离线很高线上无效 |
| 只看点击率 | 可能推“标题党”，损害长期体验；用多目标与护栏指标 |
| 辛普森悖论 | 分群后结论相反（流量结构变化）；分层分析 |
| 样本偏差 | 只对曝光样本评估，新物品/长尾被忽略；加入探索与反事实评估 |
| 实验污染 | 同一用户跨组、实验层耦合；正交分层与监控 |
| 短期指标好、长期变差 | 引入长期指标与留存实验（长周期） |

## 十一、模型上线、监控与治理

### 1. 上线流程

```text
训练（定时/触发）→ 离线评估（AUC/GAUC、与线上基线对比）→ 影子/回放验证（线上流量打分对比，不影响用户）
→ 小流量灰度（A/B）→ 指标达标逐步放量 → 全量 → 保留上一个版本用于回滚
```

- **模型与特征版本管理**（Model Registry）：版本、训练数据区间、特征版本、评估结果、负责人；
- **一键回滚**：回到上一版模型；
- **增量训练/在线学习**：对时效敏感的场景（资讯、直播）缩短更新周期，需要防止噪声与不稳定。

### 2. 监控

| 维度 | 指标 |
| --- | --- |
| **服务** | QPS、各阶段延迟、超时率、降级率、模型推理耗时与错误率（见 [指标监控](#/infra/obs-metrics)） |
| **数据/特征** | 特征缺失率、新鲜度、分布漂移（PSI）、日志延迟与丢失 |
| **模型** | 线上预估 CTR 与实际 CTR 的校准、分数分布漂移、各来源召回贡献 |
| **业务** | 点击率、时长、转化、多样性、新品曝光占比、负反馈率 |
| **异常告警** | 业务指标同比/环比突降（可能是特征/模型/数据问题），设自动保护（回退） |

### 3. 治理与合规

- **信息茧房/多样性**：设置多样性目标与探索比例，避免过度个性化；
- **内容安全与合规**：违规内容在召回/重排前过滤，未成年人保护，敏感内容降权；
- **隐私**：个人数据最小化、可解释的用户控制（关闭个性化推荐、清除画像）、数据脱敏与访问控制（见 [加密与密钥管理](#/security/crypto)）；相关法规对算法推荐有透明度与用户选择权要求，**以适用法规为准**；
- **公平性与创作者生态**：避免头部垄断、对新人有扶持；
- **可解释性**：“因为你看过 X”之类推荐理由，有助信任与排障。

## 十二、与搜索、LLM 的关系

| | 推荐 | 搜索（见 [搜索系统案例](#/design/case-search)） |
| --- | --- | --- |
| 触发 | 无 query（隐式意图） | 有 query（显式意图） |
| 召回 | 用户兴趣/协同/向量 | 倒排检索（BM25）+ 向量 |
| 排序目标 | 点击/时长/转化预估 | 相关性为主 + 业务信号 |
| 共性 | **召回→排序→重排**漏斗、日志闭环、实验评估、特征与模型工程 | 同左 |

**LLM 的影响**：用 LLM 做**内容理解与标签**、**用户兴趣的文本化表示**、**冷启动的语义召回**、**对话式推荐**与**推荐理由生成**；但**在线精排仍以延迟与成本友好的专用模型为主**，LLM 更多用于离线特征/召回与上层交互（RAG 思路见 [RAG](#/ai/rag)）。

## 十三、取舍总结

| 取舍 | 选择 | 代价 |
| --- | --- | --- |
| 召回多路 vs 单路 | 多路互补 + 配额 | 系统复杂、调参多；需分析各路贡献 |
| 精排复杂度 vs 延迟 | 漏斗控制候选量、批量推理、蒸馏 | 精度与成本的权衡 |
| 实时特征 vs 稳定性 | 关键特征实时，其余离线 | 近线链路与一致性复杂度 |
| 利用 vs 探索 | 预留探索位与新品池 | 短期指标略降，长期生态收益 |
| 离线指标 vs 线上 A/B | 离线筛选，线上定夺 | 实验周期与流量成本 |
| 个性化 vs 多样性/合规 | 重排与规则约束 | 单一指标可能下降 |
| 自研 vs 云推荐服务 | 视规模与差异化 | 自研投入大；云服务定制受限 |

## 面试追问

> [!QUESTION] 推荐系统的整体架构是什么？为什么要分召回、粗排、精排、重排？
> 离线层构建样本和特征并训练模型，近线层用流计算更新实时特征，在线层并发多路召回，再粗排、精排、重排返回列表，曝光点击日志回流形成闭环。分层是因为候选量与模型复杂度的矛盾：召回快速从千万物品里取万级，粗排用轻量模型压到千级，精排用复杂模型精准打分，重排处理多样性与业务规则，在有限延迟内逐层收敛。

> [!QUESTION] 双塔召回的原理和工程要点？
> 用户塔和物品塔分别输出向量，相关度用内积或余弦表示；物品向量离线算好并建立 HNSW 或 IVF 索引，在线只计算用户向量再做近邻检索，速度快。要点是负采样质量、物品向量与索引的增量更新和重建、检索召回率与延迟的权衡、过滤条件的处理，以及用户塔的低延迟推理。

> [!QUESTION] 离线 AUC 提升了，线上却没效果，可能是什么原因？
> 常见原因有特征穿越或数据泄漏、训练与线上特征不一致、样本只覆盖曝光导致选择偏差、离线目标与线上业务目标不一致、位置偏差，以及线上服务延迟、超时和降级影响。应使用线上真实特征落盘训练、按时间切分数据、看 GAUC，并最终以线上 A/B 为准。

> [!QUESTION] 如何解决冷启动问题？
> 新用户用热门、编辑精选、上下文和兴趣引导，并快速用实时特征学习；新物品用内容特征做语义召回，进入新品流量池按固定配额曝光，根据初期表现赛马放量；同时用 bandit 等探索机制和预留探索位，避免只推已知爆款。

> [!QUESTION] 训练和服务特征不一致怎么避免？
> 用同一份特征定义同时服务离线与在线，建立特征平台；线上把实际使用的特征落盘作为训练样本，彻底避免不一致；训练样本按样本发生时刻取特征保证时间正确性；监控特征缺失率、新鲜度和分布漂移，模型与特征处理逻辑版本一一对应。

> [!QUESTION] 推荐服务要求几十到上百毫秒，怎么保证稳定？
> 为各阶段分配延迟预算并设超时，多路召回并发，精排批量推理，特征批量读取并本地缓存，热点用户结果预计算缓存；每个依赖有降级方案，如丢弃慢的召回路、特征缺省、模型回退到上一版或规则排序、最终返回兜底热门缓存；对慢依赖用熔断和对冲请求，并对降级开关定期演练。

> [!QUESTION] 如何评估推荐效果？A/B 实验要注意什么？
> 离线看 AUC、GAUC、NDCG 和召回率用于快速筛选，线上以 A/B 实验为准，指标分核心指标、护栏指标和长期指标。按用户哈希分桶保证同用户体验一致，分层正交避免实验干扰，保证足够样本和周期，做显著性检验，警惕新奇效应、辛普森悖论和实验污染，先小流量验证再放量。
