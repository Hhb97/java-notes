# 事故响应与复盘

> [!ABSTRACT] 核心要点
> - **事故响应的第一目标是“尽快恢复用户服务”，不是“找到根因”**。止血手段（回滚、降级、限流、切流、扩容）优先于排查；**根因分析留给恢复之后**。
> - **有序的响应靠角色分工和分级**：**事故指挥官（IC）** 统一决策、**技术负责人**带队排查、**沟通负责人**对内外同步、**记录员**记时间线；按严重度（P0~P3）决定升级范围、响应时限与通报对象。
> - **沟通要“固定节奏 + 固定模板”**：影响范围、当前状态、已采取措施、下次更新时间；**不猜测、不甩锅、不承诺未确定的恢复时间**。
> - **复盘（Postmortem）的目的是改进系统，不是追责个人**：**无责（blameless）文化**让人愿意说出真相；产出是**时间线、根因与贡献因素、做得好与不好、可执行的改进项（负责人 + 期限）**。
> - **根因几乎从不是“某人犯了错”**：人只是触发者，真正的问题是**让这个错误能发生并扩大的系统缺陷**（缺少防呆、缺少灰度、缺少监控、缺少回滚、缺少演练）。
> - **改进项要闭环**：没有负责人和期限的改进项等于没有；同类故障复发是复盘失败的信号。

## 二、事故分级与升级

### 1. 分级标准（示例，需结合业务定制）

| 级别 | 定义（示例） | 响应要求 |
| --- | --- | --- |
| **P0 / SEV1** | 核心业务全面不可用或严重资损/数据泄露；影响大量用户 | **立即**拉起应急（5 分钟内响应），高管通报，指挥官 + 全员待命，定时对外同步 |
| **P1 / SEV2** | 核心功能显著降级（成功率明显下降/部分用户不可用） | 15 分钟内响应，相关团队参与，值班领导知悉 |
| **P2 / SEV3** | 非核心功能异常或局部影响，有降级手段 | 工作时间内处理，值班人跟进 |
| **P3 / SEV4** | 轻微问题，无明显用户影响 | 纳入常规缺陷/迭代 |

分级依据：**用户影响面 × 业务重要度 × 资损/合规风险 × 持续时间**；**宁可高估**，发现影响小再降级；升级触发条件要明确（如“30 分钟内未止血自动升一级”）。

### 2. 谁来响应：值班体系

- **一线值班（On-call）**：接收告警、初判、必要时升级；**二线/专家**（按领域）；**管理升级链**（技术负责人、业务负责人）；
- **轮值**：固定周期轮换，有交接清单；值班人员**不应是单点**（有备份）；
- **告警质量**：告警必须**可行动**、带 Runbook 链接（见 [指标监控：告警原则](#/infra/obs-metrics)）；**告警疲劳**（太多误报）会让真正的告警被忽略——定期治理：合并、降噪、删除无人处理的告警；
- **值班补偿与可持续**：夜间告警多说明系统有问题，应作为技术债优先治理，而不是靠人硬扛。

## 三、响应：角色与流程

### 1. 角色

| 角色 | 职责 |
| --- | --- |
| **事故指挥官（IC, Incident Commander）** | **统一决策**：分配任务、决定止血方案、升级与结束事故；**不亲自排查**，保持全局视野 |
| **技术负责人（Tech Lead / Ops Lead）** | 带领技术排查，提出与执行止血/恢复操作；可按领域分组（DB、网络、应用） |
| **沟通负责人（Comms Lead）** | 对内（业务、客服、管理层）与对外（用户、状态页）按节奏同步；收集影响信息 |
| **记录员（Scribe）** | 在事故文档里实时记录时间线、决策、命令与结果 |
| **业务代表** | 评估业务影响（订单、资损、用户数），参与降级决策 |

小团队一人可兼多个角色，但**指挥与排查最好分开**。

### 2. 处置流程（检查清单）

1. **确认事故**：看监控/拨测确认不是误报；**初步范围**（哪些用户/接口/区域）；
2. **分级并拉起响应**：建专用沟通群/会议（所有信息集中于此）、指定 IC 与角色、开启事故文档；
3. **看变更**：**最近是否有发布/配置/开关/数据库变更/依赖变更？**（大多数事故与变更相关）——有则**优先回滚**；
4. **止血**：按预案执行——回滚、关特性开关、降级、限流、切流/隔离故障单元、重启/扩容、摘除异常实例；每个动作**宣布 → 执行 → 验证效果**；
5. **定位（并行但不阻塞止血）**：指标 → 链路 → 日志漏斗（见 [链路追踪、日志与告警](#/infra/obs-trace)）；保留现场（线程栈、堆 dump、抓包、日志快照）后再重启；
6. **恢复验证**：核心业务指标回归稳态（成功率、延迟、队列）；对账与数据修复；
7. **结束与交接**：确认稳定一段时间后宣布结束；安排复盘；

### 3. 止血手段优先级（从快到慢）

| 手段 | 速度 | 适用 |
| --- | --- | --- |
| **关特性开关 / 切回旧逻辑** | 秒级 | 新功能引起 |
| **回滚发布 / 回滚配置** | 分钟级 | 变更引起（最常见） |
| **降级非核心功能 / 限流** | 秒~分钟 | 容量不足、依赖故障、被攻击 |
| **切流 / 摘除故障节点或可用区** | 分钟级 | 局部故障、单机房/单实例异常 |
| **扩容 / 重启** | 分钟级 | 资源耗尽、瞬时故障（重启前先保留现场） |
| **临时修复（Hotfix）** | 小时级 | 无法回滚的缺陷；风险高，需评审与灰度 |

> [!WARNING] 不要在线上“边猜边改”
> 事故中最危险的行为是**多人同时随意改线上**（改配置、重启、改数据）——会让问题复杂化、破坏现场。所有变更**由 IC 授权、记录、逐个执行并验证**；操作前想好回退。

## 四、沟通

### 1. 对内沟通（节奏）

- **固定频率**：P0 每 15~30 分钟一次，即使“无新进展”也同步；P1 每小时；
- **内容模板**：

```text
【事故通报 #3】2026-10-12 21:40  级别：P1
影响：约 15% 用户下单失败（支付渠道 A 超时），预估损失订单 xx 笔/分钟
状态：处理中——已切换到渠道 B，成功率从 82% 恢复到 96%，观察中
已采取：21:22 发现告警；21:28 确认与 20:55 发布的路由变更相关；21:35 回滚发布；21:38 渠道切换
下一步：确认回滚后各区域成功率；排查渠道 A 超时原因；
需要：客服同步话术（见下）；风控协助核对异常订单
下次更新：22:10 或有重大变化时
```

- **只陈述已知事实**，区分“已确认/正在排查/推测”；**不推测根因、不指责、不承诺恢复时间**（除非有把握，且给区间）；
- **客服/运营**需要口径：影响范围、用户可采取的操作、补偿方案。

### 2. 对外沟通

- **状态页/公告**：及时、透明、简明：现象、影响、进展、恢复时间；避免技术黑话；
- 重大事故事后发布**公开复盘**（脱敏）有助于信任；
- 涉及**数据泄露/合规**：按法规与公司流程在规定时限内通报（法务/安全参与）。

## 五、复盘（Postmortem）

### 1. 无责文化

- **目的是学习与改进系统**，不是找人背锅。如果“某人操作失误”就是根因，等于承认系统允许一次失误造成严重后果——**缺陷在于缺少防呆和保护**；
- 事实陈述**使用“系统/流程”主语**而非人名（“发布流程没有灰度”而不是“小王直接全量发布”）；
- 鼓励**坦诚**：被惩罚的人以后会隐瞒；复盘中的信息必须是安全的；
- 管理者的责任：保障无责氛围、推动改进项落地、提供资源。

### 2. 触发与时机

- **必须复盘**：P0/P1、涉及资损/数据损坏/安全、客户可感知的重大故障、**差点发生的重大事故（Near Miss）**、重复发生的故障；
- **时机**：事故结束后 **2~5 个工作日内**开会（记忆新鲜、情绪平复），文档先行（IC/记录员起草时间线）；
- **参与者**：事故相关人员、各团队代表、不在场的“局外人”（提供新视角）。

### 3. 复盘文档模板

```markdown
# 事故复盘：<一句话标题>（日期，级别）

## 摘要
一段话：发生了什么、影响多大、持续多久、如何恢复、主要根因与改进。

## 影响
- 用户影响：受影响比例/数量、业务（下单、支付…）、持续时间（开始—恢复）
- 业务/财务影响：订单损失、资损、赔偿；声誉/合规影响
- 关键指标：MTTD / MTTA / MTTR

## 时间线（UTC+8，精确到分钟，包含决策与动作）
| 时间 | 事件 |
| 20:55 | 发布 v2.3.1（修改路由规则） |
| 21:22 | 告警：下单成功率 < 95%，值班 A 响应 |
| 21:28 | 确认与发布相关，拉起 P1 响应，指定 IC |
| 21:35 | 回滚发布 |
| 21:42 | 成功率恢复，观察中 |
| 22:30 | 结束事故 |

## 根因与贡献因素
- **直接原因（触发）**：…
- **根本原因（系统层面）**：…（用 5 Why 追到流程/设计/监控缺陷）
- **贡献因素**：监控盲区、缺少灰度、预案缺失、文档过期、容量余量不足…
- **为什么没有更早发现/更早止血**：…

## 做得好的地方
（快速回滚、沟通有序、预案有效…）

## 做得不好 / 运气成分
（告警延迟 7 分钟、回滚脚本未经演练、恰好在低峰…）

## 改进项（Action Items）
| # | 改进 | 类型 | 负责人 | 截止日期 | 状态 |
| 1 | 发布流程强制金丝雀与自动指标判定 | 预防 | … | … | … |
| 2 | 增加“渠道成功率”业务告警，5 分钟内触发 | 检测 | … | … | … |
| 3 | 回滚脚本纳入每月演练 | 响应 | … | … | … |

## 经验教训与附录
（监控截图、关键日志、相关链接）
```

### 4. 根因分析方法

| 方法 | 做法 |
| --- | --- |
| **精确时间线** | 先还原事实：何时发生什么，用日志/监控/变更记录**交叉验证**；事实清楚才能分析因果 |
| **5 Why** | 连续追问“为什么”，从现象追到**系统/流程层面**。例：成功率下降→路由规则错误→发布未经测试覆盖该路径→测试环境缺少该渠道数据→**没有机制要求发布前做渠道回归** |
| **贡献因素分析（多因素）** | 复杂系统事故很少只有单一原因：把**触发因素、放大因素、延迟发现因素、延迟恢复因素**分别列出（鱼骨图/因果图） |
| **变更分析** | “事故前最近一次变化是什么？”——发布、配置、数据、流量模式、依赖、季节/日期（如跨月/跨年/夏令时） |
| **对比分析** | 与正常时段/正常实例对比（哪个实例/区域/版本异常） |
| **Near-miss 分析** | 事故没发生但差一点——同样产出改进项 |

**避免的结论**：“员工疏忽”“操作失误”“偶发”“网络抖动（无证据）”——这些没有指向可改进的系统缺陷。

### 5. 改进项：让复盘真正有价值

好的改进项是 **SMART**（具体、可衡量、可达成、相关、有期限）并有类型：

| 类型 | 目标 | 例 |
| --- | --- | --- |
| **预防（Prevent）** | 让同类问题不再发生 | 发布强制灰度、配置变更评审、容量护栏、类型系统/校验防呆 |
| **检测（Detect）** | 更早发现 | 业务指标告警、SLO 燃烧率、拨测、异常检测 |
| **缓解（Mitigate）** | 缩小影响与加快恢复 | 降级开关、自动回滚、限流、故障隔离 |
| **响应（Respond）** | 提升处置效率 | Runbook、值班培训、工具、沟通模板 |
| **流程/文化** | 系统性改进 | 变更窗口、演练制度、评审清单 |

- 改进项要有**负责人和截止日期**，进入统一的待办跟踪系统，**定期（周/月）回顾完成率**；
- **优先级**：优先“成本低、覆盖面大”的（如发布灰度）；避免只列“加强培训/提高意识”这种无法验证的条目；
- **验证**：改进完成后用**演练/混沌实验**验证有效（见 [稳定性工程](#/design/eng-chaos)）；
- **复发检测**：同类故障复发要追溯上次改进项为何未生效。

## 六、示例复盘（虚构，仅示意写法）

> [!NOTE] 说明
> 以下为**虚构示例**，用于展示结构与语气，不对应任何真实事故。

**标题**：路由规则变更导致 15% 下单失败（P1，持续 47 分钟）

**摘要**：10 月 12 日 20:55 发布的网关路由变更，把部分支付请求错误路由到已下线的渠道 A 备用节点，造成约 15% 的下单失败。21:35 回滚后恢复。根本原因是**变更发布缺少金丝雀与业务指标自动判定**，且**监控缺少“渠道维度成功率”**，导致发现晚、回滚晚。

**影响**：约 8.2 万笔下单请求失败（其中约 60% 用户重试成功），估算订单损失约 3.1 万笔；MTTD 27 分钟，MTTR 47 分钟。

**根因（5 Why）**：成功率下降 ← 请求被路由到失效节点 ← 路由规则中保留了旧节点地址 ← 变更评审只检查语法没有校验目标节点存活 ← **没有对路由变更的自动化校验与灰度**。

**贡献因素**：全量发布（无灰度）；告警仅看总成功率（被其他渠道稀释，阈值 95% 未触发）；回滚脚本在预发验证过，但生产权限需二次审批耗时 6 分钟。

**做得好**：值班 A 5 分钟内响应并拉群；IC 迅速指定并要求先回滚；沟通群信息集中；客服口径 10 分钟内同步。

**改进项**：① 网关配置变更强制**金丝雀 + 自动判定**（成功率/延迟）（预防，负责人 X，10/31）；② 增加**按渠道/按路由目标**的成功率告警，5 分钟内触发（检测，Y，10/20）；③ 路由变更增加**目标节点存活校验**（预防，Z，10/25）；④ 回滚权限预授权给值班（响应，W，10/18）；⑤ 每季度演练“错误路由”场景（流程，V，Q4）。

## 七、度量与持续改进

| 指标 | 说明 |
| --- | --- |
| **MTTD / MTTA / MTTR** | 发现 / 响应 / 恢复的平均或分位时间；分级统计，趋势比绝对值更重要 |
| **事故数量与级别分布** | 总量下降不是唯一目标（也许是少报）；关注 P0/P1 趋势与重复事故比例 |
| **变更导致的比例** | 指导发布流程改进（见 [CI/CD：DORA 指标](#/infra/cicd)） |
| **复盘覆盖率与按期完成率** | 应复盘的事故中完成复盘的比例；改进项按期关闭率 |
| **告警质量** | 误报率、无人处理告警数、夜间唤醒次数 |
| **预案覆盖与演练** | 核心场景预案覆盖率、演练频次 |

**知识沉淀**：事故库（可检索）、典型根因清单、新人培训案例、从复盘提炼“检查清单”并嵌入发布与评审流程。

## 八、常见根因分类（用于归纳趋势）

| 类别 | 例 | 典型改进方向 |
| --- | --- | --- |
| **变更相关** | 发布缺陷、配置错误、数据库变更不兼容、开关误操作 | 灰度、自动回滚、配置校验、变更评审 |
| **容量与流量** | 突发流量、热点、慢查询、重试风暴、资源耗尽 | 压测、限流、弹性、过载保护 |
| **依赖故障** | 下游变慢、中间件宕机、第三方、DNS/证书 | 超时/熔断/降级、冗余、证书过期监控 |
| **基础设施** | 机器/网络/磁盘、云厂商故障、机房 | 多可用区、容灾演练 |
| **数据** | 数据错误/丢失/不一致、误删 | 备份恢复、对账、权限与防呆 |
| **监控与响应** | 告警缺失/延迟/噪声、预案缺失/过期、权限不足 | 业务告警、SLO、Runbook、演练 |
| **设计缺陷** | 单点、隐性耦合、缺少幂等、竞态 | 架构评审、混沌实验 |
| **安全** | 攻击、漏洞利用、凭据泄露 | 见 [Web 安全](#/security/web) |

## 九、常见反模式

| 反模式 | 问题 / 对策 |
| --- | --- |
| **事故中先找根因，不先止血** | 影响时间被拉长；变更相关先回滚 |
| **多人同时操作线上** | 破坏现场、问题复杂化；IC 统一授权与记录 |
| **复盘变批斗会** | 人们隐瞒信息；坚持无责与系统视角 |
| **根因写成“人员疏忽”** | 没有可改进的系统缺陷；用 5 Why 追到流程与设计 |
| **改进项无人认领、无期限** | 复发；负责人 + 截止日期 + 定期回顾 |
| **只写“加强培训/提高意识”** | 无法验证；改成自动化防呆、检查清单、工具 |
| **复盘文档写完就束之高阁** | 建事故库、新人学习、复盘中提炼的清单进入流程 |
| **不复盘“小事故”和 Near Miss** | 错过便宜的学习机会；轻量复盘（半小时） |
| **告警太多导致疲劳** | 治理告警：可行动、分级、降噪、删除 |
| **沟通沉默或过度承诺** | 固定节奏同步；只讲事实；不承诺未确定的时间 |
| **事故结束就散，未验证数据** | 对账、补偿、数据修复后再关闭 |

## 面试追问

> [!QUESTION] 线上出现严重故障，你会怎么处理？
> 先确认影响范围并分级，拉起应急群并指定指挥官与沟通负责人；第一时间看最近的变更，优先回滚或关特性开关，其次降级限流、切流、扩容，所有操作由指挥官授权并记录，先止血后定位；恢复后验证核心指标和数据一致性，再宣布结束，并安排无责复盘。

> [!QUESTION] 事故响应中为什么要先止血再找根因？
> 用户影响随时间累积，止血能立即降低损失，而根因排查往往耗时且需要保留现场。多数事故与变更相关，回滚、关开关、降级、切流这些手段比定位根因快得多；恢复后再基于保留的日志、监控和现场分析根因。

> [!QUESTION] 什么是无责复盘？为什么重要？
> 复盘的目的是改进系统而不是追责个人，事实陈述以系统和流程为主语。如果惩罚当事人，大家会隐瞒真相，后续同类问题无法暴露；而把人的失误当根因，等于承认系统缺少防呆、灰度、监控和回滚等保护，改进应落在这些系统缺陷上。

> [!QUESTION] 一份好的复盘包含什么？改进项怎么保证落地？
> 包含摘要、影响与指标、精确时间线、根因与贡献因素、做得好与不好以及运气成分、改进项。改进项要具体可衡量，分预防、检测、缓解、响应等类型，有负责人和截止日期，进入统一跟踪并定期回顾完成率，完成后用演练验证有效，同类故障复发要追溯为何未生效。

> [!QUESTION] 事故沟通要注意什么？
> 固定节奏同步，即使没有进展也更新；使用模板写明影响、状态、已采取措施、下一步和下次更新时间；只陈述已确认的事实，区分推测，不指责、不承诺未确定的恢复时间；有专门的沟通负责人对接业务、客服、管理层和用户，让技术人员专注排查。

> [!QUESTION] 如何减少告警疲劳？
> 告警要可行动并附 Runbook，基于症状和 SLO 而不是单纯资源阈值，分级并合并同类告警，定期治理误报和无人处理的告警，关键路径设置死人开关检测，夜间唤醒次数作为技术债优先治理。
