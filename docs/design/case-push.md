# 案例：实时消息推送系统设计详解

> [!ABSTRACT] 核心要点
> - 推送平台的任务是**把一条消息，可靠、低延迟、成本可控地触达目标用户的设备**。与 IM 的区别：**以“系统/运营→用户”的单向通知为主，扇出规模大（单次可达亿级）、对顺序要求弱、更强调到达率、限频与合规**。
> - **多通道**：**在线 → 自有长连接（WebSocket/自定义 TCP）实时推送；离线 → 厂商通道（APNs/FCM/华为小米 OPPO vivo 等）唤醒；重要消息再降级到短信/邮件**。**长连接是实时性与成本的最佳点，厂商通道是离线触达的必需品**。
> - **扇出是核心难点**：全员广播**不能逐用户查路由发送**，而是**把消息按“接入节点”广播出去，由各节点遍历本机连接**；离线部分分片批量交给通道网关，**限速 + 优先级 + 分批**。
> - **推送只是“提示”，内容靠拉取**：payload 尽量轻（标题 + 业务 ID），详情由客户端拉取；这样**可撤回、可更新、不泄露敏感信息**，但要小心**“推送后所有客户端同时拉取”的惊群**（抖动 + 缓存 + 限流）。
> - **可靠性**：在线 **ACK + 重试 + TTL**；离线消息存储 + 上线补拉；**去重（msgId）与折叠（collapse）**；**不追求严格有序**（通知类场景）。
> - **治理**：**频控、免打扰、用户偏好、合规授权**与**效果漏斗（下发→到达→展示→点击）**同样重要，否则推送变成骚扰与封号风险。

> [!NOTE] 说明
> 容量数字为用于推演的**假设**。长连接接入层与路由的细节与 [IM 案例](#/design/case-im) 同源，可对照阅读；Netty/长连接参见 [Netty 实战](#/infra/netty-practice)、[TCP 深入：保活](#/cs/net-tcp)。厂商通道的限额、政策与接口随时间变化，**以各厂商官方文档为准**。

## 一、需求与约束

### 1. 推送类型

| 类型 | 例 | 特点 |
| --- | --- | --- |
| **单推（个性化）** | 订单状态、验证码、私信提醒 | 目标明确、延迟敏感、量大（事务通知） |
| **群推/标签推** | 某城市用户、某会员等级、某兴趣人群 | 先**圈选人群**再扇出 |
| **全员广播** | 系统公告、突发新闻、大促开始 | 单次目标亿级，**扇出压力最大** |
| **定时/周期推送** | 每天 9 点日报、课程提醒 | 时间轮/调度（见 [任务调度案例](#/design/case-scheduler)） |
| **事件触发推送** | 价格变动、关注的人开播 | 事件驱动（见 [事件驱动架构](#/design/event-driven)） |
| **站内信/红点** | 消息中心、未读数 | 存储 + 拉取为主 |

### 2. 非功能目标与容量估算（假设）

| 维度 | 假设 |
| --- | --- |
| 用户 | 注册 3 亿，DAU 8000 万，**同时在线长连接 1000 万** |
| 日推送量 | 事务通知 5 亿条/天 + 营销/运营 3 亿条/天 ≈ **8 亿条/天**，平均 9000 条/秒，峰值（整点、活动）**10 万条/秒** |
| 全员广播 | 3 亿设备，在线 1000 万 + 离线 2.9 亿；目标：在线用户 **1 分钟内**送达，离线通过厂商通道 **30 分钟内**完成下发 |
| 延迟 | 事务通知：在线 P99 < 1 秒；营销：分钟级可接受 |
| 接入层 | 单节点 10 万连接 → 1000 万连接 ≈ **100 台**，冗余与多机房约 **150 台** |
| 可靠性 | 事务通知到达率 ≥ 99.9%（在线 + 离线综合）；不重复（用户感知） |

**广播的关键算术**：在线 1000 万用户，如果**逐用户查路由 + 发送**：1000 万次 Redis 查询 + 1000 万次网络发送，仅路由查询按 10 万 QPS 也要 100 秒，且压垮路由存储——所以**必须按接入节点广播**（见下）：广播 1 条消息 → 向 150 个接入节点各发 1 条 → 节点内存里遍历本机 ~7 万连接 → 秒级完成。

## 三、长连接接入层与路由

与 [IM 案例](#/design/case-im) 的接入层同构：

- **连接管理**：鉴权（令牌）→ 注册路由 `user:{uid}:{device} → nodeId`（Redis，随心跳续期，见 [Redis 数据结构](#/redis/types)）→ 心跳保活（应用层 + TCP keepalive，间隔小于 NAT/LB 空闲超时，见 [TCP 深入：保活](#/cs/net-tcp)）→ 断线清理；
- **单机承载**：Netty + epoll，10 万连接/节点，调优 fd/内存/内核参数（见 [Netty 实战](#/infra/netty-practice)、[Linux 排查](#/infra/linux)）；
- **节点优雅下线**：发布/缩容前通知客户端迁移，**分批滚动、客户端退避重连**，防**重连风暴**（见 [发布策略](#/infra/release)）；
- **多终端**：同一用户多设备都在线时，按策略（全部/最近活跃）下发；
- **Web 端**：WebSocket 或 SSE（单向推送足够，自带重连，见 [TCP 深入：WebSocket/SSE](#/cs/net-tcp)），经网关时注意长连接超时与 Upgrade 支持（见 [API 网关案例](#/design/case-gateway)）；
- **连接数保护**：单用户连接数上限、握手限流、按节点水位拒绝新连接（让客户端换节点）。

### 1. 人群解析（群推/标签推）

- 人群条件（城市=深圳 且 会员=黄金 且 30 天活跃）由**用户画像/标签系统**产生；
- **圈选**：用 **Bitmap（RoaringBitmap）**做集合交并差（见 [ClickHouse 行为分析：Bitmap](#/bigdata/ck-analytics)、[工程中的算法](#/cs/algo-engineering)），或在 ClickHouse/ES 里查询用户 ID，**分页导出**为用户列表分片；
- **大人群不要一次性加载进内存**：按 ID 范围分片（如每片 1 万），每个分片是一个独立的扇出子任务，便于并行、限速、断点续跑与失败重试；
- 人群**快照**：任务创建时固定人群版本（防止任务执行期间人群变化导致重复/遗漏）。

### 2. 任务拆分与进度

```text
Task(推送任务)  →  拆成 N 个 Shard(分片：用户ID区间 或 列表片)  →  每个 Shard 是一条队列消息
Shard 执行：取用户 → 过滤(频控/免打扰/黑名单/偏好) → 在线/离线判定 → 分别投递 → 记录进度
进度持久化到 DB：taskId/shardId/状态/已处理游标；Worker 崩溃后从游标恢复（幂等）
```

- **幂等**：`(taskId, userId)` 作为去重键（Redis `SETNX` 或布隆/Bitmap），重试不重复推送；
- **限速**：按任务/按通道/按下游容量令牌桶限速（见 [工程中的算法：限流](#/cs/algo-engineering)）；
- **优先级**：事务通知（验证码、订单）> 运营通知 > 营销广播；**独立队列/独立消费组/独立限额**，营销广播绝不能挤占验证码（舱壁隔离，见 [稳定性工程](#/design/eng-chaos)）；
- **熔断与暂停**：发现异常（投诉激增、通道错误率高）可**一键暂停/撤回任务**；
- **定时推送**：任务到点才进入扇出（时间轮/调度中心触发）；时区与用户本地时间（“早上 9 点”按用户时区拆分任务）。

## 五、消息可靠性与离线

### 1. 在线下发的可靠性

| 机制 | 说明 |
| --- | --- |
| **ACK** | 客户端收到消息后回 ACK（msgId）；服务端在**超时**内未收到则**重推**（指数退避、次数上限） |
| **TTL（有效期）** | 每条消息带过期时间（如验证码 5 分钟、营销 24 小时）；过期不再重试/不再补发——**过期的通知比没有更糟** |
| **去重** | 客户端按 msgId 去重（本地记录最近 N 个）；服务端重试可能造成重复 |
| **顺序** | 通知类**不保证全局有序**；同一业务实体的状态类通知用**版本号/时间戳**让客户端丢弃旧状态 |
| **超时转离线** | 在线推送无 ACK（连接已半死）→ 判定失败，转离线通道，并清理该连接 |

### 2. 离线消息

- **存储**：用户维度的**离线队列**（Redis List/ZSET 或 KV/DB，保留 N 天、每用户最多 M 条，超限丢弃最旧）；
- **上线补拉**：客户端建立连接后上报 `lastMsgId/lastSeq`，服务端返回其后的未读消息（与 IM 的增量拉取同理，见 [IM 案例：拉取模型](#/design/case-im)）；
- **拉取为兜底**：推送（长连接/厂商通道）是“快”，**客户端主动拉取（启动、前台切换、定时）是“可靠”**；
- **厂商通道的不可靠性**：到达率受系统省电策略、权限、厂商限频影响，**不能假设厂商推送必达**，关键消息要有应用内站内信兜底。

### 3. 推送载荷：轻量 + 拉取详情

```json
{ "msgId": "m_8f3a…", "type": "ORDER_SHIPPED", "title": "您的订单已发货", "body": "点击查看物流",
  "bizId": "O20261012000123", "ttl": 86400, "collapseKey": "order:O20261012000123", "ts": 1760250000 }
```

- **payload 不放敏感信息**（金额、手机号、完整内容），避免锁屏泄露与第三方通道留存；
- **内容通过 bizId 拉取**：支持撤回、更新、鉴权（点击后再校验权限）；
- **折叠键（collapse key）**：同一订单的多条状态通知，后者覆盖前者（APNs `apns-collapse-id`、FCM `collapse_key`）；
- **大小限制**：APNs 约 4KB、FCM 约 4KB 级，payload 要精简（以各通道官方限制为准）。

## 六、离线通道网关（APNs / FCM / 厂商通道）

### 1. 通道概览

| 通道 | 场景 | 要点 |
| --- | --- | --- |
| **APNs** | iOS | HTTP/2 长连接，基于 Token（JWT）认证；`apns-priority`（10 立即/5 省电）、`apns-expiration`（TTL）、`apns-collapse-id`；设备令牌失效返回 410 要删除；静默推送有频率限制 |
| **FCM** | 海外 Android（依赖 Google 服务） | HTTP v1 API、优先级（high/normal）、TTL、主题订阅、批量发送 |
| **国内厂商通道** | 华为、小米、OPPO、vivo、荣耀等 | 各自 SDK 与 API；**通知分类（通讯/服务/营销）决定是否限额与展示**，营销类每日有条数限制；需要在 App 里集成各厂商 SDK 并上报 `厂商+token` |
| **统一推送联盟 / 聚合 SDK** | 简化多厂商接入 | 仍受各厂商政策约束 |
| **短信 / 邮件** | 验证码、重要通知兜底 | 成本高、需模板与签名备案；合规严格 |

> [!NOTE] 以官方为准
> 各通道的限额、分类规则、接口、证书/Token 有效期等随政策频繁变化，实现与上线前务必对照最新官方文档。

### 2. 网关设计要点

- **设备令牌管理**：`user → [ {deviceId, platform, vendor, token, appVersion, lastActive, 授权状态} ]`；**令牌会变更/失效**（卸载、重装、过期）：收到通道的“无效令牌”回执要**立即清理**，否则浪费配额并可能被限流；
- **按通道隔离**：每个通道独立的连接池、线程池、限流与熔断（**舱壁**），一个厂商抖动不影响其他；
- **限速与批量**：遵守各通道速率限制，**令牌桶限速**；支持批量接口的用批量；HTTP/2 多路复用提升吞吐；
- **重试与退避**：对可重试错误（超时、503、限流）指数退避重试；对不可重试错误（令牌无效、payload 非法）不重试并记录；
- **优先级与 TTL 映射**：把平台的优先级与过期时间映射到各通道参数；
- **多通道策略**：同一设备只选**一个最佳通道**（如华为设备优先华为通道，失败再 FCM/自有长连接），避免重复弹窗；
- **回执与错误码**：统一抽象为内部状态（已提交通道/通道已受理/失败原因），不同通道回执能力差异大（很多只有“已受理”而没有“已展示”）。

## 七、频控、免打扰与合规

| 机制 | 做法 |
| --- | --- |
| **频控（Frequency Capping）** | 按用户/类别限制单位时间推送条数（营销类每日 ≤ 2 条、每周 ≤ N 条）；用 Redis 计数器（`INCR` + 过期）或滑动窗口（见 [工程中的算法：限流](#/cs/algo-engineering)）；**事务类通知不受营销频控限制**；扇出过滤阶段检查 |
| **免打扰/勿扰时段** | 用户设置（夜间 22:00~8:00）；营销类遵守，紧急类（安全告警）可穿透；按**用户本地时区**；被拦截的可延后到次日发送 |
| **用户偏好/订阅** | 按类别开关（订单通知、活动通知、私信…）；用户退订必须立即生效；系统通知权限关闭则不发 |
| **合规** | 营销推送需**用户同意**，提供**退订**方式，遵守个人信息保护与广告相关法规及各应用商店/厂商规则，**以适用法规为准**；内容审核（模板审核、敏感词）；保留发送记录用于审计 |
| **防滥用（发送方）** | 业务方接入需**认证 + 配额 + 模板审批**；单业务方限流；审计日志；防止被攻破的业务账号群发垃圾推送 |
| **去重与折叠** | 同一事件多次触发只发一次（业务幂等键）；同类通知合并 |

**频控的权衡**：过度推送导致用户关闭通知权限甚至卸载（不可逆），**触达效果的长期价值高于单次点击率**——频控阈值应通过 A/B 实验与长期留存指标确定。

## 八、洪峰与惊群

### 1. 突发推送洪峰

整点活动、突发新闻、秒杀开始会同时触发海量推送：

- **削峰**：任务进 Kafka，扇出 Worker 按容量消费；营销类限速平滑；
- **分级与降级**：容量不足时**先保事务通知，延后/丢弃营销广播**；
- **预扩容**：已知大促提前扩容接入层与 Worker（见 [压测与容量规划](#/design/eng-loadtest)）；
- **客户端打散**：定时类提示可在客户端加随机抖动（见下）。

### 2. 推送后的“点击惊群”

一条广播推送到达后，**大量用户几乎同时点开**，同时请求同一个接口/页面（活动页、详情接口），造成对后端的瞬时冲击：

| 对策 | 说明 |
| --- | --- |
| **推送分批错峰** | 全员广播不要同一秒发完：按时间窗口分批（如 10 分钟内匀速），把点击流量摊平 |
| **客户端随机延迟拉取** | 收到“有新内容”的推送后，客户端随机延迟 0~N 秒再拉取（抖动） |
| **接口缓存/静态化** | 活动页、详情接口预热并缓存、CDN 化；推送里携带的内容 ID 对应资源提前准备好 |
| **限流与降级** | 活动接口限流、排队、降级（见 [限流、熔断与降级](#/distributed/governance)、[秒杀系统](#/design/seckill)） |
| **预热** | 推送前预热缓存、扩容服务 |
| **合并推送** | 推送内容本身尽量自包含（轻量展示），减少“必须再请求”的比例 |

## 九、触达统计与效果评估

### 1. 漏斗

```text
任务目标人群数
 → 平台下发数（扇出处理，过滤频控/免打扰/无令牌后的实际发送）
 → 通道受理数（长连接 ACK / 厂商接受）
 → 到达数（客户端回执，部分通道无法获得）
 → 展示数（通知栏展示，需客户端上报）
 → 点击数 → 转化数（下单/阅读）
```

- 各环节的**转化率与流失原因**（过滤原因分布、令牌无效、通道错误码）是排障与优化依据；
- **回执采集**：自有长连接用 ACK；厂商通道多数只有“受理”，到达/展示靠**客户端 SDK 上报**（设备省电策略下可能不上报，需统计口径说明）；
- **归因**：点击带 `msgId/taskId` 参数，业务侧按其归因转化；
- 数据流：回执/点击事件 → Kafka → Flink/ClickHouse 聚合（见 [ClickHouse 行为分析](#/bigdata/ck-analytics)），实时看板 + 任务复盘。

### 2. 优化方向

- **到达率**：令牌质量治理、通道选择（按设备厂商最优通道）、多通道兜底、App 引导用户开启通知权限与关闭电池优化（保活/白名单，合规前提）；
- **点击率**：个性化内容与时机（用户活跃时段推送）、文案/图标 A/B、折叠与频控避免疲劳；
- **长期指标**：关闭通知率、卸载率、留存——**不能只看点击率**。

## 十、可用性、监控与安全

### 1. 高可用

| 风险 | 对策 |
| --- | --- |
| 接入节点宕机 | 客户端重连到其他节点；路由 TTL 清理；未 ACK 消息重推或转离线 |
| Redis（路由/频控）故障 | 路由降级：全部按“离线/厂商通道”处理或本地缓存路由；频控降级为宽松或本地计数；见 [稳定性工程](#/design/eng-chaos) |
| 厂商通道故障/限流 | 通道级熔断，退避重试，切换备用通道，积压队列；事务类优先 |
| Kafka/队列积压 | 扩容消费者；营销任务暂停；按优先级调度 |
| 扇出 Worker 崩溃 | 分片进度持久化，重启后续跑（幂等） |
| 误发/错发 | **审批 + 灰度（先发 1% / 内部用户）+ 一键暂停/撤回**（长连接可撤回未展示的，厂商通道通常无法撤回）；高风险任务二次确认 |
| 机房故障 | 多机房接入，用户就近；路由与离线存储跨机房复制 |

### 2. 监控

| 指标 | 说明 |
| --- | --- |
| 在线连接数、建连/断连速率、重连风暴 | 接入层健康（见 [指标监控](#/infra/obs-metrics)） |
| 各优先级队列积压与扇出速率 | 洪峰与容量 |
| 在线下发延迟 P99、ACK 率、重试率 | 实时性与可靠性 |
| 各通道：提交成功率、错误码分布、限流次数、令牌失效比例 | 通道健康 |
| 触达漏斗转化、关闭通知率、投诉数 | 业务与合规 |
| 频控拦截数、免打扰拦截数 | 治理效果 |

### 3. 安全

- **连接鉴权**：令牌校验、绑定设备；防伪造连接；
- **发送鉴权与审计**：业务方 AppKey + 签名（见 [加密与签名](#/security/crypto)）、配额、操作审计；
- **内容安全**：模板审核、敏感词；防钓鱼内容；
- **数据保护**：设备令牌、用户标识脱敏存储；payload 不放敏感信息；TLS 传输；
- **防滥用**：对接入层做握手限流、单 IP 连接数限制、异常行为检测（见 [Web 安全](#/security/web)）。

## 十一、取舍总结

| 取舍 | 选择 | 代价 |
| --- | --- | --- |
| 自建长连接 vs 全部依赖厂商通道 | 在线长连接 + 离线厂商通道 | 长连接维护成本；厂商通道不可控 |
| 逐用户发送 vs 按节点广播 | 全员广播按节点；定向推送按路由 | 广播实现与节点内遍历的复杂度 |
| 推 payload 全文 vs 轻量 + 拉取 | 轻量 + 拉取 | 多一次请求，要防惊群 |
| 严格有序 vs 无序 + 版本号 | 通知类不保序 | 客户端需处理旧状态 |
| 高到达 vs 低打扰 | 频控与偏好优先，事务类例外 | 营销触达量下降，换长期留存 |
| 强一致统计 vs 近似统计 | 最终一致漏斗 | 展示/到达口径有缺口 |
| 撤回能力 vs 通道特性 | 长连接可撤回，厂商通道不可撤回 | 上线前审批与灰度更重要 |

## 十二、常见坑

| 坑 | 对策 |
| --- | --- |
| 全员广播逐用户查路由发送，压垮 Redis 和接入层 | 按接入节点广播，节点本地遍历；离线按设备分片 |
| 营销广播挤占验证码/订单通知 | 多优先级队列 + 独立限额与消费组（舱壁） |
| 推送后全员同时点击打爆接口 | 分批错峰、客户端抖动、接口缓存预热、限流降级 |
| 设备令牌失效不清理，浪费配额被限流 | 处理无效令牌回执，定期清理 |
| 假设厂商推送必达 | 站内信 + 上线补拉兜底，关键消息多通道 |
| 同一设备多通道重复弹窗 | 单设备选单通道；msgId 去重；collapse 键 |
| 推送载荷含敏感信息 | 轻量 payload + 点击后拉取并鉴权 |
| 离线消息无 TTL，用户几天后收到过期通知 | 每条消息带 TTL，过期丢弃 |
| 重连风暴（发布或故障后全部连接同时重连） | 客户端退避抖动、服务端握手限流、分批滚动发布 |
| 时区/勿扰处理不当，半夜骚扰用户 | 按用户本地时区与勿扰设置过滤，延后发送 |
| 误发大范围推送无法撤回 | 审批、小流量灰度、内部预发、一键暂停；理解通道撤回能力 |
| 只看点击率，忽略关闭通知与卸载 | 长期指标与护栏指标，频控 A/B |
| 任务无幂等，重试导致重复推送 | `(taskId, userId)` 去重，分片进度持久化 |
| 厂商限额/政策变化未跟进 | 持续对照官方文档，监控通道错误码 |

## 面试追问

> [!QUESTION] 推送系统和 IM 有什么区别？
> IM 是双向、会话内有序、强调消息不丢不重不乱序和多端同步；推送以系统或运营向用户的单向通知为主，扇出规模可达亿级，对顺序要求弱，更强调到达率、多通道触达、频控免打扰、合规和效果统计，并且离线触达依赖厂商通道。两者的长连接接入层和路由设计相似。

> [!QUESTION] 全员广播给上亿用户怎么设计？
> 不能逐用户查路由发送。在线用户把消息按接入节点广播，每个节点在本机遍历连接并分批下发，成本与节点数相关，秒级完成；离线用户按设备令牌分片放入离线任务队列，由通道网关按各通道限速批量发送。任务拆成可持久化进度的分片，用 taskId 加 userId 去重，并设置优先级、限速和一键暂停。

> [!QUESTION] 在线用户和离线用户分别怎么推送？如何保证可靠？
> 在线走自有长连接，客户端 ACK，超时未 ACK 重试，最终转离线；离线走 APNs、FCM 和各厂商通道唤醒，同时保存离线消息，用户上线后按 lastMsgId 增量补拉。每条消息带 TTL 和去重 ID，通知不保证有序。厂商通道不保证必达，关键消息要有站内信和补拉兜底。

> [!QUESTION] 推送后用户集中点击造成后端压力怎么办？
> 广播分批匀速发送摊平点击，客户端收到后随机延迟再拉取，被引用的接口和页面提前预热缓存并 CDN 化，接口做限流和降级，推送内容尽量自包含，减少必须再请求的比例。

> [!QUESTION] 如何做频控和免打扰？
> 在扇出过滤阶段按用户和消息类别检查：营销类用 Redis 计数器或滑动窗口限制单位时间条数，事务类不受限；用户设置的勿扰时段按本地时区拦截并延后，紧急类可穿透；按类别订阅开关和系统通知权限也在此过滤；频控阈值用 A/B 实验结合长期留存和关闭通知率确定。

> [!QUESTION] 厂商推送通道有哪些坑？
> 设备令牌会失效需要及时清理；各通道有速率限制，国内厂商还按通知分类限制营销条数；回执能力差，多数只有受理没有展示；到达率受系统省电策略影响；不同通道参数和政策差异大且经常变化。要按通道做舱壁隔离、限速、退避重试和熔断，单设备选单通道并用多通道兜底。

> [!QUESTION] 如何衡量推送效果？
> 建立下发、通道受理、到达、展示、点击、转化的漏斗，分析各环节流失原因，如过滤原因、无效令牌和通道错误；点击带任务和消息标识用于归因转化；同时关注关闭通知率、卸载率和留存等长期护栏指标，而不是只看点击率。
