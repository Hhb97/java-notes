# 案例：LBS 附近的人与打车派单设计详解

> [!ABSTRACT] 核心要点
> - LBS 的本质是**“空间 + 时间”的高频写、实时读问题**：大量对象（用户、司机、商家）**每几秒更新一次位置**（写远多于读），查询要求**“某点附近 N 米内/最近的 K 个”**在**毫秒到几十毫秒**返回。关键技术是**空间索引**：把二维坐标映射成**可索引、可分片的一维键**。
> - **空间索引选型**：**Geohash**（字符串前缀，简单，Redis GEO 采用，边界需查 9 个邻格）；**S2/H3**（球面/六边形层级网格，覆盖计算精确、邻居距离均匀，大厂常用）；**四叉树/R-树**（树形，适合内存索引与范围查询）。**核心套路：圈出覆盖查询范围的若干单元格 → 取候选 → 用精确距离过滤 → 排序截断。**
> - **“只存最新位置”是第一原则**：位置是**覆盖型高频更新**，历史轨迹另走时序/日志管道；在线状态用 **TTL** 表达（超过 N 秒未上报视为离线）；写入要**批量、限频、自适应**，不要每次移动都写库。
> - **打车派单不是“找最近的司机”**：要用**路网 ETA（而非直线距离）**、**司机状态与方向**、**服务分/偏好**，并且从“**逐单贪心**”演进到“**时间窗内批量二分图匹配**（全局最优，提高整体效率）”；还要处理**应答超时重派、司机同一时刻只被派一单（并发控制）、取消与改派**。
> - **扩展靠“按空间分片”**：按**城市/网格**切分，**一个网格由一个调度单元（单线程/Actor）处理**，避免跨节点争用；**热点区域（机场、商圈、演唱会）** 要细分网格或动态拆分，并限制候选数。
> - **隐私与合规**是必修课：位置是敏感个人信息，需要**最小化采集、模糊化展示、可关闭、脱敏存储、访问审计**。

## 1. 背景、范围与指标

### 场景

| 场景 | 描述 | 特点 |
| --- | --- | --- |
| **附近的人/商家/门店** | 社交、本地生活、外卖商家发现 | 读多，位置更新频率较低（用户打开 App 时），要求排序与过滤丰富 |
| **打车/外卖配送派单** | 乘客下单 → 匹配附近司机/骑手 → 接单 → 行程 | **司机位置高频上报**、强实时、强状态一致，匹配质量决定平台效率 |
| **地理围栏** | 进入/离开某区域触发事件（到店提醒、电子围栏、风控） | 点与多边形关系的高效判断 |
| **轨迹与里程** | 行程轨迹记录、里程计价、回放 | 海量时序点，存储与压缩 |

### 规模与指标（示例，需按业务校准）

| 指标 | 示例量级 | 说明 |
| --- | --- | --- |
| 在线司机/骑手数 | 百万级（全国同时在线） | 单城可达几十万 |
| 位置上报频率 | 每 3~5 秒 / 次 | **写 QPS = 在线数 / 上报间隔**：100 万 / 4 秒 ≈ **25 万 QPS** |
| 附近查询 QPS | 数万~十万 | 乘客打开地图、下单时的周边司机展示 |
| 查询延迟 | P99 < 50~100ms | 地图上“周围车辆”刷新要流畅 |
| 派单决策延迟 | 秒级（含应答等待） | 内部计算毫秒~百毫秒 |
| 定位精度 | 米级 | 受 GPS/基站/WiFi、地图匹配影响 |
| 可用性 | 99.95%+ | 派单是营收核心链路 |

**写远大于读**，且写是**覆盖写**（只关心最新），这决定了存储与索引设计的方向。

## 2. 关键设计决策（ADR 摘要）

| 决策 | 选择 | 理由 | 代价 |
| --- | --- | --- | --- |
| **空间索引** | 大规模/精度要求高：**S2 或 H3 网格**；中小规模/快速落地：**Geohash（Redis GEO）** | 网格化后可按单元格分片、聚合与并行；邻接与覆盖计算成熟 | 需要覆盖算法与邻格处理；边界附近需查多个格子 |
| **位置存储** | **内存索引（按网格分片）为主**，Redis 或自研服务；历史轨迹异步入时序库/数据湖 | 写 QPS 极高且只关心最新值，内存最合适 | 内存成本；故障恢复靠司机重新上报（秒级自愈） |
| **位置更新协议** | **长连接（TCP/MQTT/WebSocket）+ 批量上报 + 自适应频率** | 减少连接与握手开销，可下发控制指令 | 长连接网关的运维，见 [案例：实时消息推送系统](#/design/case-push)、[MQTT 协议详解](#/iot/mqtt) |
| **距离度量** | **粗筛直线距离，精排路网 ETA** | 直线近 ≠ 实际近（河流、单行线、高架） | ETA 计算成本高，只对少量候选算 |
| **派单策略** | **时间窗批量匹配（全局最优）+ 逐单贪心兜底** | 批量匹配提升整体接驾效率与成交 | 增加几百毫秒~数秒等待；实现复杂 |
| **并发控制** | **司机状态机 + 原子占用（CAS/单线程 Actor）** | 防止一个司机同时被派多单 | 需要网格内串行化或分布式锁 |
| **分片维度** | **按城市 → 网格**；热点网格动态细分 | 数据局部性好，调度单元可单线程化 | 跨边界匹配需要处理邻格 |

## 4. 空间索引

### 要解决的问题

给定点 `(lat, lng)` 与半径 `r`，**从百万个点里快速找出范围内的点**。逐个算距离是 O(N)，不可行。空间索引的做法：**把二维空间划分成层级化的单元格，每个点属于某个单元格；查询时只取覆盖查询范围的单元格里的点**。

### 空间索引方案对比

| 方案 | 原理 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| **Geohash** | 经纬度二分编码成字符串，前缀 = 区域 | 简单；可存入任何支持字符串/范围的存储（Redis、DB、ES）；前缀分片天然 | 矩形网格形变；边界需查邻格；邻居距离不均 | 中小规模、快速落地 |
| **S2（Google）** | 球面立方体投影 + 希尔伯特曲线，64 位 CellID，层级 0~30 | **精确球面几何**；任意区域（圆/多边形）**覆盖（Region Cover）**；Cell ID 可范围查询 | 概念较复杂，库较重 | 大规模、需要多边形/围栏、全球 |
| **H3（Uber）** | 六边形层级网格（16 个分辨率） | **邻居距离均匀**（六边形等距），聚合（热力图、供需）与 k 环扩散方便 | 层级不严格嵌套（子格不完全落入父格）；六边形实现 | 供需热力、派单、运营分析 |
| **四叉树/KD 树（内存）** | 递归四分空间，叶子存点 | 内存中查询快，**自适应密度**（密集区更深）；可做 KNN | 动态更新（频繁移动）需要维护；分布式分片麻烦 | 单机内存索引、中小数据 |
| **R-树/R*-树** | 以矩形包围盒组织 | 适合**线/面等有范围的对象**（POI、道路、围栏），数据库空间索引（PostGIS） | 点高频更新性能一般 | 静态/低频更新的地理对象 |
| **PostGIS / 数据库空间索引** | GiST/R-tree | SQL 能力强，复杂空间运算 | 高频位置更新与高 QPS 不适合 | 低频、复杂查询、数据分析 |
| **ES geo 查询** | BKD 树等 | 与搜索结合（文本 + 位置）方便 | 高频更新代价大 | 商家/POI 搜索，见 [案例：搜索系统设计详解](#/design/case-search) |

**选型建议**：

- **“附近的人/司机”（动态点、高频更新）**：内存网格索引（Geohash/S2/H3 网格 + HashMap/Redis），**不要用关系库空间索引承受高频写**；
- **“附近的商家/POI”（静态点、可文本搜索）**：ES/PostGIS，位置变化少；
- **围栏/区域运营**：S2/H3 覆盖 + 倒排；
- **热力与供需统计**：H3 网格聚合最方便。

### Redis GEO 的用法与限制

```java
// 位置更新（覆盖写）：成员是司机 ID，分值内含 geohash
redis.opsForGeo().add("drivers:city:110100", new Point(lng, lat), "driver:" + driverId);
// 附近查询：半径 2km 内，按距离升序，取 20 个，带距离
GeoResults<GeoLocation<String>> r = redis.opsForGeo().search("drivers:city:110100",
        GeoReference.fromCoordinate(lng, lat),
        new Distance(2, Metrics.KILOMETERS),
        RedisGeoCommands.GeoSearchCommandArgs.newGeoSearchArgs().includeDistance().sortAscending().limit(20));
```

| 注意点 | 说明 |
| --- | --- |
| **没有每个成员的 TTL** | GEO 底层是 ZSET，不能给成员单独过期；需要**离线清理**：另维护 `last_seen` ZSET，定时 `ZREMRANGEBYSCORE` 删除过期司机，或用“按时间分桶的多个 key + key 过期” |
| **单 key 过大** | 一个城市几十万司机的 ZSET 是**大 key**，查询/写入集中在单节点；按**城市 + 网格前缀**拆成多个 key，分散到多个分片，见 [Redis 大 key 与热 key 治理](#/redis/bigkey) |
| **只能按距离查，复杂过滤受限** | 司机状态（空闲/忙）、车型、评分等过滤要在应用层或用独立索引；通常为**不同状态/车型建不同 key** 或把状态存在 Hash 里二次过滤 |
| **写 QPS 上限** | 单节点数万~十万级；超出需分片 |
| **精度** | Geohash 52 位精度足够米级；距离是球面公式近似，误差可接受 |

## 5. 位置上报与更新

### 上报策略

| 策略 | 说明 |
| --- | --- |
| **自适应频率** | 行驶中 3~5 秒；停车/静止时降到 30~60 秒；接单/行程中更高频（轨迹需要）；弱网/后台降频以省电 |
| **客户端去噪与过滤** | 丢弃精度差/漂移点、速度异常点；位移小于阈值不上报 |
| **批量上报** | 客户端缓存若干点，一次上传（带时间戳），减少请求数；服务端取**最新点**更新索引，其余进轨迹 |
| **压缩与精简协议** | 经纬度用整数/差分编码，Protobuf 二进制，减少流量 |
| **长连接** | 与 [案例：实时消息推送系统](#/design/case-push) 复用长连接通道：上行位置、下行派单/指令 |
| **补传** | 弱网期间缓存，恢复后补传轨迹（带时间戳），索引只用最新点，避免旧点覆盖新点（比较时间戳） |

### 服务端处理

- **只存最新位置（覆盖写）**，附上**时间戳与版本**（防止乱序旧点覆盖新点）；
- **在线状态**：`last_seen` 超过阈值（如 10~15 秒无上报）判定离线，从索引移除或标记；
- **分片路由**：按**网格/城市**哈希路由到位置服务节点，**同一司机跨格移动**时需要从旧格移除、加入新格（先加后删，保证不丢）；
- **写入合并**：同一司机短时间多次更新在内存中合并，批量刷新到 Redis（降低写放大）；
- **轨迹分流**：位置点同时发往 MQ（Kafka），异步写时序库/数据湖用于里程、回放、分析，见 [Kafka 架构与存储](#/mw/kafka)、[InfluxDB 数据模型](#/db/influx-model)；
- **限流与防刷**：每设备上报频率上限；防伪造（见风控）。

### 容灾与自愈

位置数据**可重建**：位置服务节点宕机/重启后，内存索引丢失，但**司机几秒内会重新上报**，索引自动恢复——**无需强持久化**，只需保证**快速恢复路由**。这极大简化了可靠性设计，但需要：

- 重启后的**冷启动保护**（索引未恢复期间，查询降级、派单谨慎）；
- 分片节点故障时，**网格路由切换到备节点**（一致性哈希/路由表），备节点同样由上报重新填充；
- 关键状态（**司机是否在服务中、订单绑定关系**）**不放在位置索引里**，而是在**订单/司机状态服务**（有持久化与强一致）。

## 6. 附近的人查询

### 查询流程

1. **计算覆盖网格**：根据 `(lat,lng, r)` 取中心格及邻格（Geohash 9 宫格 / S2 `RegionCoverer` / H3 `gridDisk(k)`）；
2. **并行拉取候选**：从各网格分片取候选点（限制每格上限，防止热点格爆量）；
3. **精确距离过滤**：用球面距离（Haversine）计算真实距离，过滤超出半径的；
4. **业务过滤**：状态（在线/空闲）、性别/年龄/车型等条件、黑名单、可见性；
5. **排序**：距离/活跃度/综合分；
6. **分页/截断**：取前 K；**游标分页**用（距离, ID）作排序键，见 [API 设计与演进](#/design/arch-api)；
7. **返回**：距离做**模糊化**（隐私），不返回精确坐标。

### 热点与候选爆炸

- **商圈/机场/景区**：一个网格里候选几万，逐个过滤太慢——**更细的网格 / 动态四分**（超过阈值自动拆分为更细子格）、每格内按**活跃度/距离分层**、**限制候选数量上限**；
- **半径过大**：多级覆盖（粗格 + 细格），或先在粗粒度找到有人的格子，再下钻；
- **缓存**：对热门位置（同一小区重复查询）做**短 TTL 结果缓存**（几秒），减少重复计算，注意缓存 key 用网格而非精确坐标；
- **预计算**：对商家类静态 POI，预计算每个网格的 POI 列表与排序。

### 隐私保护

位置属于**敏感个人信息**（合规要求如个人信息保护法、GDPR）：

| 措施 | 说明 |
| --- | --- |
| **最小化采集与明示授权** | 仅在需要时采集；前台/后台权限分级；用户可随时关闭 |
| **模糊化展示** | 距离展示为“500m 内/1km”，**不返回精确坐标**；对头部用户对网格中心**加随机噪声（差分隐私思想）** |
| **防三角定位攻击** | 恶意用户在多个位置发起查询，用距离反推目标位置；对距离精度分档、限制查询频率与位置变化速度、检测异常移动 |
| **存储脱敏与保留期** | 轨迹数据加密、最小保留期、访问审计；删除请求可执行 |
| **“隐身/幽灵模式”** | 用户可选择不被他人发现 |
| **内部访问管控** | 运营/客服查看位置需要审批与日志 |

## 7. 打车派单

### 7.1 候选筛选

下单后，**不是简单找“最近的”司机**：

| 维度 | 说明 |
| --- | --- |
| **空间候选** | 以乘客上车点为中心，逐步扩大半径（1km → 2km → 3km），用网格覆盖取候选 |
| **状态** | 空闲/接单中（可接顺路单）/在服务中；**在线新鲜度**（最近上报时间）；已被派单未应答的排除 |
| **车型与服务能力** | 车型、车牌城市、订单类型（专车/快车/顺风车）、特殊需求（儿童座椅） |
| **司机偏好与限制** | 听单方向/目的地偏好、禁行区域、接单距离上限 |
| **ETA（接驾时间）** | **用路网 ETA 而非直线距离**：对粗筛后的 Top 几十个候选调用路径服务计算（批量接口），得到真实接驾耗时与距离 |
| **方向/朝向** | 司机行驶方向与上车点相对关系（避免掉头成本），可作为 ETA 修正 |
| **服务质量分** | 评分、应答率、取消率、投诉；影响排序或在 ETA 近似时作为 tie-breaker |
| **风控** | 异常司机/刷单设备排除，见风控章节 |

### 7.3 派单状态机与并发控制

关键约束：**一个司机在同一时刻只能被派给一个订单（或者按规则可拼单）**，**一个订单只能被一个司机接走**。并发场景：多个订单同时选中同一司机；司机应答与订单取消同时发生；重派与应答竞态。

```text
订单状态：CREATED → DISPATCHING → ASSIGNED（已派单，待应答）→ ACCEPTED → PICKUP → IN_TRIP → COMPLETED
                                      │  ↘ 超时/拒绝 → 回到 DISPATCHING（重派，排除该司机）
                                      └ 乘客取消 → CANCELLED
司机状态：IDLE → OFFERED（已收到派单，锁定）→ ACCEPTED/BUSY → …；OFFERED 超时回 IDLE
```

| 并发问题 | 手段 |
| --- | --- |
| **司机被重复派单** | 派单时对司机状态做**原子占用**（`IDLE → OFFERED`，Redis Lua/CAS/数据库条件更新）；占用失败则换下一个候选；占用带 **TTL（应答超时）** 自动释放 |
| **订单被重复接单** | 司机应答时对订单做条件更新 `status=ASSIGNED AND driver=自己 → ACCEPTED`；其他请求失败 |
| **应答与取消竞态** | 订单状态机 + 乐观锁/版本号，状态不允许的转移直接拒绝，返回明确提示 |
| **重派与迟到的应答** | 重派后旧司机的迟到应答要被拒绝（订单已分配给别人）；**派单带 offer_id/版本**，应答携带 offer_id 校验 |
| **调度单元内串行化** | 把一个区域的所有订单与司机操作路由到**同一个单线程调度单元（Actor/分区队列）**，天然避免竞态，大量减少分布式锁；跨单元仅在边界处协调 |
| **幂等** | 派单、应答、取消接口幂等，见 [幂等设计与重试](#/distributed/idempotent) |
| **状态一致与恢复** | 状态以订单/司机服务（持久化）为准；调度单元崩溃后从状态存储恢复进行中的订单；对账兜底 |

### 7.4 应答超时与重派

- 司机应答窗口（如 10~15 秒）；超时/拒绝则**标记该司机对此订单已尝试**，立即选下一个候选重派；
- 设置**最大重派次数/总时长**，超过则扩大半径、提高价格（动态加价）、或通知乘客“暂无司机”；
- 司机端的**推送必须可靠到达**（长连接 + 离线推送兜底），且**展示倒计时**；见 [案例：实时消息推送系统设计详解](#/design/case-push)；
- **并行派单（多司机同时收到、先应答者得）** 提高成交率，但要处理“多个司机同时应答”的竞态（订单条件更新只允许一个成功）与司机体验（抢不到的提示）。

### 7.5 供需、定价与运营

- **热力图/供需计算**：按 **H3 网格**聚合“订单需求量 vs 空闲司机数”，每几十秒更新；
- **动态定价**：需求远大于供给的网格上浮价格，引导司机前往并抑制需求，见 [案例：订单、支付与对账系统设计详解](#/design/case-payment) 的计价；
- **调度/预测**：预测未来供需，向司机推送热点区域引导；
- **公平与体验**：避免长期被“绕开”的司机、乘客长时间等待；
- **拼车/顺风车/多点配送**：更复杂的路径规划（VRP 车辆路径问题），常用启发式/近似算法。

## 8. 分片、扩展与热点

### 分片策略

| 层面 | 做法 |
| --- | --- |
| **位置服务** | 按**城市 → 网格**哈希分片；每片维护若干网格的内存索引；热点城市多片 |
| **调度服务** | **按城市/区域分片**，一个区域一个调度单元（单线程 Actor）；区域边界通过邻格共享候选 |
| **订单/状态服务** | 按订单 ID/用户 ID 分片，持久化数据库，见 [分片、一致性哈希与再平衡](#/distributed/partitioning) |
| **轨迹存储** | 按时间 + 设备分片的时序/列式存储 |
| **城市级隔离（单元化）** | 一个城市故障不影响其他城市，类似单元化思想，见 [异地多活与单元化架构](#/design/arch-multi-active) |

### 热点区域与跨边界

- **动态网格**：密度高的区域自动细分网格（四叉树式自适应），低密度区域合并；
- **边界问题**：位于分片边界的订单需要同时查看邻近分片的司机——通过**网格重叠/邻格读取**，而派单决策只在“订单所属调度单元”内完成；
- **大事件（演唱会散场、机场、节假日）**：流量突增，预先扩容、**限流排队**、候选上限、降级为简单匹配，见 [高可用架构设计](#/design/arch-availability)；
- **热点司机/热点订单**：避免同一优质司机被大量订单同时竞争（占用机制已解决正确性，但要控制无效竞争的开销）。

## 9. 地理围栏与轨迹

### 地理围栏

围栏 = 多边形/圆形区域（机场、商圈、禁行区、配送范围）。**判断点是否在围栏内**：

- **点在多边形内**：射线法/回转数算法，O(顶点数)；
- **加速**：对围栏做**空间索引（R-树，或 S2/H3 覆盖建倒排）**：先用网格找到可能包含该点的少数围栏，再精确判断；
- **事件**：位置流经过围栏服务，比较上一次与本次是否在内，产生 **进入/离开** 事件（带抖动抑制：连续 N 次确认或加迟滞缓冲，避免边界来回触发）；
- **围栏变更**：增量更新索引，版本化；
- 场景：到达提醒、进出风控、区域计价、禁行提示、配送范围判断。

### 轨迹处理

| 问题 | 处理 |
| --- | --- |
| **GPS 漂移/噪声** | 滤波（卡尔曼/滑动窗口）、异常点过滤（速度/加速度阈值） |
| **地图匹配（Map Matching）** | 把离散点吸附到道路上（HMM 等算法），得到合理的行驶路径与里程 |
| **轨迹压缩** | Douglas-Peucker 等算法按误差阈值简化点序列，节省存储与传输 |
| **里程计价** | 基于地图匹配的路径里程，结合 GPS 里程校验，防止作弊；弱信号路段补偿 |
| **存储** | 时序库/列式存储，按设备+时间分区，冷数据压缩归档，见 [InfluxDB 数据模型](#/db/influx-model) |
| **回放与分析** | 行程回放、异常行为（绕路、偏航）、运营分析 |

## 10. 可靠性、容量与监控

### 容量估算（示例）

```text
在线司机 100 万，上报间隔 4 秒 → 位置写 QPS ≈ 25 万
单条位置消息（含元数据）~ 100 字节 → 入口带宽 ≈ 25 万 × 100B ≈ 25 MB/s（~200 Mbps），可批量压缩降低
内存索引：每个司机 ~200 字节（ID、坐标、状态、时间）→ 100 万 ≈ 200 MB（单副本），分片后很小；热点与副本 ×3 仍很小
结论：瓶颈在写 QPS 与网络连接数（长连接数 100 万+），而不是内存
附近查询：10 万 QPS，每次扫描 9 个网格各取 ≤ 100 候选 → 约 900 次距离计算，CPU 可控
（以上为推演用数量级，按真实业务与压测校准，见 [压测与容量规划]）
```

### 可靠性要点

| 风险 | 对策 |
| --- | --- |
| **位置服务节点故障** | 路由切换到备节点；司机持续上报自动恢复索引；冷启动期降级 |
| **推送丢失导致派单无响应** | 长连接 + 离线通道兜底、应答超时重派、司机端状态同步（重连后拉取当前订单） |
| **订单与司机状态不一致** | 以持久化状态服务为准，定期对账（司机在服务但无订单、订单已分配但司机离线），见 [数据一致性实战](#/distributed/consistency-practice) |
| **时钟与乱序** | 位置带设备时间与服务端接收时间；只接受时间更新的点，见 [分布式时钟](#/distributed/clock) |
| **突发流量/大事件** | 弹性扩容 + 限流 + 降级（缩小候选、放宽匹配窗口）；提前预热 |
| **下游 ETA/地图服务慢** | 超时降级为直线距离估算；缓存热门路径；熔断，见 [熔断限流实战](#/spring/cloud-resilience) |
| **反作弊/虚假定位** | 风控（模拟定位检测、设备指纹、异常速度/跳点）、数据校验、司机端环境检测 |

### 监控指标

| 层 | 指标 |
| --- | --- |
| **位置链路** | 上报成功率与延迟、在线数、位置新鲜度分布（过期比例）、各分片写 QPS 与倾斜、长连接数 |
| **查询** | 附近查询 QPS/P99、候选数分布、热点网格 TopN |
| **派单** | **派单成功率、平均接驾时间（ETA/实际）、应答率、超时率、重派次数、订单等待时长、取消率** |
| **匹配质量** | 总接驾里程/时间（批量 vs 贪心对比 A/B）、空驶率 |
| **供需** | 各网格供需比、动态加价覆盖率 |
| **稳定性** | 错误率、依赖（ETA/推送）延迟、状态不一致对账差异 |
| **隐私与安全** | 异常查询（三角定位）、越权访问日志 |

策略迭代要有 **A/B 实验**（对比匹配策略、窗口长度、ETA 模型），指标看整体效率与用户体验，而不是只看单一指标。

## 11. 取舍与复盘清单

- [ ] 是否明确**写远多于读、只存最新位置**，位置数据可由上报重建而无需强持久化？
- [ ] 空间索引是否匹配规模与场景（动态点用网格内存索引，静态 POI 用 ES/PostGIS）？格子大小与查询半径匹配？是否处理了边界邻格？
- [ ] 位置是否**按城市/网格分片**，热点网格是否可动态细分，单 key/单节点是否会成为大 key 与热点？
- [ ] 距离是否**粗筛直线 + 精排路网 ETA**，ETA 服务故障是否有降级？
- [ ] 派单是否考虑**批量匹配**，窗口是否可自适应，并有逐单贪心兜底？
- [ ] **司机与订单状态是否原子占用**，应答超时、取消、重派、迟到应答是否都有处理？
- [ ] 调度是否通过**分区串行化（Actor）**避免竞态？状态是否以持久化服务为准并有对账？
- [ ] 推送是否可靠，派单应答链路是否有超时与兜底？
- [ ] **隐私**：位置模糊化、防三角定位、授权与最小化、存储脱敏与访问审计？
- [ ] 是否有大事件（演唱会、节假日）的容量与降级预案？A/B 实验与派单指标是否完善？

## 面试追问

> [!QUESTION] 附近的人是怎么实现的？Geohash 有什么问题？
> 用空间索引把经纬度映射成单元格，查询时取覆盖查询半径的格子里的候选，再用精确距离过滤排序。Geohash 把经纬度二分编码成字符串，前缀相同表示在同一格子，Redis GEO 用它做 ZSET 分值。问题是矩形网格形变、邻近点可能前缀不同的边界问题，所以要同时查中心格和 8 个邻格，再精确过滤；更大规模可用 S2 或 H3。

> [!QUESTION] 位置数据写入量很大，怎么设计存储？
> 位置是覆盖型高频写，只关心最新值，用按城市和网格分片的内存索引或 Redis 承接，写入做批量合并，在线状态用最后上报时间判定，历史轨迹异步经消息队列写入时序库。位置数据可由司机几秒内重新上报重建，不需要强持久化；关键的订单与司机服务状态放在持久化服务里。

> [!QUESTION] Redis GEO 在生产有哪些坑？
> 底层是 ZSET，没有成员级 TTL，要另维护 last_seen 或按时间分桶清理；单个城市一个 key 会成为大 key 和热点，要按城市加网格拆分到多个分片；只能按距离查，状态、车型等过滤要在应用层或分 key；写 QPS 受单节点限制，需要分片。

> [!QUESTION] 打车派单怎么设计？为什么不能只找最近的司机？
> 直线最近不等于接驾最快，要用路网 ETA 精排，并考虑司机状态、方向、车型、服务分与风控；策略上从逐单贪心升级为时间窗内批量匹配，构造订单和司机的二分图用匈牙利或 KM 算法求全局最小成本。还要处理应答超时重派、取消改派，以及一个司机同一时刻只被派一单的并发控制。

> [!QUESTION] 怎么保证一个司机不会被同时派给两个订单？
> 派单时对司机状态做原子占用，从空闲变为已派发，用 Redis Lua、CAS 或数据库条件更新，失败则换下一个候选，占用带应答超时自动释放；订单侧用条件更新保证只被一个司机接走；派单带 offer 标识，迟到应答被拒绝；更根本的是把同一区域的调度路由到单线程 Actor，串行化处理避免竞态。

> [!QUESTION] 热点区域（机场、演唱会）怎么处理？
> 动态细分网格并限制每格候选上限，对候选分层和排序截断，缓存热点查询结果，派单侧批量匹配控制规模；容量上提前扩容与预热，流量突增时限流排队并降级为简单匹配，动态加价调节供需。

> [!QUESTION] 位置隐私怎么保护？
> 最小化采集并明示授权、可关闭；展示时距离分档模糊化而不是精确坐标，防止多点查询的三角定位攻击，限制查询频率和位置跳变；存储加密脱敏并限制保留期，内部访问需审批与审计。
