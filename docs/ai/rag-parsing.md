# 文档解析与多模态 RAG（PDF、表格、OCR、图片）

> [!ABSTRACT] 核心要点
> - RAG 的效果上限常常被**解析质量**卡住：解析出的文本顺序错乱、表格被拍扁、页眉页脚混入正文，后面切分、向量化、重排再精细也救不回来。**“垃圾进，垃圾出”在这里最贴切。**
> - 解析要按文档类型选路线：**有文本层的 PDF 走版面分析**、**扫描件走 OCR**、**Office/网页走结构化解析**；复杂文档用**混合策略**并保留**页码、坐标、标题层级**等元数据。
> - **表格与图片**是重灾区：表格要保留行列语义（转 Markdown/HTML 或按行生成自然语言描述），图片要么 OCR/图表解析成文字，要么用**多模态嵌入/视觉模型**直接检索。
> - 切分应**感知文档结构**（按标题、段落、表格边界），而不是纯按字数硬切；每个片段带上**所属章节路径**作为上下文前缀。
> - 解析是**离线管道**：要有**质量评估、失败队列、版本与增量更新**，并把权限、来源等元数据一起入库，检索时据此过滤。

## 按文档类型选解析路线

| 类型 | 难点 | 推荐路线 |
| --- | --- | --- |
| **文本型 PDF**（有文本层） | 阅读顺序（多栏、页眉页脚）、表格、公式 | 先用文本层提取，叠加**版面分析**识别标题、段落、表格、页眉页脚区域 |
| **扫描 PDF/图片** | 没有文本层，清晰度、倾斜、印章遮挡 | **OCR**（文字检测 + 识别），再做版面还原；低质量件走人工兜底 |
| **Word / PPT / Excel** | 样式即结构，嵌入对象，隐藏内容 | 用格式原生解析库读取**标题样式、列表、表格**，直接得到结构；PPT 注意备注与图片 |
| **HTML / Markdown** | 导航、广告等噪声 | 正文提取（去模板）、保留标题层级和代码块；Markdown 直接按标题树切 |
| **邮件/聊天记录** | 线程、引用、签名 | 按线程重组，去除引用重复与签名，保留发件人与时间 |
| **代码/配置** | 语义单位是函数/类 | 按语法树（函数、类）切，保留文件路径与签名 |
| **音视频** | 无文字 | 语音转写（ASR）+ 时间戳；视频可再加关键帧描述 |

### 解析器的三代思路

1. **纯文本提取**：快、便宜，但丢失版面信息；适合排版简单的文档；
2. **版面分析 + 规则/模型**：检测页面里的标题、正文、表格、图片、页眉页脚区域，再按区域**重建阅读顺序**；多栏论文、报告的主力方案；
3. **视觉语言模型（VLM）解析**：把页面渲染成图，让多模态模型直接输出 Markdown/结构化内容；对复杂版式、图表、手写效果好，但**慢、贵、可能“脑补”内容**，适合难例或关键文档，要对关键数字做二次校验。

实际常用**分级策略**：先用快速解析器，质量检查不通过的页再升级到更强的方案，兼顾成本与效果。

### 清洗

- 去**页眉、页脚、页码、水印**（出现在大量页面的重复行）；
- 处理**断词与换行**：PDF 的硬换行要合并成段落，中文不要把每行末尾当作段落结束；
- 统一**空白与全半角**，去除不可见字符；
- **去重**：同一文档的多个版本、相同段落重复入库会让检索结果被重复内容占满；用内容哈希或近似去重（SimHash/MinHash）；
- **敏感信息**：入库前按合规要求做脱敏（手机号、证件号、密钥），而不是等到回答时再处理。

## 表格

表格被“拍扁”成一行行文字时，列与单元格的对应关系丢失，模型无法回答“Q3 华东区的毛利是多少”。

| 做法 | 适用 | 注意 |
| --- | --- | --- |
| **转 Markdown/HTML 表格** | 中小表格，模型能直接读懂 | 合并单元格、多级表头要展开；大表占用大量 Token |
| **按行生成自然语言** | 检索为主的表（参数表、价格表） | 每行带上表头：“产品 A 的规格：容量 10L，功率 500W” |
| **表格摘要 + 原表引用** | 大表、数据表 | 对表生成一段摘要和关键列说明用于检索；命中后再按需加载完整表 |
| **入结构化存储** | 数值型、需要精确计算的表 | 入关系库，用 Text-to-SQL 查询，见 [案例：Text-to-SQL 数据分析助手](#/ai/case-text2sql) |
| **跨页表** | 表头只在第一页 | 识别续表并合并，或为每页补上表头 |

关键原则：**需要精确数值计算和聚合的，不要指望模型读文本表格算**，走结构化数据 + 查询；需要“理解”的才放进上下文。

| 路线 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- |
| **A：转文字**（OCR、图表转表、VLM 描述） | 复用文本管道，可解释、可全文检索 | 描述可能丢细节或“脑补” | 流程图、截图、扫描件、图表（尤其能还原成数据表时） |
| **B：多模态嵌入**（图/页面直接向量化） | 保留视觉信息，不依赖解析质量 | 模型与存储成本高；生成时需视觉模型；难做精确引用 | 商品图、设计稿、版式复杂的页面、以图为主的资料 |
| **混合** | 文本召回为主，视觉模型对命中的页面做二次阅读 | 链路复杂 | 复杂手册、财报：先用文本定位页，再把页面图交给视觉模型 |

实践建议：

- 图片类内容要保留**图片原文件与所在位置**，回答时可以附带原图引用；
- VLM 生成的描述要**标注为机器生成**，对关键数值二次校验，防止幻觉；
- 图表尽量还原成**数据表**（而不是一句“折线上升”），才能回答具体数值；
- 控制成本：先过滤**装饰性图片**（Logo、分割线、背景），只处理有信息量的图。

## 结构感知切分

切分的基本原则见 [RAG 原理](#/ai/rag)。解析后有了结构，就可以做得比“每 500 字切一刀”好得多：

| 策略 | 做法 |
| --- | --- |
| **按标题树切** | 以章节为边界，过长的章节再按段落细分；每个片段附带**标题路径**（如“第 3 章 安装 > 3.2 网络配置”） |
| **保持语义单元完整** | 表格、代码块、列表、公式不在中间截断；图片说明与图在一起 |
| **父子块（small-to-big）** | 用小片段做检索（精确），命中后返回其所在的**大段落/整节**给模型（上下文完整） |
| **前缀上下文** | 每个片段前加一句“来自《文档名》第 X 章”（上下文化嵌入），显著提升召回 |
| **窗口重叠** | 对无结构文本用适度重叠（如 10%~15%）避免在句子中间丢信息 |
| **按类型差异化** | FAQ 按问答对切；合同按条款；代码按函数；会议纪要按议题 |

切分参数（片段大小、重叠）要**用评测集调**，不要照搬教程里的数字，见 [评测体系实战](#/ai/eval)。

## 元数据与权限

片段入库时附带的元数据，决定了后面能做什么：

| 元数据 | 用途 |
| --- | --- |
| 文档 ID、版本、更新时间 | 增量更新、删除旧版本、**新旧版本去重**、答案标注“依据 2024 版手册” |
| 页码、坐标、标题路径 | **引用溯源**（点击跳到原文位置）、展示来源 |
| 文档类型、业务线、语言、产品型号 | 检索前**过滤**，缩小范围提高精度 |
| **访问控制（ACL：部门、角色、用户）** | 检索时按**当前用户权限**过滤，避免越权泄露 |
| 解析方式与质量分 | 排查问题、对低质量内容降权 |

> [!WARNING] 权限必须在检索阶段过滤
> 不要把所有内容检索出来再让模型“不要泄露”。无权限的内容**根本不能进入上下文**。ACL 变更还要能**同步到索引**（事件驱动更新或定期对账），否则员工离职、调岗后仍能检索到原权限内容。

## 工程实践：解析管道

- **异步化**：解析慢（尤其 OCR/VLM），放入任务队列，由 worker 消费，状态可查询、可重试；
- **幂等与版本**：以“文档 ID + 内容哈希”判重；文档更新时**先写新版本再切换再删旧版本**，避免出现“检索空窗”；
- **增量与删除**：支持按文档删除其全部片段（向量库与全文索引、缓存同步清理）；
- **失败隔离**：单个坏文件不阻塞整批；失败原因分类（加密、损坏、超大、不支持）并告警；
- **质量评估**：抽样人工检查，或构造**带标注的解析评测集**，计算文本相似度、表格还原率、阅读顺序正确率；换解析器前后对比；
- **成本控制**：快速解析器兜底大多数文档，仅对难例使用 OCR/VLM；缓存解析结果；
- **安全**：不可信文档的解析放入**沙箱**（解析库历来是漏洞多发处）；限制文件大小与页数，防止“压缩炸弹”；
- **数据治理**：保留原文件与解析中间结果，便于重新切分、换模型重新向量化时**无需重新解析**。

## 常见坑

| 现象 | 根因 | 对策 |
| --- | --- | --- |
| 回答引用了页眉页脚内容 | 未去噪 | 版面分析识别区域，重复行规则去除 |
| 多栏文档语句混乱 | 阅读顺序错误 | 版面分析重建顺序，或用 VLM 解析 |
| 表格数据对错行列 | 表格被拍扁/合并单元格错位 | 表格专用解析；转 Markdown/HTML；按行生成带表头描述 |
| 中文被硬换行切碎、英文单词断开 | 文本层换行未合并 | 按标点和段落规则合并 |
| 扫描件乱码、漏字 | OCR 质量或图片质量差 | 预处理（去倾斜、增强）、更换引擎、人工兜底 |
| 数字被 VLM“脑补” | 视觉模型幻觉 | 关键数字二次校验，机器生成内容标注来源 |
| 同一问题召回多个版本的同一段 | 多版本未去重 | 内容哈希去重、版本过滤只检索最新 |
| 更新文档后旧答案仍出现 | 旧片段/缓存未清理 | 文档级版本替换，向量库、全文索引、缓存同步删除 |
| 越权看到别人的文档 | ACL 未入索引或未同步 | 元数据带 ACL、检索时过滤、变更事件同步 |

## 面试追问

> [!QUESTION] 为什么说 RAG 的效果很大程度取决于文档解析？
> 解析决定了后续所有环节的原料质量：阅读顺序错乱、页眉页脚混入、表格被拍扁都会让切分和向量失去语义，召回再精细也无法弥补，生成还会引用到噪声。多数“答非所问”追查到最后是解析或切分问题。

> [!QUESTION] 扫描件、复杂版式 PDF 你会怎么处理？
> 先识别是否有文本层：有则用文本提取叠加版面分析重建阅读顺序和表格；没有则 OCR；复杂或关键文档用视觉语言模型解析并对关键数字校验。采用分级策略，先快速解析器，质量检查不通过的再升级，不合格的进失败队列由人工处理。

> [!QUESTION] RAG 里的表格怎么处理？
> 保留行列语义：中小表格转 Markdown 或 HTML，检索类的表按行生成带表头的自然语言描述，大表做摘要并引用原表；需要精确计算和聚合的数值表入结构化库用 Text-to-SQL 查询，不要让模型从文本里算；跨页表要合并或补表头。

> [!QUESTION] 文档里的图片怎么进入 RAG？
> 两条路线：转文字（OCR、图表还原成数据表、视觉模型生成描述）后走文本检索，成本低可复用；或用多模态嵌入让图文在同一向量空间检索，命中后交给视觉模型回答，保留视觉细节但更贵。常见做法是文本定位页面，再把页面图交给视觉模型二次阅读。

> [!QUESTION] 切分除了按字数，还有什么更好的做法？
> 感知结构：按标题树和语义单元切，表格、代码块不截断；片段前加标题路径等上下文前缀；用父子块——小块检索、命中后返回所在大段；按文档类型差异化（FAQ 按问答、合同按条款、代码按函数）；参数用评测集调整。

> [!QUESTION] 知识库的权限怎么做？
> 入库时把 ACL（部门、角色、用户）作为元数据写入片段，检索时按当前用户权限在检索阶段过滤，无权限内容不进入上下文；权限变更通过事件同步到索引并定期对账。不能依赖让模型“不要泄露”来做访问控制。
