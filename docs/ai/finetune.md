# 微调实战：数据、LoRA/QLoRA、偏好对齐与评估

> [!ABSTRACT] 核心要点
> - 微调是**最后一级手段**：先用提示词、RAG、工具把效果推到极限；微调主要解决**“怎么说”和“稳定做”**（格式遵循、风格话术、特定任务稳定性、小模型替代大模型降本），**不擅长灌入会变化的事实知识**。
> - 微调成败 80% 在**数据**：质量远胜数量，几百到几千条高质量、覆盖边界的样本常比几万条脏数据更好；**先有评测集，再准备数据，最后才训练**。
> - 主流做法是 **SFT + LoRA/QLoRA**：冻结基座，只训练低秩适配器；单卡就能训，产物是**小文件**，可热加载、多租户共享基座。
> - 要在“学会新任务”和“不忘旧能力”间平衡：**混入通用数据、控制学习率与轮数、评测通用能力是否退化**。
> - 偏好对齐（DPO 等）用于调整**回答倾向**，需要成对偏好数据；**蒸馏**用大模型的输出训练小模型，是降本的常用路径。
> - 必须以**固定评测集对比基线**（基座+提示词、RAG）决定是否上线；微调模型要纳入版本管理与灰度。

> 本页的超参数范围和工具名是经验性参考，具体取值请以所用框架文档和你的评测结果为准。

| 回答风格要“更谨慎/更简洁/更符合品牌” | SFT 或偏好对齐 | 偏好类问题数据比规则更好表达 |
| 想让模型“记住”大量事实 | **不要微调** | 记忆不可靠、更新慢、易幻觉、难溯源 |

## 数据工程

### 数据从哪来

| 来源 | 说明 | 注意 |
| --- | --- | --- |
| **业务日志（已脱敏）** | 真实用户问题与人工/高分回答 | 去除敏感信息；筛掉低质量、错误回答；注意用户授权与合规 |
| **专家编写** | 质量最高、成本高 | 适合种子数据和评测集 |
| **大模型生成 + 人工审核** | 规模化的主要手段（合成数据） | 先写好生成规范和多样性约束；**一定要抽检与过滤**，避免把大模型错误复制进小模型；注意所用模型的使用条款 |
| **公开数据集** | 通用能力、混合数据 | 许可证；与业务分布差异 |
| **线上失败样本** | 针对性补强 | 修正后的正确答案入库，形成数据飞轮 |

### 样本格式

常见是**指令-回答**或**多轮对话**，用目标模型对应的**对话模板（chat template）**拼接，否则训练与推理格式不一致，效果会明显变差：

```json
{
  "messages": [
    {"role": "system", "content": "你是企业客服助手，回答简洁、礼貌，只依据提供的资料。"},
    {"role": "user", "content": "资料：……\n问题：发票多久能开出来？"},
    {"role": "assistant", "content": "您好，电子发票在订单完成后 1~3 个工作日内开具……[资料1]"}
  ]
}
```

要点：

- **训练格式 = 线上推理格式**：系统提示词、检索资料的排布、输出格式都和线上一致，否则学到的分布和实际不匹配；
- 只对 **assistant 部分计算损失**（多数框架支持仅训练回答 Token），不要让模型“学说用户的话”；
- 需要**拒答样本**（资料没有答案时说不知道）、**边界样本**、**格式错误的反例的修正**；
- 工具调用类任务要包含**工具调用与结果**的完整轨迹。

### 数据质量清单

| 检查 | 说明 |
| --- | --- |
| **正确性** | 答案事实与格式都正确；抽样人工复核，错误率要低（脏数据会被放大） |
| **一致性** | 同类问题风格与结论一致；不同标注者标准统一，避免相互矛盾 |
| **多样性** | 问法、长度、难度、场景分布均衡；避免大量近似重复（去重：哈希、近似去重） |
| **覆盖边界** | 含模糊问题、无答案、多意图、越权请求、攻击样例 |
| **分布一致** | 训练分布贴近线上真实分布（不是都选“漂亮”的例子） |
| **泄漏检查** | **训练集与评测集严格隔离**，包括近似重复，避免“考题进了训练集” |
| **合规** | 个人信息、商业机密、版权数据的处理与授权 |

### 数据量与配比

- **起点**：窄任务几百~几千条高质量样本就能看到明显效果；复杂风格和多任务需要更多；用**学习曲线**判断：用 25%、50%、100% 的数据各训一次，看指标是否还在涨；
- **混合通用数据**：只用业务数据容易**灾难性遗忘**（通用对话、指令遵循变差），常混入一定比例通用指令数据（比例用评测调整）；
- **多任务**：不同任务的数据按目标配比；样本少的任务可适当上采样，但避免过度重复。

### 关键超参（经验起点）

| 参数 | 含义 | 经验参考 | 现象 |
| --- | --- | --- | --- |
| **秩 r** | 低秩矩阵的秩，决定适配器容量 | 8、16、32 常见；复杂任务可更大 | 太小学不会，太大易过拟合且收益递减 |
| **alpha（α）** | 缩放系数，实际缩放 α/r | 常取 r 或 2r | 影响更新幅度，常与学习率联动调 |
| **目标层** | 给哪些线性层加适配器 | 注意力的 q/k/v/o；效果不足可扩展到 MLP 层 | 覆盖面越大容量越大、显存越多 |
| **学习率** | 步长 | LoRA 通常比全量微调大（如 1e-4~2e-4 量级起步） | 太大损失震荡/遗忘；太小学不动 |
| **轮数 epoch** | 过几遍数据 | 小数据 1~3 轮 | 过多易过拟合，验证损失回升就停 |
| **批大小/梯度累积** | 有效批大小 | 以显存为限，用累积凑到 16~64 的有效批 | 批太小训练噪声大 |
| **序列长度** | 最大 Token 数 | 取数据 95 分位；过长浪费显存 | 截断会丢信息，注意截断位置 |
| **dropout** | 适配器的正则 | 0~0.1 | 数据少时可略加 |
| **warmup 与调度** | 学习率预热与衰减 | 少量预热 + 余弦衰减 | 缓解训练初期不稳 |

> [!TIP] 调参的顺序
> 先固定数据与基线配置，**一次只改一个量**；优先调数据质量与学习率/轮数，再调 r 与目标层。训练过程同时看训练损失与**验证损失**，验证损失开始上升就是过拟合信号。更多通用训练技巧见 [训练神经网络：优化器、正则化与常见坑](#/aimodel/training)。

### 工具与基础设施

- **训练框架**：社区有 Hugging Face 的 Transformers/PEFT/TRL、LLaMA-Factory、Axolotl、Unsloth 等，封装了数据格式、LoRA/QLoRA、DPO 等流程；选择时看对目标基座的支持、分布式能力和维护活跃度；
- **算力**：单卡 + QLoRA 可微调中小规模模型；更大模型或全量微调需要多卡与分布式策略（数据并行、张量/流水线并行、ZeRO 等）；
- **实验管理**：记录数据版本、超参、基座版本、评测分数（用实验跟踪工具），保证**可复现与可对比**；
- **云上微调服务**：部分厂商提供托管微调（上传数据、选基座、得到可调用的模型），省运维但受限于其支持的模型和数据出境要求；
- **数据安全**：训练数据含业务敏感信息时，评估托管服务的数据处理条款，或使用私有化训练。

## 偏好对齐与蒸馏

### 偏好对齐（DPO 等）

SFT 教模型“怎么答”，偏好对齐教模型“**哪种答案更好**”：

| 方法 | 思路 | 特点 |
| --- | --- | --- |
| **RLHF** | 先训**奖励模型**，再用强化学习（如 PPO）优化策略 | 效果强，但流程复杂、训练不稳定、成本高 |
| **DPO** 及变体 | 直接用**成对偏好数据**（同一问题的“好答案 / 差答案”）优化，不显式训练奖励模型 | 实现简单稳定，常用在 SFT 之后；效果依赖偏好数据质量 |
| **基于可验证奖励的强化学习** | 对有标准答案的任务（数学、代码、结构化任务）用规则/程序判定奖励 | 适合能自动验证的任务，是提升推理能力的重要方法 |

偏好数据来源：人工比较、线上用户点赞点踩、让强模型按评分细则比较两份回答（再人工抽检）。**偏好数据里“好坏”标准必须一致**，否则模型学到的是噪声。

### 蒸馏

用**大模型（教师）**生成高质量答案或带推理过程的答案，作为训练数据训练**小模型（学生）**，是最常见的降本做法：

1. 在真实业务问题上用大模型生成答案（可加提示词约束与拒答策略）；
2. **自动过滤 + 抽样人工审核**（程序验证、一致性检查、评分模型）；
3. SFT 小模型；用评测集比较与大模型的差距、成本与延迟；
4. 线上**路由**：简单问题走小模型，难例回退大模型，持续把难例补进训练数据。

注意各家模型的**使用条款**对“用其输出训练其他模型”的限制。

## 训练过程与排错

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 训练损失不降 | 学习率过小/数据格式错误（模板不对、损失掩码错）/标签全被掩码 | 检查数据打印、模板、掩码；先用少量样本过拟合验证流程正确 |
| 训练损失降得很快但验证损失升 | **过拟合**，数据少、轮数多 | 减少轮数、降低 r、增加数据与多样性、加 dropout |
| 效果提升但通用能力下降（**灾难性遗忘**） | 学习率过大、轮数过多、数据分布窄 | 混入通用数据、降低学习率、减小 r、用评测监控通用基准 |
| 输出重复或不停止 | 缺少结束标记、模板与推理不一致 | 检查 EOS 与对话模板，推理参数（重复惩罚、最大长度） |
| 在线效果不如离线 | 训练分布与线上不一致、提示词排布不同 | 统一格式，用线上真实样本评测 |
| 显存不足 | 序列长、批大、模型大 | QLoRA、梯度检查点、缩短序列、减小批并增大梯度累积 |
| 训练不稳定（损失尖刺） | 学习率高、数据脏、数值精度问题 | 降学习率、增大预热、清洗异常样本、梯度裁剪 |
| 合并适配器后效果变差 | 量化合并误差、合并方式不当 | 在合并后的模型上重新评测，必要时用适配器动态加载 |

> [!TIP] 先做“过拟合小样本”冒烟测试
> 取 20~50 条样本训练到几乎背下来，如果连这都做不到，问题在数据格式、模板或掩码，而不是超参。

## 评测与上线

评测是微调的**决策依据**，不是收尾步骤：

| 评测项 | 做法 |
| --- | --- |
| **任务指标** | 在固定评测集上对比：基座+提示词、基座+RAG、微调模型；指标含准确率/格式合规率/人工或 LLM 评分 |
| **通用能力回归** | 抽一批通用问题与基准，确认没有明显退化 |
| **安全** | 拒答与越权、注入攻击样例，微调有时会**削弱原有的安全对齐** |
| **成本与延迟** | 微调小模型 vs 大模型的单次成本、P95 延迟、吞吐 |
| **鲁棒性** | 改写问法、噪声输入、长输入下的表现 |
| **人工抽检** | 关键场景由领域专家复核，校准自动评分 |

上线与维护：

- **版本管理**：数据版本、基座版本、适配器版本、训练配置、评测报告一起归档，可回滚；
- **灰度**：小流量对比线上指标（满意度、转人工率、成本），再放量；
- **服务**：推理引擎支持**多适配器**时可一基座服务多任务/租户（见 [大模型原理与推理服务](#/ai/llm-internals)）；合并导出则作为独立模型部署；
- **持续迭代**：线上失败样本回流→人工修正→进入下一版训练集；定期评估**新基座 + 提示词/RAG** 是否已追平微调效果，避免维护无收益的微调模型；
- **监控**：输出分布漂移、拒答率、格式失败率、投诉。

## 成本估算

| 项 | 说明 |
| --- | --- |
| **数据** | 标注/审核人力常是**最大成本**，大于算力 |
| **训练算力** | LoRA/QLoRA：单卡数小时到数天（取决于模型、数据量、序列长度）；多次实验乘以迭代次数 |
| **评测** | 评测集构建与 LLM 评审调用费 |
| **服务** | 自部署需 GPU 常驻成本；对比 API 按量计费，要按调用量算**盈亏平衡点** |
| **维护** | 基座升级后的重训、数据更新、监控、人员 |

结论常是：**调用量大且任务窄**才值得蒸馏+小模型自部署；调用量小或任务多变，用大模型 API + 提示词/RAG 通常更划算。

## 常见坑

| 坑 | 后果 | 对策 |
| --- | --- | --- |
| 没评测集就开训 | 无法判断是否变好 | 先建评测集和基线 |
| 想用微调灌知识 | 记不牢、会编造、难更新 | 用 RAG；微调只学格式与风格 |
| 数据脏、答案互相矛盾 | 效果比基线还差 | 清洗、抽检、统一标准 |
| 训练/推理模板不一致 | 线上效果远低于预期 | 统一对话模板与系统提示词 |
| 评测集泄漏进训练集 | 分数虚高 | 严格划分与近似去重 |
| 过度训练 | 过拟合与遗忘 | 早停、混合通用数据、监控验证损失 |
| 忽视安全回归 | 微调后更容易越狱 | 微调后加安全评测与护栏 |
| 微调完不再维护 | 基座升级后落后，数据过期 | 定期对比新基座方案，数据持续更新 |

## 面试追问

> [!QUESTION] 什么时候该微调，什么时候不该？
> 缺事实知识或知识常变用 RAG，不微调。提示词、RAG、工具都调到极限后，如果问题是格式风格不稳、窄任务稳定性、想用小模型替代大模型降本，才考虑 SFT 或蒸馏；前提是有评测集和高质量数据。想用微调让模型记住文档效果差、更新慢、难溯源。

> [!QUESTION] LoRA 的原理和优势？
> 冻结基座权重，在线性层旁路加两个低秩矩阵 A、B，只训练它们，输出为 W·x 加缩放后的 B·A·x。可训练参数只有原来的千分之几到百分之几，显存和成本大降；产物是小的适配器文件，可合并或在推理时动态加载，一个基座服务多个任务或租户。QLoRA 再把基座 4 位量化，使单卡可微调更大模型。

> [!QUESTION] 微调数据怎么准备？要注意什么？
> 质量优先于数量，覆盖边界、拒答和线上真实分布；格式与线上推理一致并使用目标模型的对话模板，只对回答部分算损失；去重、抽检、统一标注标准；训练集与评测集严格隔离防泄漏；混入通用数据缓解遗忘；合成数据必须过滤和人工抽检，并注意合规与模型使用条款。

> [!QUESTION] 什么是灾难性遗忘？怎么缓解？
> 模型在学习新任务时丢失原有的通用能力。缓解办法：混入通用指令数据、降低学习率与轮数、减小秩或限制适配器范围、早停，并用通用基准评测监控；用适配器而不是全量覆盖也更容易回退。

> [!QUESTION] DPO 和 SFT、RLHF 有什么区别？
> SFT 用“问题-标准答案”教模型怎么答；RLHF 先训奖励模型再用强化学习优化策略，效果强但复杂且不稳定；DPO 直接用成对的“好答案/差答案”偏好数据优化策略，不需要显式奖励模型，实现简单稳定，常放在 SFT 之后调整回答倾向，效果依赖偏好数据的一致性。

> [!QUESTION] 怎么决定一个微调模型能不能上线？
> 在固定评测集上与基线（基座+提示词、基座+RAG）对比任务指标，同时检查通用能力和安全回归、成本延迟和鲁棒性，关键场景人工抽检；达标后灰度并监控线上指标，数据、基座、适配器版本一起归档可回滚；还要持续评估新基座的方案是否已追平，避免维护无收益的微调。

> [!QUESTION] 蒸馏怎么做才有效？
> 在真实业务问题上用大模型生成答案，自动过滤加人工抽检保证质量，再 SFT 小模型；用评测集比较与大模型的差距、成本和延迟；线上用路由让简单问题走小模型、难例回退大模型，并把难例补进训练数据；同时留意教师模型的使用条款限制。
