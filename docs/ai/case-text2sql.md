# 案例：Text-to-SQL 数据分析助手设计详解

> [!ABSTRACT] 核心要点
> - 目标：让业务人员用自然语言查数据（“上个月华东区各品类销售额环比”），系统生成 SQL、执行并给出表格/图表与解释。难点不在“写出 SQL”，而在**业务语义对齐、权限与安全、结果可信**。
> - **“直接把整个库 Schema 丢给模型”只适合 Demo**。生产方案是：**语义层（指标与维度的统一定义）+ Schema/示例检索 + 受限的 SQL 生成 + 多层校验 + 只读沙箱执行**。
> - **正确性**比通顺更重要：同一个“销售额”在不同表有不同口径，模型会选错。**指标口径要由语义层定义，模型只负责把问题映射到指标与维度**，再由确定性引擎生成 SQL，是最稳的路线。
> - **安全**是底线：只读账号、白名单表与列、行列级权限由**数据库/服务端强制**、语句类型与成本限制、超时与结果行数限制、审计；**绝不信任模型生成的 SQL**。
> - 必须有**评测集**（问题→标准 SQL/标准结果），以**执行结果准确率**为主指标；对**歧义问题主动澄清**，对**无法回答的问题说无法回答**。
> - 用户信任来自**透明**：展示所用口径、时间范围、SQL 与数据来源，允许用户修改后重跑。

## 1. 背景与目标

| 项 | 说明 |
| --- | --- |
| **用户** | 业务运营、产品、管理层；不会写 SQL，但需要即席查询 |
| **数据** | 数仓/数据集市中的数十到数百张表，指标口径有文档但分散 |
| **场景** | 即席查询、指标对比、明细筛选、趋势、占比、TopN；不做大规模跨库复杂建模 |
| **非目标** | 写操作；跨系统的复杂数据整合；替代专业分析师的深度建模 |
| **质量目标** | 常见问题执行准确率达到可接受门槛（如 ≥90%，以评测集为准），不确定时不瞎答 |
| **安全目标** | 零越权；任何情况不执行写操作；资源可控 |
| **体验目标** | 简单问题 5~10 秒出结果，可追问与修改，答案可追溯 |

## 2. 关键设计决策

| 决策点 | 选择 | 原因 |
| --- | --- | --- |
| 让模型直接写 SQL 还是写“查询意图” | **两种模式并存**：核心指标走**语义层（模型只选指标/维度/过滤），长尾明细走受限的直接生成 SQL** | 语义层保证口径一致；直接生成覆盖长尾；两者按问题类型路由 |
| 如何给模型 Schema | **检索相关表/列 + 业务描述 + 示例**，而不是全量 | 全量 Schema 又长又杂，容易选错、成本高 |
| 权限在哪里做 | **数据库/查询网关强制**（账号、视图、行列级策略） | 模型会被诱导，应用层拼 SQL 过滤不可靠 |
| 生成后做什么 | 解析→校验→（可选）EXPLAIN→执行→校验结果→解释 | 多层把关，错误及早失败 |
| 歧义怎么办 | **先澄清**（指标口径、时间范围、维度粒度） | 猜错的代价是业务决策出错 |
| 复杂问题 | 拆成多个子查询或分步（先查再算），每步可见 | 一步写超长 SQL 极易出错 |

## 4. 语义层与 Schema 检索

### 为什么需要语义层

| 没有语义层 | 有语义层 |
| --- | --- |
| “销售额”可能对应 5 个字段、3 种口径，模型随机选一个 | 指标“销售额=已支付订单金额-退款，按支付时间统计”**唯一定义** |
| 模型自己拼 JOIN，漏条件、重复计数 | 指标与维度预先定义了**可用的连接路径与过滤**，由引擎生成 SQL |
| 口径变化要改所有提示词和示例 | 改一处，所有查询一致 |
| 难以审计 | 结果可以追溯到指标定义与版本 |

语义层通常包含：**指标（度量+聚合+过滤+时间口径）、维度（含层级，如国家→省→市）、实体与连接关系、同义词（“GMV/成交额/销售额”）、枚举值映射（“华东”→region IN (...)）**。可以用专门的语义层产品或自建一套“指标 YAML + 查询编译器”。

### 两种生成模式的路由

| 问题类型 | 模式 | 模型输出 | 由谁生成 SQL |
| --- | --- | --- | --- |
| **核心指标分析**（占 70%~80% 的高频问题） | **语义查询** | `{metric: "gmv", dims: ["region","category"], filters: [...], time: "last_month", compare: "mom"}` | **语义层编译器**（确定性） |
| **长尾/明细查询** | **受限直接生成 SQL** | SQL（仅 SELECT） | 模型生成，经校验与权限改写 |
| 无法回答/越界 | 拒答或澄清 | 说明原因，引导修改问法 | — |

核心指标走语义层，把“最容易错且最重要的部分”交给确定性引擎；长尾给灵活性但接受更严格的校验与提示“结果仅供参考”。

### Schema 检索

数据表多时必须先**缩小范围**：

1. **表/列描述入库**：为每张表、每列准备业务描述、示例值、枚举含义、数据新鲜度，向量化存储（业务描述比物理字段名更重要）；
2. **混合检索**：问题与表描述、术语表、历史成功查询做向量+关键词检索，得到候选表；
3. **连接路径扩展**：根据外键/语义层的关系，把必要的关联表补进来；
4. **列裁剪**：只给相关列，附描述与样例值；超大枚举只给 Top 值；
5. **检索示例**：取**相似问题的已审核 SQL** 作为 Few-shot（效果通常显著）；
6. **权限预过滤**：用户无权的表/列在这一步就**不出现**，减少越权尝试，也减少提示词噪声。

> [!TIP] 表描述比表结构重要
> 列名 `amt_3`、`flag_x` 对模型毫无意义。先投入数据治理：规范命名、补全注释、维护术语表，比调提示词收益大得多。

## 5. SQL 生成、校验与修复

### 生成

- 提示词包含：任务说明、**方言**（MySQL/ClickHouse/Hive 等差异大）、候选 Schema 与描述、语义层说明、相似示例、业务约束（默认时间范围、必须带分区过滤、不允许 `SELECT *`）、输出格式（先思考要点再给 SQL，用结构化字段分开）；
- 复杂问题**先拆解**：识别需要的指标、过滤、分组、时间窗口，再写 SQL；
- **多候选 + 自一致**（可选）：生成多条 SQL，用**执行结果一致性**投票，提升关键问题的准确率（成本更高）。

要点：

- **解析而非正则**：用 SQL 解析器得到 AST，在 AST 上检查语句类型、涉及的表和列、函数白名单、是否多语句；
- **权限改写在 AST 层**：为每个涉及的表自动注入行级过滤（租户 ID、部门、数据域），**覆盖**模型写的任何条件；列级权限用**脱敏视图或列掩码**；
- **成本护栏**：先 `EXPLAIN` 估算扫描行数/分区，超阈值拒绝；强制时间范围；限制 JOIN 数量；设置查询超时与最大返回行数；使用**独立资源队列/只读副本**，避免拖垮生产；
- **修复循环**：把**具体错误**（列不存在、语法错误、超时）和相近的合法列名回传给模型；重试 ≤2 次，仍失败就**澄清或明确告知无法回答**；
- **结果检查**：空结果、全 NULL、金额出现负数、同比 10000% 等异常给出提示，让用户核对口径。

## 6. 安全与权限

| 风险 | 对策 |
| --- | --- |
| **写操作/破坏性语句** | 只读账号 + 只允许 SELECT + AST 校验；数据库层面没有写权限，这是**最后防线** |
| **越权读取** | 行列级权限在**数据库/查询网关**强制（行策略、视图、列掩码）；检索阶段不暴露无权表；SQL 层再次校验 |
| **提示注入** | 数据里的文本（如备注字段）可能含指令：把查询结果当**数据**，且生成 SQL 的权限不因结果内容而扩大；不让模型根据结果自动发起新的高权限查询 |
| **数据泄露** | 敏感列默认脱敏；对外部模型调用，评估**哪些 Schema/样例值/结果会发给模型**，必要时用私有化模型、只发 Schema 不发结果、脱敏样例值 |
| **资源滥用** | 并发限制、用户级配额、单查询超时与扫描限制、慢查询熔断 |
| **结果外带** | 导出需审批与水印；限制单次返回行数；记录导出审计 |
| **越狱问法** | “忽略权限”“查所有人的工资”：权限不由模型判断，直接被数据库策略拒绝；同时记录告警 |
| **审计合规** | 记录用户、问题、生成 SQL、涉及表列、扫描量、返回行数、是否导出；支持追溯与脱敏保留 |

## 7. 歧义、澄清与解释

用户问题常常**欠指定**：

| 歧义类型 | 例子 | 处理 |
| --- | --- | --- |
| **口径** | “销售额”是含税还是不含税？ | 有默认口径则采用并**显式展示**；无默认则追问 |
| **时间** | “上个月”是自然月还是近 30 天？“今年”到哪天？ | 固定规则并展示解析后的具体日期范围 |
| **维度粒度** | “各地区”是省还是大区？ | 默认粒度 + 允许下钻 |
| **多义实体** | “苹果”是品牌还是品类？ | 列出候选让用户选择 |
| **不可回答** | 数据里没有该信息 | 明确说明缺什么数据，不要硬编 |

**澄清要克制**：一次问一个最关键的问题，提供选项按钮；高频场景用默认值减少打断。

**解释与透明**是信任的来源，每个结果展示：

- 使用的**指标与口径**（链接到定义）、**时间范围、过滤条件**；
- **SQL**（可折叠）与数据更新时间；
- 数据**范围与限制**（“仅包含已支付订单，已排除测试订单”）；
- 异常提示与建议追问（“同比下降较多，要按渠道拆分看吗？”）；
- 允许用户**直接修改条件或 SQL 重跑**，并把修正后的版本作为反馈沉淀为示例。

可视化：由**规则**根据结果形态选择图表（时间序列→折线，类别对比→柱状，占比→饼/条形），模型只负责给标题与摘要，避免让模型编造数字——**摘要中的数字必须来自结果集**，可以做程序化核对。

## 8. 评测

| 层次 | 内容 |
| --- | --- |
| **评测集** | 100~500 个“问题 → 标准 SQL/标准结果”，按难度（单表、多表连接、嵌套、窗口函数、时间对比）、业务域、歧义问题、**应拒答问题**分层；含同义问法 |
| **核心指标** | **执行准确率（Execution Accuracy）**：生成 SQL 的**执行结果**与标准结果一致（允许列顺序等无关差异）；不要用 SQL 文本相等来判（等价写法很多） |
| **其他指标** | 语法有效率、Schema 链接准确率（选对表列）、澄清触发率与正确率、拒答正确率、平均重试次数、延迟、单次成本、扫描量 |
| **安全评测** | 越权、写操作、注入、绕过的红队样例，必须 100% 被拦截 |
| **回归** | 语义层、示例、提示词、模型变更都跑评测门禁；失败案例分类（选错表/口径错/连接错/时间错/方言错）定位优化点 |
| **线上** | 点赞点踩、用户修改 SQL 的比例、重复提问率、人工抽检；修正后的 SQL 回流示例库与评测集 |

评测方法与门禁的通用做法见 [评测体系实战：数据集、LLM 评审与回归门禁](#/ai/eval)。

## 9. 成本、性能与降级

| 项 | 做法 |
| --- | --- |
| **延迟预算** | 检索 200ms，生成 2~5 秒，执行取决于库（目标 <5 秒），解释 1~2 秒；流式展示“正在查询…”进度 |
| **成本** | 缓存：相同/相似问题复用已验证的 SQL 与结果（按数据新鲜度设置 TTL）；简单问题用小模型，复杂问题升级；Schema 裁剪减少 Token |
| **数据库保护** | 只读副本/专用资源组；高成本查询排队；热点指标预聚合（物化视图/汇总表），语义层优先命中汇总表 |
| **降级** | 模型不可用 → 提供常用报表入口/预置问题；SQL 校验失败 → 澄清或转人工分析师；超时 → 建议缩小范围或改为异步导出 |
| **容量** | 并发不高但单次重，关键是对数据库的**资源隔离**与限流，而非 Web 层扩容 |

## 10. 实施路线

1. **阶段 0：数据治理**：梳理核心主题域，补全表/列描述与术语表，确定 10~20 个核心指标口径；
2. **阶段 1：单域 MVP**：一个主题域，语义层 + 检索 + 只读执行 + 基本校验，建立评测集；仅内部试用；
3. **阶段 2：扩展与加固**：多域、权限改写、成本护栏、澄清与解释、反馈回流；安全红队；
4. **阶段 3：规模化**：缓存与预聚合、模型路由、导出审批与审计、运营看板；
5. **持续**：失败案例分析→补语义层/示例/描述；每次变更走评测门禁。

## 11. 取舍与复盘清单

- [ ] 核心指标是否由**语义层**定义，而不是模型临场发挥？
- [ ] 权限是否在**数据库/网关**强制，而不是靠提示词或应用层拼接？
- [ ] 数据库账号是否**只读**，并有资源组、超时和行数限制？
- [ ] 是否有**评测集**与执行准确率，每次变更是否回归？
- [ ] 歧义是否**澄清**，口径/时间范围是否**显式展示**？
- [ ] 结果摘要的数字是否来自结果集并经过核对？
- [ ] 外部模型会接触哪些**数据与 Schema**？是否脱敏、是否符合合规？
- [ ] 是否有**降级路径**与**审计日志**？

## 面试追问

> [!QUESTION] Text-to-SQL 在生产环境最大的难点是什么？
> 不是写出语法正确的 SQL，而是业务语义对齐与安全：同一指标口径多样、表列命名晦涩、问题欠指定，加上权限与资源保护。所以要用语义层固化指标口径，检索缩小 Schema，加歧义澄清，以只读沙箱和数据库层权限兜底，并以执行准确率评测。

> [!QUESTION] 为什么要引入语义层？模型直接写 SQL 不行吗？
> 直接写 SQL 容易选错表列、漏过滤、JOIN 重复计数，指标口径不一致且无法审计。语义层把指标、维度、连接路径唯一定义，模型只负责把问题映射成指标和维度，再由确定性编译器生成 SQL，高频核心问题更准更稳；长尾明细再用受限直接生成作补充。

> [!QUESTION] 怎么防止模型生成的 SQL 越权或造成破坏？
> 多层防护：数据库使用只读账号并在库内强制行列级权限；用 SQL 解析器检查只允许单条 SELECT、白名单表列与函数；在 AST 层注入租户和部门过滤，覆盖模型写的条件；EXPLAIN 成本检查、超时、行数和资源组限制；审计日志。不能信任模型输出，也不能靠提示词做访问控制。

> [!QUESTION] 如何评测 Text-to-SQL 系统？
> 构建按难度、业务域分层的评测集，包含歧义和应拒答样例，核心指标是执行准确率，即比较生成 SQL 与标准 SQL 的执行结果而不是文本；同时看 Schema 链接准确率、澄清与拒答正确率、重试次数、延迟成本，并做安全红队；变更走回归门禁，线上用户修改的 SQL 回流为示例和评测样例。

> [!QUESTION] 用户问题有歧义怎么办？
> 能用默认规则的采用默认并显式展示解析出的口径和日期范围；关键歧义一次只问一个问题并给选项；多义实体列出候选；数据里没有的信息明确说明无法回答。澄清要克制，避免过度打断，同时允许用户修改条件重跑。

> [!QUESTION] 怎么降低成本和对数据库的压力？
> 缓存已验证的 SQL 与结果并按数据新鲜度设置过期；简单问题用小模型；裁剪 Schema 减少 Token；热点指标预聚合并让语义层优先命中汇总表；使用只读副本和专用资源组，对高成本查询限流排队；强制时间范围和分区过滤。
