# 配置管理与全链路灰度

> [!ABSTRACT] 核心要点
> - 配置管理要解决四个问题：**分层（谁定义、谁覆盖）、动态（哪些能热更新）、安全（敏感信息）、治理（变更可灰度可回滚可审计）**。配置是比代码更危险的变更——它**秒级全量生效、不经过发版流程**。
> - **动态刷新有边界**：`@ConfigurationProperties` 与 `@RefreshScope` 可以重新绑定，**但数据源、线程池、已创建的连接等资源不会因为改了配置就重建**；强相关配置要放在同一个配置项里整体刷新，避免“半新半旧”。
> - **敏感配置不要明文**放在配置中心：用加密存储或密钥管理系统，配置里只放引用；配置也要按环境/命名空间严格隔离与授权。
> - **全链路灰度**的本质是**把“这是灰度流量”的标记（染色）贯穿所有调用环节，每一跳按标记选择对应版本的实例**，没有标记或无匹配版本则回退到稳定版本。
> - 染色要覆盖：**网关 → HTTP 调用（Feign/RestClient） → RPC（Dubbo/gRPC） → 消息队列 → 异步线程 → 定时任务**，任何一环丢标记，灰度流量就会“跳回”稳定版本，造成**版本混用**与难以复现的问题。
> - 灰度不只是路由：**数据库变更、缓存、消息、配置**都要有兼容与隔离策略，否则新版本写的数据会让老版本出错，**回滚能力是灰度的前提**，见 [发布策略：灰度、蓝绿、特性开关与数据库变更](#/infra/release)。

原则：

- **同一个配置项只在一处定义**，其余层不重复；否则出现“改了不生效”（被更高优先级覆盖）的排查噩梦；
- **环境隔离用命名空间**而不是名字后缀；生产命名空间权限单独管控，见 [Nacos 与服务注册发现、配置中心](#/mw/registry)；
- 命名规范：`<服务名>-<profile>.yaml`、`shared-<领域>.yaml`；配置文件拆分按**变更频率与责任人**分，不要把所有东西塞一个大文件；
- **加载顺序与优先级**由框架决定（Spring Boot 的外部化配置规则 + 配置中心的 shared/ext/应用配置顺序，版本间有差异），**启动日志或管理端点里确认最终生效值**，不要靠记忆。

### 动态刷新：能做与不能做

| 配置类型 | 能否动态 | 做法与注意 |
| --- | --- | --- |
| **业务开关、阈值、白名单、文案** | 能 | `@ConfigurationProperties` 绑定的 Bean 或 `@RefreshScope` Bean；或自己监听配置变更回调 |
| **限流/熔断规则** | 能 | 规则中心推送，见 [熔断限流实战](#/spring/cloud-resilience) |
| **日志级别** | 能 | 通过日志系统的动态调整 |
| **数据源连接串、账号** | 一般**不要热更新** | 已建立的连接池不会自动重建；需要重启或专门的“数据源热切换”设计（新池建好 → 切换 → 关旧池） |
| **线程池大小** | 谨慎 | 部分线程池支持动态调整核心/最大线程数，但要整体设计；队列容量等可能不可改 |
| **Bean 结构与组件装配** | 不能 | 条件装配在启动期决定，改了需要重启 |
| **端口、上下文路径** | 不能 | 重启 |

### `@RefreshScope` 的原理与坑

- 被 `@RefreshScope` 标注的 Bean 放在特殊的 **refresh 作用域**，**首次使用时创建并缓存**；收到刷新事件后，缓存被**清空**，**下次访问时重新创建**，从而绑定新的配置值；
- **懒创建**：刷新后第一次访问才重建，所以如果这个 Bean 初始化有副作用或很慢，会拖慢那次请求；
- **有状态 Bean 会丢状态**（计数器、本地缓存、持有连接的组件）：刷新即重建，状态丢失；不要把有状态组件放进 RefreshScope，或把配置与状态分离；
- **注入到单例中的 RefreshScope Bean 是代理**，通过代理转发，保证拿到最新实例；直接 `new` 或缓存引用会拿到旧对象；
- **并发刷新**：刷新瞬间正在处理中的请求可能用到旧实例，业务要能容忍短暂的新旧并存；
- **@Value 默认不刷新**（除非所在 Bean 是 RefreshScope），推荐使用 `@ConfigurationProperties` 集中管理；
- **关联配置要整体变更**：多个相关参数（如熔断阈值与窗口）放在同一个 Data ID，保证原子可见，避免客户端先后看到部分变更。

### 多环境与配置继承

- 开发/测试/预发/生产各自命名空间与独立的配置中心实例（或至少独立权限）；
- **环境差异只放真正有差异的项**（地址、容量、开关），公共项在共享配置中，减少重复和漂移；
- **配置与代码版本的兼容**：新版本代码依赖新配置项时，要**先发布配置（带默认值兼容旧代码）再发布代码**，回滚代码时配置仍兼容；
- **配置模板与校验**：用 Schema/校验规则（必填、范围、枚举）约束，发布前自动校验，启动时校验失败要**快速失败**并给出明确信息。

### 敏感配置

| 做法 | 说明 |
| --- | --- |
| **不明文存放** | 数据库密码、密钥、令牌不要明文放配置；使用配置加密（客户端解密）或接入密钥管理系统，配置里只存引用/占位符 |
| **最小权限与分环境** | 生产配置只读给开发，写权限与审批分离；不同环境密钥不同 |
| **日志与端点脱敏** | 不打印完整配置；暴露环境信息的管理端点要鉴权并脱敏 |
| **轮换** | 密钥定期轮换；轮换时要支持新旧并存的过渡期，见 [加密与密钥管理](#/security/crypto) |
| **配置审计** | 谁读了/改了敏感配置 |

### 配置变更治理

配置变更与代码发布同等对待（流程见 [Nacos 与服务注册发现、配置中心](#/mw/registry) 的配置发布章节）：**校验 → 审批 → 灰度（指定实例）→ 观察 → 全量 → 可回滚 → 审计**。补充几点：

- **变更与监控联动**：配置发布事件标注在监控曲线上，出现异常能快速关联；
- **高危配置分级**：限流阈值、路由、开关、降级策略等高危配置需要双人审批，普通配置可快速通道；
- **配置漂移检测**：定期对比配置中心与实例实际生效值（通过暴露的生效版本摘要），发现“某些实例没更新”；
- **回滚演练**：确认回滚确实能在分钟内恢复；
- **与特性开关的关系**：长期存在的业务开关用专门的特性开关平台（支持按用户、比例、灰度），配置中心做基础配置，见 [发布策略](#/infra/release)。

### 灰度对象与染色策略

| 灰度维度 | 例子 | 特点 |
| --- | --- | --- |
| **按用户** | 内部员工、白名单用户、用户 ID 哈希百分比 | **粘性好**，体验一致，首选 |
| **按请求属性** | 请求头、Cookie、App 版本、地区、渠道 | 适合内测与区域试点 |
| **按流量比例** | 随机 5%、10% | 简单，但同一用户可能时新时旧，需粘性处理 |
| **按租户** | 指定企业租户 | B 端系统常用 |
| **按服务/功能** | 单个服务先升级，被灰度调用方选择性调用 | 小范围验证单服务变更 |

**染色在入口完成**：网关根据规则给请求打标（如 `X-Gray: v2`），**同时清除外部传入的同名头**（防止用户伪造进入灰度）；后续只传递，不重新决策（避免链路中途换标）。

### 各环节的标签透传与选路

| 环节 | 机制 | 要点 |
| --- | --- | --- |
| **注册中心** | 灰度实例注册时携带元数据标签（`version=v2`、`gray=true`） | 发布流水线给灰度实例设置标签；稳定实例不带或带 `stable` |
| **网关** | 规则染色 + 按标签选择路由/实例 | 见 [Spring Cloud Gateway 深入](#/spring/cloud-gateway) |
| **HTTP 调用** | 出站拦截器写入灰度头；自定义 `ServiceInstanceListSupplier`/LoadBalancer 按标签过滤实例列表 | 拦截器写入、负载均衡读取，见 [OpenFeign 深入](#/spring/cloud-feign) |
| **RPC（Dubbo/gRPC）** | 通过调用上下文（Attachment/Metadata）透传标签；路由规则按标签 | Dubbo 的标签路由；见 [Dubbo 集群容错与服务治理](#/mw/dubbo-practice) |
| **消息队列** | 灰度标写入消息头；消费端按标签路由到灰度消费者或灰度 Topic | 见下文消息灰度 |
| **异步线程/线程池** | 线程切换时显式传递上下文 | 否则标记丢失，后续调用落回稳定版本 |
| **定时任务** | 灰度实例是否执行任务、执行哪些数据范围要显式配置 | 防止灰度与稳定实例重复/遗漏执行同一任务，见 [案例：分布式任务调度系统设计详解](#/design/case-scheduler) |
| **缓存、数据库** | 见下文数据兼容 | 最容易出事故 |

负载均衡选实例的规则（核心）：**请求带灰度标 → 优先选带该标签的实例；没有可用灰度实例 → 回退到稳定实例；请求无标 → 只选稳定实例（不得误入灰度）**。回退要有监控，避免灰度实例全挂时悄悄全部走稳定而无人察觉。

### 消息与异步灰度

| 方案 | 做法 | 优缺点 |
| --- | --- | --- |
| **灰度 Topic/队列** | 灰度流量生产到独立 Topic，灰度消费者订阅 | 隔离清晰；Topic 数量翻倍，需管理 |
| **同 Topic + 标签过滤** | 消息头带灰度标，稳定消费者跳过灰度消息、灰度消费者只消费灰度消息 | 简单；依赖 Broker 的过滤能力或消费端过滤，跳过的消息要正确处理位点 |
| **灰度消费组** | 灰度消费者单独消费组，仅在灰度环境接收 | 与业务耦合小 |

注意：灰度消息只能被**兼容的消费者**处理；若灰度生产者发布了新格式消息，稳定消费者必须能忍受（遵守 Schema 兼容性，见 [Kafka 生态](#/mw/kafka-ecosystem)），否则稳定侧消费失败。

### 数据与状态的灰度

灰度最难的是**共享的数据层**：

| 对象 | 风险 | 对策 |
| --- | --- | --- |
| **数据库结构变更** | 新版本需要新字段，老版本不认识；回滚后老版本遇到新数据 | **扩展-迁移-收缩（expand/contract）**：先加字段（可空/默认值）→ 双写/回填 → 切读 → 最后删旧；全程新旧版本都能运行；见 [发布策略](#/infra/release) |
| **缓存数据格式** | 新版本写入新格式，老版本读取反序列化失败 | 缓存 Key 带版本、格式向后兼容；灰度实例使用独立 Key 前缀或兼容读写 |
| **消息格式** | 同上 | 向后兼容的 Schema，只增不改 |
| **共享的外部副作用** | 灰度与稳定重复执行（发短信、扣款） | 幂等键；任务只让一方执行 |
| **配置** | 新版本依赖新配置 | 先发配置（对旧版本无害）再发代码，见前文 |
| **数据隔离灰度（影子库）** | 需要完全隔离灰度数据 | 压测/测试流量走影子库、影子表，生产灰度通常仍共享数据，所以靠兼容性 |

> [!WARNING] 回滚比发布更重要
> 灰度的价值是“出问题时影响小且能快速回退”。**如果新版本已经写入了老版本无法识别的数据，回滚就会引发二次事故**。设计时就要确认：老版本能读新版本写的数据吗？回滚路径演练过吗？

要点：

- **按版本拆分的指标是前提**：监控必须能区分灰度与稳定（指标带 `version` 标签、日志带版本字段、追踪带版本属性），否则灰度小流量的异常会被稳定流量稀释；
- **放量节奏**：小比例先跑足够长时间与样本量，再扩大；低峰期不能代表高峰，关键业务要覆盖高峰；
- **回滚方式**：摘除灰度标签/实例（秒级）；回滚代码前先确认数据兼容；
- **灰度与发布方式的关系**：金丝雀（逐步放量）、蓝绿（整套切换）、滚动更新（逐批替换实例）各有适用场景，见 [发布策略：灰度、蓝绿、特性开关与数据库变更](#/infra/release) 与 [CI/CD 流水线与 GitOps](#/infra/cicd)；K8s 层面的权重与灰度由 Ingress/服务网格承担，微服务层面的**标签路由**解决“多个服务联动灰度”的问题。

### 泳道（环境隔离）

“**泳道**”是更强的隔离形式：为某个特性/项目分配一整条独立的服务链路（一组带同一泳道标签的服务实例），**流量带泳道标时只在该泳道内流转**，缺失的服务回退到基线环境。用途：

- **多个特性并行测试**，互不干扰，共享一套基线环境，节省成本；
- 测试环境按特性隔离，避免“测试环境被别人占用/污染”；
- 与全链路灰度机制相同（标签染色 + 回退），区别是**泳道面向测试与开发流程，灰度面向生产放量**。

实现时同样需要：实例标签、全链路透传、消息/缓存/数据的隔离（测试泳道通常使用独立的 Topic、Key 前缀或测试库）。

## 落地建议

1. **先把基础打牢**：配置分层与变更治理、实例元数据标签、统一的上下文透传（含异步）、版本维度的监控；
2. **从网关 + HTTP 调用的标签路由起步**，逐步覆盖 RPC、消息、定时任务；每扩展一环要用**测试用例验证“标签不丢、不串、可回退”**；
3. **数据兼容放在设计评审**：每个涉及数据结构、缓存、消息的变更都要回答“旧版本能处理新数据吗？能回滚吗？”；
4. **平台化**：发布系统自动给实例打标签、管理灰度规则与放量节奏、自动对比指标与回滚，避免人工操作失误；
5. **演练**：定期演练灰度回滚、标签丢失（回退到稳定）、灰度实例全挂的场景。

## 常见坑

| 坑 | 说明与处理 |
| --- | --- |
| **标签在线程切换后丢失** | 线程池/@Async 未传上下文，后续调用走稳定版本，出现版本混用；装饰线程池、传递上下文 |
| **外部伪造灰度头** | 用户自带 `X-Gray` 进入灰度；网关清除外部同名头再生成 |
| **灰度实例无人调用或被误调用** | 标签与选路规则不一致；加回退监控与“灰度实例流量占比”看板 |
| **无标流量落到灰度实例** | 负载均衡未排除灰度实例；规则要求无标只选稳定实例 |
| **消息被稳定消费者处理了灰度格式** | 消息格式不兼容；Schema 向后兼容，灰度消息有过滤 |
| **定时任务重复或遗漏** | 灰度/稳定实例同时执行同一任务；任务按标签分配，幂等 |
| **缓存格式不兼容** | 新版本写缓存老版本读崩溃；缓存 Key 带版本或格式兼容 |
| **数据库字段删除过早** | 回滚后老版本报错；遵循扩展-迁移-收缩，延后删除 |
| **配置先后顺序错误** | 代码上线但配置缺失；先配置后代码，带默认值 |
| **监控无法区分版本** | 灰度问题被淹没；指标/日志/追踪都带版本维度 |
| **刷新配置导致有状态 Bean 丢失** | `@RefreshScope` 重建；状态与配置分离 |
| **配置覆盖关系混乱** | 同一项多处定义；统一单一来源，管理端点核对生效值 |

## 面试追问

> [!QUESTION] 全链路灰度是怎么实现的？
> 网关根据规则（用户、请求头、比例）给灰度请求染色，清除外部伪造的同名头；灰度实例在注册中心带版本标签；每一跳调用通过拦截器透传标签，负载均衡按标签优先选灰度实例，没有则回退稳定实例，无标请求只走稳定实例；RPC、消息、异步线程和定时任务也要透传或按标签分配，监控按版本拆分指标并支持秒级回退。

> [!QUESTION] 灰度中最容易出问题的地方是什么？
> 标签在线程切换、消息、定时任务处丢失造成版本混用，以及共享数据层的兼容性：数据库字段、缓存格式、消息格式新旧版本是否互相兼容、回滚后老版本能否处理新版本写入的数据。应采用扩展-迁移-收缩的数据库变更、向后兼容的格式，并演练回滚。

> [!QUESTION] 配置中心的动态刷新有什么限制？@RefreshScope 的原理？
> 业务开关、阈值等可以动态刷新，数据源、线程池大小、Bean 装配等通常不能或需要专门设计。RefreshScope Bean 首次使用时创建并缓存，刷新时清空缓存，下次访问重建以绑定新值，所以有状态 Bean 会丢状态、重建有懒加载延迟、@Value 默认不刷新，相关配置应整体放在同一配置项避免半新半旧。

> [!QUESTION] 配置变更为什么比代码发布更危险？怎么治理？
> 配置秒级全量生效、不经过发版流程，错误配置的爆炸半径大。要做校验、审批、指定实例灰度、观察、全量、一键回滚与审计，高危配置双人审批，变更标注到监控曲线，配置中心故障时用本地快照兜底，大促期间冻结变更。

> [!QUESTION] 灰度、蓝绿、金丝雀、泳道有什么区别？
> 金丝雀是逐步放量的灰度；蓝绿是维护两套完整环境并整体切换，回滚快但成本高；滚动更新是逐批替换实例；泳道是为特性分配一条隔离的服务链路，主要用于并行测试，也用同样的标签染色加回退机制。K8s 层的权重发布解决单服务流量切分，微服务标签路由解决多服务联动灰度。

> [!QUESTION] 灰度流量必须粘性吗？怎么保证？
> 尽量保证，否则同一用户一会儿新版本一会儿旧版本，体验不一致且难以排查。按用户 ID 或租户哈希决定是否灰度而不是随机，染色在入口一次完成并全链路透传，中途不重新决策。
