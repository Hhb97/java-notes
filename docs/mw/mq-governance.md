# 消息队列平台化与治理

> [!ABSTRACT] 核心要点
> - 当公司里有**几十个团队、几百个 Topic** 时，消息队列的问题已经不是“Kafka/RocketMQ 怎么用”，而是**“怎么让大家安全、规范、可观测地用”**。无治理的消息队列是**共享基础设施里最容易被一个业务拖垮全局**的那一类。
> - 治理的目标是三件事：**稳定（隔离与限流，防止互相拖累）、可控（谁创建、谁用、谁负责、怎么下线）、可见（轨迹、积压、延迟、成本）**。
> - 抓手是**平台 + SDK + 规范**：平台管 Topic/权限/配额/监控/工具，SDK 把序列化、追踪、重试、幂等、限流、降级等“最佳实践”固化进代码，规范与审计让违规可发现。
> - **最小可行治理（先做）**：Topic 与消费组**统一申请和命名**、**负责人信息**、**积压与延迟告警**、**关闭自动创建 Topic**、**生产者/消费者基础限流**、**死信队列与重放工具**。其余能力按痛点逐步补齐。
> - 衡量治理效果要看**SLO 与事故数**：发送成功率、端到端延迟、积压时长、可用性、因消息队列引起的故障数，而不是平台功能数。

## 为什么需要治理

典型的“自由使用”演化：

| 阶段 | 现象 | 后果 |
| --- | --- | --- |
| 少量团队 | 各自申请 Topic，口头约定格式 | 可以工作 |
| 规模增长 | Topic 命名混乱、无人负责、僵尸 Topic 无人敢删 | 运维成本上升，容量不可控 |
| 流量增长 | 某业务**大消息/高频发送/无限重试**把 Broker 打满 | **全公司消息延迟**（共享集群的邻居噪声） |
| 事故 | 消费者组名冲突“抢”别人的消息、误删 Topic、误重置位点 | **数据丢失、重复处理、资金/订单类事故** |
| 审计 | 无法回答“这条消息谁发的、谁消费了、为什么丢” | 排查靠猜，合规无法满足 |

核心矛盾：**消息队列是共享的、异步的、解耦的**——解耦带来灵活，也让问题**难以定位责任**。治理就是把“隐含的约定”变成“显式的契约与机制”。

### 命名规范与元数据

- **Topic 命名**：`<环境>.<业务域>.<数据/事件名>[.<版本>]`，如 `prod.order.order-paid.v1`；包含环境防止串用，包含业务域便于归属与计费；
- **消费组命名**：`<业务域>.<应用名>.<用途>`，**一个消费组对应一个应用的一个用途**，禁止多个不同应用共用消费组名（会互相抢消息）；
- **元数据**：负责人、等级、保留期、是否敏感数据、上下游依赖、Schema 版本，全部入库，平台页面可查；
- **环境隔离**：开发/测试/生产使用不同集群或不同命名空间，防止测试流量进入生产；
- **分级**：按重要等级放入不同集群或资源池，核心业务不与日志类大流量混跑。

### 容量模板

为不同类型提供**标准模板**（而不是让业务自选分区、副本、保留期）：

| 模板 | 分区/队列 | 副本 | 保留 | 适用 |
| --- | --- | --- | --- | --- |
| 核心交易 | 按吞吐与并行度（预留余量） | 3，`min.insync=2` | 7 天 | 订单、支付事件 |
| 普通业务 | 中等 | 3 | 3 天 | 通知、同步类 |
| 日志埋点 | 较多 | 2 | 1~3 天，压缩 | 日志、埋点、监控 |
| 变更日志（压缩） | 按键空间 | 3 | 压缩保留 | 状态同步、CDC |

具体参数以各引擎与自己压测为准，规划方法见 [Kafka 生产运维](#/mw/kafka-ops) 与 [压测方法与容量规划](#/design/eng-loadtest)。

## 权限、多租户与配额

| 手段 | 做法 |
| --- | --- |
| **认证与授权** | 每个应用独立账号/凭证；ACL 到 Topic/消费组粒度，**最小授权**（生产者只写、消费者只读）；凭证从密钥系统注入，定期轮换，见 [认证与授权](#/security/auth) |
| **配额与限流** | 按应用/租户限制生产与消费速率、连接数、请求占比；超限节流而不是打挂集群 |
| **资源隔离** | 重要业务用独立集群/资源池；同集群内用配额与优先级；大流量日志类与交易类分开 |
| **消息大小限制** | 统一上限（如 1MB 量级，按引擎调整），大对象走对象存储传引用，见 [对象存储与文件服务](#/design/case-objectstore) |
| **防误操作** | 删除 Topic、重置位点、缩短保留期等危险操作需二次确认/审批/冷静期；禁止业务账号拥有集群管理权限 |
| **敏感数据** | 标注敏感 Topic，访问更严、保留更短，传输加密，必要时字段级加密，见 [加密与密钥管理](#/security/crypto) |

## 统一 SDK 与使用规范

把容易出错的最佳实践**固化进 SDK**，比写文档更有效。

### 生产者

| 规范 | 说明 |
| --- | --- |
| **统一消息信封** | `messageId/eventId`（幂等键）、`eventType`、`eventTime`、`producer`、`traceId`、`schemaVersion`、业务 `key`；业务体是结构化数据，见 [事件驱动架构：事件设计、Outbox 与 Saga](#/design/event-driven) |
| **序列化与 Schema** | 统一格式（Avro/Protobuf/JSON + Schema 校验），发送前校验，见 [Kafka 生态：Connect、Streams 与 Schema Registry](#/mw/kafka-ecosystem) |
| **可靠发送** | 关键消息采用 **Outbox**（本地消息表）保证与业务事务一致；确认回调处理失败；有限重试 + 退避 + 落库兜底 |
| **背压与降级** | 发送缓冲满时的行为（阻塞/丢弃/落本地）要可配置；非核心消息可降级丢弃并计数 |
| **限流与大小检查** | SDK 内置速率与大小限制，超限快速失败并上报 |
| **异常上报** | 发送失败、重试、超时统一打指标与日志，不要吞异常 |
| **链路追踪** | 自动把 trace 上下文注入消息头，消费端续接，见 [链路追踪、日志与告警](#/infra/obs-trace) |

### 消费者

| 规范 | 说明 |
| --- | --- |
| **幂等模板** | 提供**幂等消费**工具（按 eventId 去重表/Redis），默认接入，而不是每个业务各写各的 |
| **重试与死信** | 统一重试策略：有限次数 + 指数退避；超过进入死信，禁止无限重试堵塞队列（毒消息）；区分**可重试异常**与**不可重试异常** |
| **顺序与并发** | 默认并发消费；需顺序的显式声明按 key 串行；说明并发度与分区/队列数的关系 |
| **处理超时** | 单条处理超时设置，避免卡住导致 Rebalance；慢任务异步化 |
| **位点提交** | 处理成功后提交，禁止“先提交后处理”；批量提交的故障语义要明确 |
| **优雅停机** | 停止拉取、处理完在途消息、提交位点后退出 |
| **消费灰度/回放** | 支持按时间/位点重放、按标签路由到灰度消费者（谨慎且需审批） |
| **版本兼容** | 容忍未知字段、对新增字段有默认值，遵守 Schema 兼容性 |

### SDK 的取舍

| 方式 | 优点 | 缺点 |
| --- | --- | --- |
| **薄封装 SDK**（在官方客户端上加规范） | 灵活、成本低、便于升级、保留引擎特性 | 靠自觉，无法强制 |
| **厚封装 + 统一 API（屏蔽引擎）** | 业务可切换引擎，规范强制 | 抽象泄漏、特性取最小公分母、维护成本高 |
| **代理/网关层**（HTTP/gRPC 收发） | 多语言接入、集中限流与鉴权、可灰度 | 多一跳延迟与单点，需高可用 |
| **云上托管消息服务** | 免运维，内置多数治理能力 | 成本与厂商绑定，灵活度受限 |

经验：**先用薄封装 + 平台管控 + 规范审计**，当多引擎并存且业务经常需要切换时再考虑统一 API；不要一开始就追求“完美抽象”。

## 观测：监控、轨迹与工具

### 监控与告警

分层的指标体系：

| 层 | 指标 | 告警思路 |
| --- | --- | --- |
| **集群** | 可用性、磁盘/网络水位、ISR/副本健康、请求延迟、控制器稳定性 | 容量预测 + 水位告警，早于故障 |
| **Topic** | 写入/读取速率、大小、分区倾斜、错误率 | 与基线对比，突增突降告警 |
| **生产者** | 发送成功率、耗时、重试、缓冲占用 | 失败率阈值 |
| **消费者** | **积压（条数与时间）**、消费速率、处理耗时、消费者数、Rebalance 次数、死信量 | **积压时长**比条数更贴近业务影响，按等级设阈值 |
| **端到端** | 生产到消费的延迟分位数 | SLO 告警 |
| **业务** | 关键事件的对账差异（如订单事件数 vs 消费处理数） | 兜底发现“消息丢了”这类隐蔽问题 |

告警要**路由到负责人**（来自 Topic/消费组元数据），而不是只发给平台团队；分级（P0 业务停摆、P1 积压增长、P2 趋势预警）并有处置手册（Runbook）。

### 查询、重放与死信工具

| 工具 | 价值 | 注意 |
| --- | --- | --- |
| **消息查询** | 按 Topic+位点/时间/messageId/业务 key 查看消息内容 | 敏感消息脱敏，查询需权限与审计 |
| **死信管理** | 查看、筛选、**批量重放或丢弃**死信，记录处理原因 | 重放前先修复根因；重放有幂等保障 |
| **位点管理** | 重置到时间点/最新/最早，限定于消费组且需审批 | **高危操作**，防误重置导致大量重复或丢失；留痕 |
| **消息重放（回放）** | 按时间窗口重放历史消息到指定目标（或测试环境） | 目标必须幂等；限速防止打爆下游 |
| **流量复制** | 生产流量复制到预发做验证或压测 | 隔离与脱敏 |
| **对账工具** | 比较上游事件数与下游处理数 | 发现“静默丢失” |

## 稳定性与容灾

- **集群分级与隔离**：核心交易 / 普通业务 / 日志大数据 / 测试环境分不同集群；重大活动前**扩容与限流预案**；
- **多机房**：同城双活（拉伸集群）或主备（异步复制）；平台需支持**流量与消费切换**的演练与位点翻译，见 [Kafka 生产运维](#/mw/kafka-ops) 的跨集群复制；
- **故障降级**：生产者在消息队列不可用时的降级策略：关键消息落本地库（Outbox）后重试，非关键消息丢弃并计数；消费者失败转死信；
- **限流与保护**：平台级总开关（熔断某 Topic 的写入、暂停某消费组）、慢消费者保护，防止一个坏消费者拖垮整个组；
- **变更管理**：扩分区、改参数、升级走灰度窗口与回滚预案；变更窗口避开大促；
- **混沌演练**：定期演练 Broker 宕机、网络分区、磁盘打满、消费者全部掉线，验证告警与预案，见 [稳定性工程：混沌实验与容灾演练](#/design/eng-chaos)。

## SLO 与成本

### 平台 SLO（示例结构）

| 指标 | 定义 | 目标思路 |
| --- | --- | --- |
| **发送可用性** | 成功发送请求数 / 总请求数 | P0 集群 99.99% 级别（按业务确定） |
| **端到端延迟** | 生产到可消费的 P99 | 核心 < 数百毫秒到秒级，按引擎与业务 |
| **积压恢复时间** | 突增后积压恢复到阈值内的时间 | 小时/分钟级，按等级 |
| **数据可靠性** | 已确认消息不丢（P0） | 副本与持久化配置达标，定期巡检 |
| **工具与支持** | 申请响应时间、故障响应 | 流程指标 |

SLO 要**与业务等级绑定**，并**公开**给使用方；对不符合规范的业务（如不接 SDK、不设告警）不承诺 SLO。

### 成本与容量

- **成本归属**：按 Topic/租户统计存储、流量、请求，分摊到业务，推动**保留期收紧、压缩开启、废弃 Topic 清理**；
- **容量预测**：基于历史增长趋势预测磁盘与带宽，提前扩容；
- **僵尸治理**：定期扫描无写入/无消费/无人负责的 Topic 与消费组；
- **压缩与降本**：压缩算法、合并小消息、减少不必要的副本（非核心）、冷数据下沉（引擎的分层存储能力）。

## 落地顺序

不要一上来建大平台，**按痛点分阶段**：

1. **止血（1~2 周）**：关闭自动创建 Topic；建立 Topic/消费组台账与负责人；积压与延迟告警接到负责人；消息大小上限；危险操作审批；
2. **规范（1~2 月）**：命名与模板；薄封装 SDK（信封、追踪、重试、死信、幂等模板）；Schema 契约与 CI 兼容性检查；ACL 与账号体系；
3. **可观测与工具（2~3 月）**：消息轨迹、查询、死信重放、位点管理、对账工具；多维监控与 SLO 看板；
4. **隔离与容灾（持续）**：集群分级、配额、限流；跨机房与演练；成本归属；
5. **持续运营**：事故复盘（见 [事故复盘与改进](#/design/eng-postmortem)）驱动治理规则；季度审计僵尸 Topic 与权限；规范演进与培训。

## 典型事故与教训

| 事故 | 根因 | 治理措施 |
| --- | --- | --- |
| 日志业务突发大流量，交易消息延迟 | 共享集群，无配额与分级 | 集群分级、配额与限流、重要业务独立资源 |
| 无限重试把毒消息卡死整条队列 | 失败 requeue 无上限 | SDK 默认有限重试 + 死信，区分异常类型 |
| 两个应用误用同一消费组名，消息被“抢走” | 命名无约束 | 消费组统一申请与归属校验 |
| 值班人员手动删 Topic/重置位点，造成数据丢失 | 无审批与保护 | 危险操作审批、冷静期、权限收敛 |
| 消息“丢了”无法定位 | 无轨迹与对账 | 全链路轨迹、对账、关键消息 Outbox |
| 扩分区后顺序错乱 | 变更未评估 key 映射 | 变更评审，涉及顺序的 Topic 禁止原地扩分区 |
| 上游改字段，下游批量反序列化失败 | 无 Schema 契约 | Schema Registry + 兼容性检查 + CI |
| 测试环境消费者连上生产 | 环境未隔离 | 环境前缀、网络隔离、凭证隔离 |
| 重大活动前才发现磁盘将满 | 无容量预测 | 容量模型、水位告警、扩容预案 |

## 检查清单

- [ ] 所有 Topic 与消费组是否有负责人、等级、用途登记？
- [ ] 是否关闭了自动创建 Topic，创建走模板与审批？
- [ ] 账号与 ACL 是否最小授权，凭证是否由密钥系统管理？
- [ ] 是否有配额与限流，核心业务是否与大流量业务隔离？
- [ ] 生产者与消费者是否使用统一 SDK（信封、追踪、重试、死信、幂等）？
- [ ] 是否有 Schema 契约与兼容性检查？
- [ ] 积压（时间维度）、延迟、错误率、死信量是否按负责人告警？
- [ ] 是否有消息轨迹、查询、重放、对账工具？
- [ ] 危险操作（删除、位点重置、缩保留）是否有审批与审计？
- [ ] 是否做过容灾与故障演练？是否定期清理僵尸 Topic？

## 面试追问

> [!QUESTION] 公司里消息队列被多个团队共用，你会怎么治理？
> 目标是稳定、可控、可见。先止血：关闭自动创建 Topic、建立 Topic 与消费组台账和负责人、积压延迟告警路由到负责人、消息大小限制、危险操作审批。再规范：命名与容量模板、统一 SDK（信封、追踪、重试、死信、幂等）、Schema 契约、最小授权。然后补可观测工具：消息轨迹、查询重放、对账，并做集群分级、配额限流和容灾演练。

> [!QUESTION] 如何防止一个业务打爆共享的消息集群？
> 按重要等级做集群或资源池隔离，核心交易不与日志类大流量混跑；在集群层用生产消费速率配额对应用节流；SDK 内置速率与消息大小限制；Topic 申请时评估容量并用标准模板；监控流量突增并有平台级熔断开关；大促前做扩容与限流预案。

> [!QUESTION] 消息“丢了”怎么定位？
> 靠消息轨迹和对账：按 messageId 查看生产、存储、消费各阶段事件。生产端有发送事件但 Broker 没有存储，说明发送失败；已存储但没有消费事件，说明消费端被过滤、异常或位点问题；再对比上游事件数与下游处理数发现静默丢失。关键消息用 Outbox 保证与业务事务一致。

> [!QUESTION] 统一 SDK 应该做哪些事？要不要屏蔽底层引擎？
> 固化信封（eventId、eventTime、traceId、schemaVersion）、序列化与 Schema 校验、追踪注入、有限重试与死信、幂等消费模板、限流与大小检查、优雅停机和异常上报。是否屏蔽引擎要权衡：薄封装灵活但靠自觉，厚封装统一但抽象泄漏、特性被降到最小公分母。通常先薄封装加平台管控，多引擎频繁切换时再考虑统一 API。

> [!QUESTION] Topic 的生命周期怎么管？怎么清理僵尸 Topic？
> 申请时登记负责人、用途、容量与等级，审批后按模板创建并自动配置权限与告警；运行期监控与定期审计；下线前先扫描无写入或无消费的 Topic，通知负责人确认，按先停写、观察、再停读、保留期后删除的顺序，防止误删，所有变更留痕。

> [!QUESTION] 消息队列平台的 SLO 怎么定？
> 按业务等级定义发送可用性、端到端延迟 P99、积压恢复时间、已确认消息的可靠性，并公开给使用方；对不接入规范 SDK、不设告警的业务不承诺；用事故数和 SLO 达成率衡量治理效果，而不是平台功能数量。
